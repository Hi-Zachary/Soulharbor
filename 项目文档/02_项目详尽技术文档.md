## 1. 设计原则

1. **安全与生成解耦**：危机相关场景走咨询路由与更强 DPO scale；不做临床诊断承诺。  
2. **单卡单 chat LoRA × 多 scale**：一份 4-bit 基座 + `dpo_synth_*`（PEFT 名 `chat`），咨询 / 闲聊用不同 scale；摘要走裸基座；`RLock` 串行 GPU。  
3. **Episode 写入零 LLM、Profile 旁路可提议、读取代码编排**：Episode 只做确定性分块 + 向量化；Profile 默认可 LLM→pending→确认；读路径规划器 → hybrid → AER 扩窗 → 链 → 覆盖度选择 → 全量 Profile；读侧可选 LLM 用于规划。  
4. **隐私默认可控**：用户可关记忆 / 一键遗忘；前端不展示记忆原文。  
5. **工程可部署**：SQLite 单文件、start.sh 一键启动（始终加载分类器与 LLM）。

## 2.1 模型组件说明书（是什么 / 为何选 / 作用）

> 完整卡片见 [`01` §五](./01_项目大纲与架构.md)。此处给技术文档用的职责对照；**不含**只做评测分词的 jieba 等工具库。

| 组件 | 是什么（一句话） | 为何选（一句话） | 在链路里干什么 |
|------|------------------|------------------|----------------|
| **Qwen3-14B** | 通义开源 14.8B 因果 LLM，强中文/指令 | 单卡 4-bit 可部署；够心理对话 | 唯一生成基座：对话 / 规划 / 摘要 |
| **chat LoRA** `dpo_synth_*` | DPO 对齐后的对话 adapter（线上 r=8 / α=16） | 不 merge、可调 scale；偏好「更共情少敷衍」 | 用户回复；咨询 0.7 / 闲聊 0.3；摘要走裸基座 |
| **MacBERT-base → intent ckpt** | 中文 BERT 改进（EMNLP'20 Findings）+ 二分类微调 | 快、稳、与生成解耦；分流任务 base 足够（验证准确率 99.7%） | `is_consult` → LoRA 强度与指标（不控记忆开关） |
| **BGE-M3** | BAAI 多语检索向量（arXiv:2402.03216），dense 1024 维 | 中文检索强、开箱即用；无需再训 | 记忆原文块 embedding + 读路径语义召回（assistant 块降权 0.55） |

**分工口诀：** MacBERT 管「咨询还是闲聊（强度）」；BGE-M3 + 字级 BM25 管「记忆混合召回」；AER 扩窗 / 跨会话链 / 覆盖度选择管「经历重建与去冗余」；Qwen+chat 管「怎么说」；会话摘要用裸基座。

## 3. 启动与进程模型

**脚本**：`product_app/start.sh`

1. `conda activate /root/autodl-tmp/CondaEnv/soulhar`（按需改为本机环境）  
2. `cd` 到仓库根  
3. 端口默认 `8000`；若被本服务占用则 kill 后重启，否则报错退出  
4. 自动选最新 `dpo_synth_*` / `bge-m3`  
5. `uvicorn product_app.app.main:app --host 0.0.0.0 --port $PORT --log-level info`

**startup（`main.py`）**：加载 `IntentClassifier` + `SoulHarborLLM`，并 `_MEMORY.set_llm(_LLM)`。

**并发**：

- GPU：生成引擎内 `threading.RLock` 串行所有生成调用（chat / 规划 / summary 共用一把锁）  
- `_LLM_EXECUTOR = ThreadPoolExecutor(max_workers=2)`：GPU 由 RLock 串行，小池只起限流排队作用  
- `_POST_TURN_EXECUTOR = ThreadPoolExecutor(max_workers=settings.post_turn_workers)`（默认 8）跑 post-turn（ingest / summary）  
- 流式：独立**非 daemon** 线程写完回复，即使客户端 Abort 也能落库  
- `_ADMIN_TOKENS: set[str]`：登录后生成 `secrets.token_hex(16)` 随机 token 加入集合；管理 API 从 cookie 取 token 与集合校验

## 5. 聊天主链路（详解）

### 5.1 非流式 `/api/chat`

1. 鉴权、解析 `text`、确保 `sid` / `conversation_id`；sid 跨用户不匹配时**静默 rotate**（写 warning 日志）  
2. `append_message(user)`；标题为空时取用户首条文本截 20 字做自动标题（`auto[:20] + ("…" if len(auto)>20 else "")`）  
3. `_prepare_chat_turn`：先调 MacBERT 分类得 `is_consult`；再调 `build_chat_context` 一次得到 `model_messages`（含记忆注入 + 摘要 + 未摘要原文）  
4. 在 `_LLM_EXECUTOR` 异步跑 `_LLM.generate(model_messages, is_consult=is_consult)`  
5. assistant 落库 + `append_turn_metrics`（`is_consult` + `route='consult' or 'chat'`）  
6. `_schedule_post_turn`（提交到 `_POST_TURN_EXECUTOR`）  

说明：当前实现 `build_chat_context` 只调用一次；`_prepare_chat_turn` 一次完成分类 + 上下文组装。token 计数用 Qwen3 tokenizer 精确计算（`SoulHarborLLM.count_tokens`）。

记忆写与摘要的触发时机（与第 6 步配合看）：`run_post_turn` 后调用 `ingest_message`——Episode：每轮分块 + BGE-M3 原样入库（**无 LLM 抽取、无 token 阈值**）；若开 Profile，每条 user/assistant 计入攒批，达 `MEMORY_PROFILE_LLM_TRIGGER_MESSAGES`（默认 5）或年龄阈值后，助理回合才用中文 LLM 提议最多 1 条 pending。会话摘要在未摘要消息累计 token 达 `memory_summary_window_max_tokens`（默认 3000）时触发；用裸基座（`disable_adapter`）生成。

### 5.2 流式 `/api/chat_stream`

前 1–5 步相同（共享 `_prepare_chat_turn`）；然后：

1. 先插入空 assistant 行拿 `message_id`（保证前端切会话也能查到占位）  
2. 后台**非 daemon** 线程 `generate_chat_stream`，chunk 入 `queue.Queue`  
3. `StreamingResponse(media_type="text/plain; charset=utf-8")` 吐给前端  
4. 结束或异常后 `update_message_content`（保留生成的回复）+ metrics + `_schedule_post_turn`  
5. 客户端 `Abort` 只停读流，**不取消**后台生成；后台最终通过 `_finalize_chat_turn` 写库

**生成内部取消机制**（`generate_chat_stream` → `_iter_stream`）：底层用 `TextIteratorStreamer` + 独立 worker 线程跑 `model.generate`；`CancelCriteria(StoppingCriteria)` 持有一个 `threading.Event`，每次 step 检查 `event.is_set()`。`_iter_stream` 的 `finally` 中 `cancel_event.set()` 触发停止条件，然后 `worker.join(timeout=5.0)`；若 5 秒后 worker 仍存活则视为僵尸线程，记 warning 并 detach（让其自然结束，不阻塞后续请求）。

**生成错误处理（`_chat_stream_producer`）**：LLM 异常时只把 `"\n（生成失败，请稍后再试）"` 推给客户端；只要 `chunks` 为空就**不写库**这条错误文本（防止历史被「（生成失败…）」污染）。若已有部分 chunks，则把已生成内容作为 assistant 文本正常落库。

### 5.3 意图分类

**分类器**：`IntentClassifier`  
- 目录：`{CLASSIFIER_RUN}/intent/checkpoint-*`（取最新步数）  
- Encoder：`chinese-macbert-base`  
- 输出：`is_consult ∈ {0,1}` 与概率（softmax 取 argmax）

**输入构造**（`main._classify_turn` → `_format_for_classifier` → `messages_for_classifier`）：只取最近 **1/2/3 条用户话轮**（随对话长度递增，与训练数据的 USER-only 形态一致），每条前缀 `[USER] ` 后拼成多行文本送进分类器；assistant 话轮完全不参与——分类器判断的是"用户这一轮在倾诉还是闲聊"，咨询师怎么回不影响这个判断。

**`is_consult` 当前用途**：

- 选择 chat LoRA scale（0.7 vs 0.3）
- 写入 `turn_metrics.route`（`consult`/`chat`）

`_route_hint` 在 `_prepare_chat_turn` 中未传值；`build_chat_context` 的 `route_hint` 参数保留接口但默认 `None`。

## 6. 生成引擎与 SoulHarborLLM

> 各模型「是什么 / 为何选 / 作用」见上文 **§2.1** 与 [`01` §五](./01_项目大纲与架构.md)。本节只写加载与调用细节。**产品只加载并使用一份 chat LoRA**，按场景切换 scale。

### 6.1 加载

1. 读 system 文件全文（启动时校验非空）  
2. `AutoModelForCausalLM` + `BitsAndBytesConfig(load_in_4bit=True, nf4, use_double_quant=True, compute_dtype=fp16)`；`attn_implementation='sdpa'`，不兼容时 fallback  
3. `PeftModel.from_pretrained(base, chat_path, adapter_name="chat")`  
4. `eval()`

Checkpoint 目录若含多个 `checkpoint-*`，按步数排序取**最大**者（`_pick_latest_checkpoint_dir`）。

### 6.2 Scale 切换（同一 chat adapter）

| 方法 | 行为 |
|------|------|
| `_activate_chat(is_consult)` | `set_adapter("chat")`；scale = 0.7（咨询）或 0.3（闲聊） |
| `generate_structured` | chat @ casual scale 0.3、temperature 0.0 |
| `generate_summary` | 裸基座（`disable_adapter`）、temperature 0.3 |

`_set_adapter_scale` 遍历所有 `LoraLayer` 并 `set_scale(adapter, scale)`。

### 6.3 Chat template 与多 system 合并

Qwen chat template **实质上只稳定保留第一条 system**。引擎在 `_build_history` 中把主 system 与调用方传入的全部 `role=system`（会话摘要、`<memory>` 等）用空行拼成**一条** system，再接 user/assistant。

`tokenizer.apply_chat_template` 强制 `add_generation_prompt=True` 与 `enable_thinking=False`。

### 6.4 生成参数

| 场景 | temperature | max_new_tokens | Scale | 备注 |
|------|-------------|----------------|-------|------|
| 对话（咨询/闲聊）| 0.6 | 1024 | 0.7 / 0.3 | `generate_chat` / stream |
| summary | 0.3 | 512 | —（关 LoRA） | `generate_summary` → `generate_base` |

`bad_words_ids` 屏蔽思考标记；`_strip_think` 防御性剥除残留思考块。

## 7. 记忆子系统（aer：原文库 + 查询时 AER）

> 完整方案见 `05_记忆系统_AER自适应经历重建_最终方案.md`。本节为代码级细节。

先把设计哲学说清楚：**记忆系统的所有"判断"都发生在查询时，写入时只有确定性操作。** 这意味着用户说的每句话都被当作"可能重要的经历"原样保存，而不是在保存前就被 LLM 判定"这条值得记、那条不值得"。代价是记忆库会大一些、检索逻辑要复杂一些；收益是从结构上消除了"写错"——因为根本没有"写时理解"这一步。对话里"我这次面试失败了"和"我总是失败"这两句话，前者会被原样存下，后者也会被原样存下，但**没有任何代码负责把它们升格成"用户是个失败者"**。下面按写、读、注入三条子路径展开代码级细节。

### 7.1 数据模型

**存储**：`memory_episode_chunks`（原文块）+ `memory_episode_embeddings`（BGE-M3 向量）+ `memory_embed_retry`（嵌入重试队列）+ `support_profile_*`（画像旁路）+ `memory_backfill_checkpoint`（回填断点）。详情见 `05` §3。

| 表 | 作用 |
|----|------|
| `users` | 含 `memory_enabled`（默认 1） |
| `auth_sessions` | token → user_id 映射 |
| `conversations` | 含 `title`、`summary`、`summary_updated_at`、`last_summarized_msg_id` |
| `messages` | 对话原文（`conversation_id, role, content, created_at`） |
| `memory_episode_chunks` | 记忆原文块（`UNIQUE(message_id, chunk_index)`，`is_deleted` 软删） |
| `memory_episode_embeddings` | 每块的 BGE-M3 向量 JSON |
| `memory_embed_retry` | 嵌入失败重试（`attempts < 5`） |
| `support_profile_items` / `sources` / `pending` | consent 画像：条目（`origin: explicit/confirmed`）、来源、待确认候选 |
| `turn_metrics` | 仅 `is_consult`、`route` |
| `triage_records` | 管理分诊（`status ∈ pending/tracking/resolved/ignored`） |

历史 flat 记忆表（`user_memories` / `memory_embeddings` / `memory_events` / `memory_index_meta`）仅存在于旧库；现行 `aer` 不使用。

### 7.2 写路径：`store/ingest.py`

`MemoryService.run_post_turn` → `MemoryEngine.ingest_message`：

1. 消息内容确定性分块（`chunker.py`）：≤500 字整段；否则按句界切分、按 150–350 字目标合并；
2. `upsert_chunks` 幂等落库（按 `(message_id, chunk_index)`）；BGE-M3 编码每块，失败进 `memory_embed_retry`，进程内 `process_embed_retries(limit=…)` 补跑；
3. **Profile 旁路**（`profile/service.py`，默认开）：
   - `detect_explicit`：「记住/别忘了/请记得…」→ `create_explicit`；
   - **`maybe_llm_propose`**（`MEMORY_PROFILE_LLM_PROPOSE=1`）：攒批触发后（消息数/年龄），助理回合且 pending 空时用 `proposer.py` 最多抽 1 条 → pending（须用户原文证据）；
   - `detect_propose_in_assistant`：「要不要我记住…」→ `add_pending`（弱补充；队列最多 8）；
   - `detect_confirm`：整句「可以/对/好的…」→ `pop_all_pending`，一次确认全部为 `confirmed`；
   - `detect_correct`：「A改成B」或「我现在不要A」→ 软删匹配项并可选写入新内容；
   - `detect_forget` / `detect_inspect`：忘掉关键词软删；查看只返回已确认偏好；
   - **`policy.validate`**：诊断词 / 人格标签 / 瞬时情绪前缀 / 与来源无足够重叠 → 拒绝；
4. Episode：无 token 阈值、无 LLM 抽取——每条消息都进库；Profile：默认助理后可 LLM 提议 pending（非直接写 active）。

### 7.3 读路径：`RetrievalPipeline.run`（`retrieval/pipeline.py`）

`build_chat_context` → `_engine.build_context`（`engine.py`）→ `RetrievalPipeline.run(query)`：

1. **QueryRouter**（`router.py`）：**无关键词正则**；有 LLM 时用规划器 prompt 输出 `direct`/`split` JSON（≤3 子查询）；否则整句 direct。
2. **hybrid 召回**：BGE-M3 cosine（assistant ×0.55）+ 字级 unigram/bigram BM25 → RRF（k=60）取 seed top-8；split 时各子查询召回后再 RRF。
3. **AER 扩窗**（`store/expand.py`）：连续性得分（0.40/0.22/0.18/0.10/0.10）≥0.28（连续失败 2 次停）；跨度 ≤12、窗内 ≤10 条。
5. **跨会话时序证据链**（`link.py`）：实体/语义/时间指数衰减/查询增益贪心串链。
6. **覆盖度贪心选择**（`select.py`）：top-6（相关 + 新覆盖 + 周桶多样性 − 冗余）。
7. **Profile**：`list_for_inject` **全量**注入 active 偏好（≤30），不按查询过滤。
8. `build_memory_block` 渲染 `<memory>`，token 预算 1600；超预算整行裁剪。Formatter 优先整段 user 原文（800/1000），极端超长才做 BGE 句子级语义截取。

### 7.4 注入：`service.build_chat_context`

- 记忆块以 **system 角色**加入，前缀为 `service.py:_MEMORY_SYSTEM_PREFIX`（"以下内容来自用户过往对话的检索结果，只是历史背景，不是用户本轮新说的话；能帮助回答就自然采用；和当前问题无关就忽略；冲突以当前说法为准；不要补充检索结果里没有的事实"，全文见 §8.2）。
- 块内只含 **user 原文**（`context/formatter._pick_snippet_messages`：assistant 只参与检索/扩窗，不写入 prompt），格式：

```
<memory>
[经历链 E1]
- 2026-07-20：上次说的那个室友小王…
  来源：conversation=…, message=…, pos=…
[支持偏好]
- 散步能缓解焦虑
</memory>
```

- **`build_chat_context` 完整流程**（`service.py`，顺序与代码一致）：
  1. 读 conversation 所有消息 → `classifier_msgs`（最近 `memory_recent_turns` 轮）；
  2. `model_msgs = []`；如传 `route_hint`（当前未传）追加 system；
  3. 读 `conversations.summary` → `build_session_summary_block` 追加为 system；
  4. 算 `exclude_message_ids` = 自 `last_summarized_msg_id` 以来已出现在 prompt 的消息 id；
  5. 若 `is_long_term_active(user_id)`：`_engine.build_context(...)` → 非空则追加 `<memory>` system；
  6. **Dynamic window**：自上次摘要以来的全部原文追加为 user/assistant（「要么进摘要、要么 verbatim，永不丢」）。

### 7.5 会话摘要（工作记忆，独立于长期记忆）

**触发**：未摘要消息累计 token ≥ `memory_summary_window_max_tokens`（默认 3000）时触发（Qwen3 tokenizer 精确计数）。

**模型**：`generate_summary` → 裸基座（`disable_adapter`）、temperature 0.3、max_new_tokens 512。

**流程**（`service._maybe_update_summary`）：

1. 取 `last_summarized_msg_id` 以来所有消息，统计 token；不足阈值则跳过；
2. `SUMMARY_SYSTEM` prompt：旧摘要 + 新窗口 → 新摘要（≤400 字，超长强制截断）；
3. 写 `conversations.summary`、更新 `last_summarized_msg_id`；窗口重置。

**并发**：`_summary_in_progress: set[str]` + `_summary_lock: threading.Lock` 防同会话并发；摘要生成在 post-turn 线程池跑，失败不阻塞主对话。

### 10.5 训练方法、超参与选型理由

> 原理公式与对比见 [`03`](./03_保研面试问答手册.md) 第二部分（LoRA / QLoRA / SFT / DPO）。  
> 权威超参文件：`train/configs/*.yaml`、`intent_classifier.json`。答辩时区分 **「yaml/脚本默认」** 与 **「线上落盘 adapter_config」**。

#### 10.5.1 方法总览

| 阶段 | 方法 | 原理一句话 | 框架 |
|------|------|------------|------|
| PT | Continued Pretraining + **QLoRA** | 领域语料上继续 CLM，适应心理中文分布 | LLaMA-Factory `stage=pt` |
| 主 SFT / 自我认知 | **SFT** + QLoRA | 只对助手 token 做交叉熵，学「怎么答」 | LLaMA-Factory `stage=sft` |
| 对话对齐 | **DPO**（sigmoid）+ QLoRA | 同上下文下抬高 chosen、压低 rejected 相对 reference 的偏好，无需单独 RM/PPO | LLaMA-Factory `stage=dpo` |
| 意图 | Encoder 分类微调 | MacBERT + 分类头，consult vs chat | HF Trainer |
| 记忆向量 | 不训 | 直接用 bge-m3 | — |

**为何 QLoRA + 单 chat LoRA：** 单卡要跑 14B；一份 DPO adapter + 运行时 scale 区分咨询/闲聊；摘要关 LoRA；无需第二份任务 LoRA。

#### 10.5.2 各阶段超参（`train/configs/`）

| 项 | PT | 主 SFT | 自我认知 | DPO | 意图 |
|----|----|--------|----------|-----|------|
| 配置文件 | `pt.yaml` | `sft_main.yaml` | `sft_self_cognition.yaml` | `dpo.yaml` | `intent_classifier.json` |
| LoRA r / α | 8 / 16 | 8 / 16 | 8 / 16 | 8 / 16 | —（全参微调 encoder） |
| 量化 | 4-bit | 4-bit | 4-bit | 4-bit | fp16 |
| cutoff | 1024 | 2048 | 1024 | 2048 | max_len 512 |
| lr | 5e-5 | 2e-5 | 3e-5 | **5e-6** | 2e-5 |
| epochs | 3 | **1** | **5** | 1 | 1 |
| batch × accum | 1 × 16 | 1 × 16 | 1 × 1 | 1 × 16 | 16 |
| 其它 | `qwen3_nothink`，warmup=20，`sdpa` | val_size 0.02，`load_best_model_at_end` | accum=1，lr 3e-5 × 5 epochs | `pref_beta=0.1`，sigmoid，cosine | MacBERT-base，eval_bs=32，seed=42 |

> **与历史文档的差异**：训练 yaml 现与线上落盘完全一致（r=8 / α=16），不存在"脚本 r=32 vs 线上 r=8"的割裂；DPO lr 取 5e-6（比 SFT 更低一档），自我认知取 3e-5 × 5 epochs（数据量 274 条、accum=1，用更高 lr 多跑几轮去学人设但保 `load_best_model_at_end` 防过拟合）。以 `train/configs/*.yaml` 为准。

#### 10.5.3 选型理由（答辩口径）

| 选择 | 原因 |
|------|------|
| **先 PT 再 SFT** | PT 补领域用词/知识密度；SFT 补任务格式与助手话术。只做 SFT 也能用，语料够时流水线更稳。 |
| **PT lr 更高（5e-5）、SFT/DPO 更低** | PT 要明显搬动领域分布；SFT/DPO 在已适配权重上微调，过大 lr 易毁指令遵循。 |
| **DPO 只 1 epoch、lr 5e-6、β=0.1** | 偏好对齐易过拟合/过度偏离 reference；β 过大使策略敢偏离、过小则几乎不学偏好。0.1 为常用稳妥值；DPO 的 lr 比 SFT 再低一档（5e-6），只做"在已有人设上的偏好微调"。 |
| **自我认知：accum=1、lr 3e-5、5 epochs** | 仅 274 条；accum=1 保证有效更新次数足够，稍高 lr + 多 epoch 让人设学得更稳，配合 `load_best_model_at_end` 防过拟合冲掉主 SFT。 |
| **全链路 r=8 / α=16 统一** | 训练 yaml 与线上 `adapter_config.json` 完全一致，复现即线上；α=2r 保证换 rank 时梯度量级稳定。 |
| **主对话 template=`qwen3_nothink`** | 产品对话关闭 thinking，降低延迟与格式噪声。 |
| **有效 batch ≈16（1×16）** | 单卡 14B QLoRA 显存紧；用 gradient accumulation 近似更大 batch。 |
| **cosine + 短 warmup** | 稳定收敛的默认组合；小数据 warmup 不宜过长。 |

#### 10.5.4 意图分类超参要点

- Encoder：`chinese-macbert-base`；epochs 1，lr 2e-5，train batch 16，eval batch 32，max_length 512，seed 42。
- 数据：train / valid / test = 3000 / 300 / 300，**正负严格 1:1**（各 1500 / 150 / 150），只保留 user 话轮（`[USER]` 前缀）、按轮数与字长对齐；验证准确率 99.7%、测试 99.0%（`outputs/classifiers/intent/train_meta.json`）。
- **不用 14B 做意图**：要快、稳、与生成解耦。

#### 10.5.5 CPT → SFT → DPO 训练详解（核心章节）

> 本节为 **CPT(PT) → 主 SFT → 自我认知 SFT → DPO** 这条对话主线单独立册；意图分类见 §10.5.1。  
> 权威配置：`train/configs/{pt,sft_main,sft_self_cognition,dpo}.yaml` + `train/scripts/llamafactory/run/run_pt_sft_sft.sh`（一键串联）+ `run_dpo_synth_minimax.sh`（单独 DPO）。  
> 数据详细来源/字段/样例见 [`04_数据构建与样例.md`](./04_数据构建与样例.md) §3–§6。

##### 10.5.5.1 全景：四个阶段、四份数据、四种损失

| 阶段 | 入口 | 数据集 | 框架 stage | 损失 | 基座权重 | 起始 LoRA |
|------|------|--------|-----------|------|----------|-----------|
| **CPT（continued pretraining, 俗称 PT）** | `pt.yaml` / `run_pt.sh` | `pt.jsonl`（24 443） | `pt` | **Causal-LM cross-entropy on 全 token**（assistant 段也参与 loss） | 裸 Qwen3-14B | 新建 `pt_*` |
| **主指令 SFT** | `sft_main.yaml` / `run_sft.sh` | `sft_instruction.jsonl`（20 000） | `sft` | **SFT cross-entropy on 助手 token（`assistant_loss_only`）** | 裸 Qwen3-14B（可挂 PT adapter） | 新建 `sft_*` |
| **自我认知 SFT** | `sft_self_cognition.yaml` / `run_sft_self_cognition.sh` | `sft_self_cognition.jsonl`（274） | `sft` | 同上，loss only on 助手 token | Qwen3-14B | 挂 `sft_*` 续训 → `sft_self_cognition_*` |
| **DPO** | `dpo.yaml` / `run_dpo_synth_minimax.sh` | `dpo.jsonl`（3 000） | `dpo` | **DPO sigmoid loss**： `−log σ(β·[(log πθ(chosen|x)−log πref(chosen|x)) − (log πθ(rejected|x)−log πref(rejected|x))])` | Qwen3-14B | 挂 `sft_self_cognition_*` 续训 → `dpo_synth_*`（线上 chat） |

**LoRA 在每阶段都重新 init 一个新 adapter，链式续训**：CPT 后产出 `pt_*`，主 SFT 把 `pt_*` 作 `adapter_name_or_path` 继续（同源输入），自我认知 SFT 再挂 `sft_*`，最后 DPO 挂 `sft_self_cognition_*`。四个阶段全部 **r=8 / α=16**（`train/configs/*.yaml` 与线上 `adapter_config.json` 一致），没有 merge 回基座，所有阶段都保留为独立 LoRA 目录（方便回滚与 A/B），线上 `product_app` 推理时按需加载对应目录。

##### 10.5.5.2 CPT：用的什么数据？`[USER]` 这种文字真的不影响训练吗？

**用的是什么数据——是问答对，不是长文章。** 上游 `archive/sources/llm/pt.json` 是 EmoLLM 项目整理的 **心理领域 Q-A 短片段**，平均每条约 110 字符（最长 836、最短 29），全部是「一个问题 + 一个简短解答」的单轮结构。`build_lmf_pt_jsonl.py` 用正则 `^\s*问题\s*[:：]\s*(?P<q>...)\s*\n\s*答案\s*[:：]\s*(?P<a>...)` 把每条切成 Q/A，拼成 `[USER] {q}\n[ASSISTANT] {a}`，写出 `{"text": ...}` 共 24 443 行。处理后样例（来自 `pt.jsonl` 第 1 条）：

```json
{"text": "[USER] 心理咨询师，我觉得我的胸闷症状越来越严重了，这让我很害怕。\n[ASSISTANT] 我能理解你的感受，首先我们要明确你的症状并不是生理问题，而是心理问题。我们可以尝试找出引发你胸闷的心理原因。"}
```

**`[USER]`/`[ASSISTANT]` 这种字面文字对训练有没有影响？——几乎没有，但有必要解释清楚。**

1. LLaMA-Factory 的 `stage=pt` **不使用 chat template**，直接把整段 `text` 当作一段连续文本做 **Causal-LM**：从 `[` 起一个 token 一个 token 往下预测下一个 token，整段（包括 `[USER]`、`[ASSISTANT]`、中文）都算 loss。也就是说，`[USER]` 这 6 个字符也参与模型对下一个 token 的预测。  
2. 那么会不会「学到这种奇怪符号」？**影响极小**，原因有三：
   - Qwen3 tokenizer 把 `[USER]` / `[ASSISTANT]` / `\n` 各自切成 **1 个 token**（因为这类英文方括号 + 全大写是预训练分布里很常见的边界标记，几乎不可能被切成 2 段）；
   - 训练完没人会再以 `[USER]...` 这种纯文本格式去问模型；真正推理走 `apply_chat_template`（Qwen 的 ChatML 格式），没有这些 token；
   - PT 的目的是「让基座在心理中文分布上多看几遍」，并不指望它学会这种「格式」。这一步主要在 **补语料 + 拉概率**，副作用可忽略。  
3. 那为什么还要套 `[USER]/[ASSISTANT]` 而不是直接 `Q:\nA:\n`？——**为下一阶段 SFT 做分布铺垫**：SFT 阶段的对话也是「先用户后助手」的轮次结构，CPT 让模型先在心理领域里见过「用户提问 → 助手回答」这种双行排布，到 SFT 时学 chat 格式更顺。**这是经验性设计**，不是必要条件。

**损失**：Causal-LM cross-entropy on **全 token**。具体地，假设 `text = [t1, t2, ..., tL]`，模型对每个位置 `i` 预测 `p(t_i | t_<i)`，loss = `−Σ log p(t_i | t_<i) / L`。没有 mask，整段都算。

**为什么 cutoff_len=1024 就够**：平均 110 字符 ≈ 50 token，1024 token 远大于均值；整段一次性前向即可。

##### 10.5.5.3 主指令 SFT：loss 只算在助手 token 上

**数据**：20 000 条 ShareGPT `conversations`（SoulChat ≈ 90% + EmoLLM data_pro ≈ 10%，首轮用户句签名做互斥去重），全部带统一 `system = "你是Soulharbor心理健康助手，请你用专业温和的方式帮助用户解决心理问题。"`，`tools = []`（主对话不教工具调用）。

**格式**：ShareGPT `{"conversations": [{"from": "human", "value": ...}, {"from": "gpt", "value": ...}, ...]}`，由 `dataset_info.json` 中 `formatting: sharegpt` + `columns.messages = conversations` 告诉 LLaMA-Factory 怎么读。

**怎么变 token？LLaMA-Factory 内部的关键步骤（精简伪代码，对应 `src/llamafactory/data/aligner.py` + `parser.py`）**：

```python
# 对每条 ShareGPT 样本
messages = [
    {"role": "system",    "content": row["system"]},
    {"role": "user",      "content": row["conversations"][0].value},
    {"role": "assistant", "content": row["conversations"][1].value},
    {"role": "user",      "content": row["conversations"][2].value},
    {"role": "assistant", "content": row["conversations"][3].value},
    ...
]
prompt_ids = tokenizer.apply_chat_template(messages[:-1], add_generation_prompt=True)
full_ids   = tokenizer.apply_chat_template(messages,      add_generation_prompt=False)

labels = [-100] * len(prompt_ids) + full_ids[len(prompt_ids):]
# 即：system/user/所有历史 assistant 之前的 token 都 mask 掉，loss 只回传到「当前 assistant 回复」对应的 token 上。
```

**要点**：
- `template=qwen3_nothink` + `enable_thinking=false` → 走 Qwen3 的非思考分支（无 `<think>...</think>` 段），和线上推理一致。  
- 标签 `-100` 在 PyTorch `CrossEntropyLoss(ignore_index=-100)` 里会被跳过——所以**只有本轮 assistant 的 token 参与损失**；这与 PT 的「全段算 loss」是本质区别，也是「SFT 让模型学会怎么回答」而不是「让它背下整段多轮对话」的关键。  
- 多轮对话里，每个 `from=gpt` 的回复都是独立的一段「标签非 -100」，分别参与同一个 loss 累加。  

**loss**：`SFT loss = −Σ_{i∈assistant token} log pθ(t_i | t_<i) / N_assistant`。PyTorch 实现里分母是「所有非 -100 标签数」。

##### 10.5.5.4 自我认知 SFT：极小数据 + 低 lr 续训

数据 274 条 ShareGPT 短对话，原始上游是 EmoLLM `self_cognition_EmoLLM` 85 条种子（人设文案都是「我是 EmoLLM…」），经 `build_lmf_sharegpt_self_cognition_soulharbor.py` 替换为 SoulHarbor 人设，再经 `expand_/rewrite_/soften_*` 扩到 274 条。

**与主 SFT 的关键差异**（在 yaml / 脚本里）：

```yaml
# sft_self_cognition.yaml
adapter_name_or_path: saves/qwen14b/lora/sft_<RUN_TAG>   # 挂主 SFT
lora_rank: 8
lora_alpha: 16
per_device_train_batch_size: 1
gradient_accumulation_steps: 1     # ← accum=1，因为 274 条 × accum 大 → 有效 batch 过小、有效更新不足
learning_rate: 3.0e-5              # ← 比主 SFT 的 2e-5 略高：人设数据短、任务单一，用稍高 lr 更快学会
num_train_epochs: 5.0              # ← 小数据多跑几轮 + load_best_model_at_end 防过拟合
cutoff_len: 1024                   # ← 比主 SFT 短，对话本来就短
val_size: 0.02
warmup_steps: 20
```

**为什么是 accum=1**：`effective_batch = per_device × accum × n_gpu`。自我认知是单卡 1×1×1=1，274 个样本跑 5 epoch = 1370 个 optimizer step；如果 accum=16，5 epoch 只有约 85 个 step，对一个 LoRA 来说根本来不及动权重。accum=1 是「小数据专用设置」。

**为什么挂主 SFT 续训**：让 LoRA 先在 2 万条主对话上学会「SoulHarbor 怎么回话」，再学 274 条「SoulHarbor 是什么」——人设不会被新学的语气盖掉，也不会因为从零训而把主对话能力忘了。

##### 10.5.5.5 DPO：chosen vs rejected 的偏好对齐

**数据**：3 000 对 ShareGPT 上下文 + `chosen`/`rejected` + `meta`。  
- **Prompt 上下文**：`conversations` 到「待回复的用户句」为止（最后一轮通常 `from=human`）。  
- **Chosen**：取自 SoulChat 原文或裁判选出的较好回复（更共情、更具体）。  
- **Rejected**：用 **MiniMax-M2.7**（`rejected_gen_model="MiniMax-M2.7"`、`temperature=0.8`）按「敷衍/欠共情/略说教」指令生成；`check_rejected_quality.py` 过滤 `rejected_gen_is_usable=false`。  
- **互斥**：`meta.excluded_sft` 字段记录了用作互斥基准的 SFT 文件路径，保证 DPO 的 prompt 不会出现在主 SFT 训练样本里，避免「同一个对话既 SFT 又 DPO」造成的分布泄漏。

**格式**：`dataset_info` 注册 `ranking: true`，LLaMA-Factory 会把同一条 sample 拆成两轮去算：

```json
{
  "conversations": [{"from":"human","value":"..."},{"from":"gpt","value":"..."},{"from":"human","value":"..."}],
  "chosen":   {"from":"gpt","value":"<较好的回复>"},
  "rejected": {"from":"gpt","value":"<敷衍的回复>"}
}
```

**DPO 损失（`pref_loss=sigmoid`，最经典形式）**：

```
L_DPO(θ) = −E_{(x, y_c, y_r) ∼ D} [
    log σ( β · ( Δ_c − Δ_r ) )
]
Δ_c = log πθ(y_c | x) − log π_ref(y_c | x)   # chosen 相对 reference 的对数概率差
Δ_r = log πθ(y_r | x) − log π_ref(y_r | x)   # rejected 相对 reference 的对数概率差
```

直觉：**让 chosen 相对 ref 的概率差 > rejected 相对 ref 的概率差**，从而拉高 chosen、压低 rejected。`π_ref` 是冻结的参考策略。

**`π_ref` 从哪里来？——LLaMA-Factory 的简化做法**（对我们这个 14B QLoRA 场景）：**复用基座 Qwen3-14B + 当前 adapter 的 base 部分**作为 reference（同源同分布），不再额外加载一个 ref_model。这意味着 `Δ_c − Δ_r` 在数值上等价于「策略相对 base 的偏移差」，省一半显存；效果上与论文等价形式略有差异，但 LLaMA-Factory 实测可用、显存友好，是社区默认选项。

**`pref_beta=0.1` 的含义**：β 是 KL 强度的倒数（越小越保守、越不敢偏离 ref；越大越激进）。**0.1 是社区常用稳妥值**：心理对话希望贴合 chosen 的偏好、又不能太偏离 SFT 已经学好的话术；太大易「过度共情」生成复读模板，太小则几乎不学偏好。

**`pref_loss=sigmoid`** 是原版 DPO（论文 *Direct Preference Optimization*，Rafailov et al., NeurIPS 2023）；与 `hinge`/`ipo`/`kto` 等变体的区别仅在「margin 怎么映射成损失」，本题口径采用原版 sigmoid。

**DPO 超参与前序阶段的关系**：训练脚本与 yaml 全部 **r=8 / α=16**，lr 取 **5e-6**（比 SFT 的 2e-5 更低一档）——DPO 只在"已经对齐好的 chat LoRA"上做偏好微调，不希望再大动权重；`pref_beta=0.1` 是社区常用稳妥值。线上落盘 `dpo_synth_*/adapter_config.json` 与此完全一致，没有"脚本与线上 rank 不一致"的问题。

##### 10.5.5.6 通用训练基础设施（贯穿四个阶段）

**QLoRA 4-bit**：基座 14B 用 bitsandbytes NF4 量化到 4-bit，前向时反量化到 fp16；LoRA 权重以 fp16 训练、可学习参数 ≈ r × (d_in + d_out) × n_target_layers，约 30~120 M（r=8 vs 32 差 4 倍）。这样单卡 A100 80G 能塞下 14B + LoRA + KV cache + 优化器状态。

**`lora_target=all`**：LLaMA-Factory 会展开到当前模型的所有线性层（Qwen3-14B 的 `q_proj/k_proj/v_proj/o_proj/up_proj/down_proj/gate_proj` 共 7 个 target × 40 层）。r=8 时 trainable ≈ 8 × (5120 + 5120) × 7 × 40 × 2 ≈ 18 M；r=32 时 ≈ 73 M。

**`flash_attn=sdpa`**：用 PyTorch 2.x 的 `F.scaled_dot_product_attention`（不依赖额外 flash-attn 编译）；与 Qwen3-14B 的 GQA 兼容。  
**`gradient_checkpointing=true`**：在前向时丢弃中间激活，反向时重算，节省约 30% 显存；代价是 step 时间 +20~30%。  
**`per_device_train_batch_size=1` × `gradient_accumulation_steps=16`**：单卡显存紧，effective batch ≈ 16（足够稳的梯度估计）。  
**`fp16=true`**：与 4-bit 基座反量化后的 dtype 对齐；LoRA 权重以 fp16 训练，适配本仓库单卡训练配置。  
**`lr_scheduler_type=cosine` + `warmup_steps=20`**：经典组合；warmup 让前期 lr 从 0 慢慢升，避免把刚加载的 adapter 打飞。  
**`seed=42`**：与数据集划分、shuffle 顺序对齐——可复现实验的前提。

**`template=qwen3_nothink`**：自定义模板名，对应 `template.py` 中关闭 `<|im_start|>think` 块的配置，**强制不输出 思考段**，与线上推理 prompt 完全一致。

**`cutoff_len` 的选取**：
- PT 1024：平均 110 字符 ≈ 50 token，1024 远大于均值；PT 不需要长上下文。
- 主 SFT / DPO 2048：多轮心理对话平均 11.3 轮，token 数 P95 约 1500~1800；2048 覆盖绝大多数样本，少数被截断。
- 自我认知 1024：对话普遍 ≤ 4 轮。

##### 10.5.5.7 一键串联脚本：`run_pt_sft_sft.sh`

代码片段（精简注释版，便于答辩时贴屏）：

```bash

# 3) 自我认知 SFT：基座 + 挂主 SFT adapter 续训（rank 8/16, accum=1, lr=3e-5, 5 epochs）
```

##### 10.5.5.8 关键超参选型理由（覆盖 §10.5.3，加深）

| 选择 | 为什么是这个数 |
|------|----------------|
| **CPT lr=5e-5**（SFT 是 2e-5、DPO 是 5e-6） | CPT 要明显搬动领域分布；lr 小了等于没训。SFT/DPO 在已适配权重上微调，过大 lr 易毁指令遵循。5e-5/2e-5/5e-6 的「阶梯」是 LLaMA-Factory + QLoRA 中文社区常用组合。 |
| **CPT cutoff=1024** | 平均文本 110 字符 ≈ 50 token；1024 够用且省显存。 |
| **主 SFT cutoff=2048** | 多轮心理对话 P95 约 1500~1800 token；2048 覆盖绝大多数样本。 |
| **CPT/SFT/DPO 都用 cosine + warmup_steps=20** | 短 warmup 对 LoRA 够稳定；cosine 末段 lr 接近 0，模型有充分时间「收敛」到当前分布。 |
| **CPT/SFT/DPO 都 accum=16**（自我认知除外） | 单卡 14B QLoRA 显存紧；accum 模拟更大 batch，让梯度估计更稳。 |
| **自我认知 accum=1 / lr=3e-5 / 5 epoch** | 274 条 × accum=16 = 17 step，太少；accum=1 = 1370 step（5 epoch）。人设数据短而单一，稍高 lr 学得快，多跑几轮用 `load_best_model_at_end` 挑验证集最佳 checkpoint 防过拟合。 |
| **DPO 只 1 epoch、lr 5e-6** | 偏好对齐易过拟合 / 过度偏离 reference；少 epoch + 低 lr 把它限制在「微调」而不是「重训」。 |
| **DPO β=0.1** | β 是 KL 强度的倒数；0.1 是社区常用稳妥值。 |
| **DPO `pref_loss=sigmoid`** | 原版 DPO 损失形式（Rafailov et al., 2023）。 |
| **全链路 r=8 / α=16** | 训练 yaml 与线上 `adapter_config.json` 完全一致；α=2r 保证换 rank 时梯度量级稳定。chat 更小 rank 足够做偏好偏移且省显存。 |
| **`lora_target=all`** | Qwen3-14B 全部线性层都覆盖；不漏 MLP 才能学好分布变化。 |
| **`gradient_checkpointing=true`** | 4-bit 14B 单卡显存仍紧；用时间换空间（step +20~30%）。 |
| **`fp16=true`** | 与 NF4 反量化 dtype 对齐；本机环境 fp16 路径最稳。 |
| **`flash_attn=sdpa`** | 不依赖额外编译；Qwen3 GQA 兼容。 |
| **`template=qwen3_nothink` + `enable_thinking=false`** | 强制关闭思考段，与线上 prompt 完全一致；省延迟、减少格式噪声。 |

##### 10.5.5.9 常见疑问 FAQ（答辩高频）

1. **PT 既然只是「看一遍文本」，为什么还需要 LoRA？**——全参微调 14B 单卡放不下；QLoRA 是单卡 14B 训练的唯一现实路径。LoRA 的隐式正则（只动低秩增量）也防止在小语料上过拟合。
2. **CPT、SFT、DPO 产物为什么不 merge？**——(a) 合并后无法单独 A/B；(b) 线上只挂最终 `dpo_synth_*`，中间产物保留独立目录便于回滚；(c) 训练 chain 中某一步坏了可以单独重训。
3. **如果只有单卡显存不够，CPT/SFT/DPO 能否省一步？**——可以跳 CPT 直接 SFT，效果略有下降（领域词频没补），见 §10.5.3「先 PT 再 SFT」理由。本仓库默认跑全链，因为训练一次性成本可控。
4. **`adapter_name_or_path` 续训时，LoRA 权重是接着训还是重新 init？**——LLaMA-Factory 续训时会**加载已存在的 adapter 权重**（不是重新 init），从已有 r/α/dropout 继续训练；新增 target 层会 init。
5. **`save_steps` 与 `load_best_model_at_end` 怎么配合？**——`save_strategy=steps` + `save_steps=50/200` 每 N 步存一个 checkpoint；`load_best_model_at_end=true` + `eval_strategy=steps` + `metric_for_best_model=eval_loss` 在训练结束时回选验证集 loss 最低的 checkpoint 作为最终产物。自我认知 yaml 没开 `load_best_model_at_end`（数据太少，val_size=0.02 不稳）。

### 10.6 主对话离线评测（SoulChat 自动指标）

路径与说明：

- 脚本：`evaluate/dialogue/`；数据：`evaluate/dialogue/data/soulchat_{seen,unseen}_1k.jsonl`；runs：`evaluate/dialogue/runs/soulchat_corpus_eval_20260426_092741/`（说明见 `evaluate/dialogue/docs/主对话评测说明.md`、`evaluate/README.md`）
- 汇总 JSON：`evaluate/dialogue/runs/soulchat_corpus_eval_20260426_092741/aggregate_per_model_seen_unseen.json`
- 计分实现：`evaluate/dialogue/lib/metric.py`（jieba 分词 + NLTK BLEU + rouge 库）

#### 10.6.1 评测设置

| 项 | 内容 |
|----|------|
| 语料 | SoulChatCorpus，按「是否进过训练分布」切 **seen / unseen** 各 **1000** 条 |
| 任务 | 给定 instruction（上文），模型生成回复，与参考 `output` 比自动指标 |
| 对比模型 | **base**（裸 Qwen3-14B）、**sft**（自我认知 SFT LoRA，run 目录名 `self_cognition`）、**dpo**（线上 chat LoRA `dpo_synth_*`） |
| 汇总方式 | **每个模型单独算**：对该模型在 seen、unseen 上的指标按预测条数加权平均（各 1000 → 等价算术平均），得到 3 组结果 |

#### 10.6.2 指标含义与计算

中文先用 **jieba** 切成词序列，再在词级上算分（不是按字符硬切）。

| 指标 | 含义 | 怎么算（直觉） |
|------|------|----------------|
| **BLEU-1…4** | 生成文本与参考的 **n-gram 精确率**（越高越像参考的用词组合） | 对每条样本算 sentence BLEU（平滑 `method1`），再对全集平均；BLEU-n 表示最多看到 n 元词组。实现里同时报告 1～4，分数 ×100 |
| **ROUGE-1** | 与参考的 **词重叠**（偏召回的 F1） | unigram 重叠的 F 值 ×100 |
| **ROUGE-2** | **二元词组**重叠 F 值 ×100 | 比 ROUGE-1 更严，要求相邻两词也一致 |
| **ROUGE-L** | 基于 **最长公共子序列（LCS）** 的 F 值 ×100 | 允许词序不完全相同，仍奖励「大段结构相近」 |

面试口径：

- BLEU 偏 **「像不像参考答案的用词」**（精确率视角）；ROUGE 偏 **「参考里的信息盖住了多少」**（召回/重叠视角）。  
- 心理对话的参考回复并非唯一标准答案，**自动指标只能作相对比较**（base → sft → dpo），不能单独证明「共情更好」。  
- 与 SoulChat 论文常用的 BLEU/ROUGE 报告方式一致，便于横向对照。

#### 10.6.3 结果（seen+unseen 加权，每模型 n=2000）

| 模型 | BLEU-1 | BLEU-2 | BLEU-3 | BLEU-4 | ROUGE-1 | ROUGE-2 | ROUGE-L |
|------|--------|--------|--------|--------|---------|---------|---------|
| base | 13.23 | 5.55 | 2.50 | 1.32 | 20.52 | 4.17 | 15.04 |
| sft | **29.56** | **13.06** | **6.90** | **4.17** | 30.65 | 7.89 | **24.64** |
| dpo | 27.91 | 12.59 | 6.46 | 3.75 | **31.49** | **8.06** | 24.44 |

#### 10.6.4 结果说明什么

1. **相对 base 大幅提升**：SFT / DPO 的 BLEU-1 约 **+14～16**，ROUGE-L 约 **+9～10**，说明领域 SFT + 对齐后，回复在词面与参考心理对话更接近，不是「微调无效」。  
2. **SFT 与 DPO 同量级**：DPO 的 BLEU 略低于 SFT，但 ROUGE-1/2 略高或持平——符合直觉：DPO 优化的是 **偏好（更共情、少敷衍）**，不一定单调抬高 n-gram 重合；自动指标上两者都远强于 base。  
3. **seen / unseen 分开看时接近**（见各 `*_seen` / `*_unseen/metrics.json`）：未见集没有断崖，说明不是只背训练集。  
4. **局限**：BLEU/ROUGE 不直接测安全、危机处理、记忆使用；这些靠记忆长程 QA、人工抽查与产品规则补充。

## 12. 已知限制与工程注意

1. **首 token 延迟**：读路径记忆检索是纯代码编排（无逐轮 LLM），开销主要是向量与词法打分；可选 LLM 拆句/重排会拉长 TTFB，默认关闭。  
2. **DPO 否认记忆**：模型有时声称「AI 无记忆」；记忆块 system 前缀与主 system 需协同，不能只靠复杂规则。  
3. **原文库无写时生命周期**：已结束的旧处境仍可能被召回；主要靠查询相关选择、覆盖度选择与 token 预算抑制，抗 stale 主要依赖读路径。  
4. **单卡串行**：chat / 规划 / summary /（可选）Profile 提议抢同一把锁；Episode 写路径无 LLM。  
5. **SQLite + 混合检索**：语义侧默认用 FAISS `IndexFlatIP` 按用户缓存（`MEMORY_ANN_ENABLED=1`，指纹失效重建；失败回退 Python cosine）；词法 BM25 仍扫文本。单用户块数很大时再考虑 HNSW / 外置向量库。  
6. **不宣称临床级**：危机主要靠分类器进咨询路由与温和话术，不做自动报警产品承诺。  
7. **FastAPI version 字符串 0.2.0**：与文档叙述的能力描述一致即可，版本号是否同步不影响功能。

## 13. 推理参数与解码策略详解

> 这一节把生成参数都摆出来，并解释**为什么这么选**。面试如果被追问"top_p 0.95 是不是有点高""为什么 0.6 温度不 0"，可以直接引本节。

### 13.1 主对话参数（`chat_model.py` 默认 + `apply_chat_template`）

| 参数 | 值 | 为什么 |
|------|---|--------|
| `temperature` | **0.6**（引擎默认） | 高于 0.7 易跑偏（情绪化/越界），低于 0.4 易重复啰嗦。0.6 是「有温度但不失控」的折中。 |
| `top_p` | **0.95**（引擎默认） | 核采样概率阈值；低于 0.9 易出现模板化回复；等于 1.0 不裁剪（不可取）。 |
| `repetition_penalty` | **1.08** | 轻惩罚重复。≥1.15 易句法拗口；≤1.0 等于不惩罚。 |
| `bad_words_ids` | `["", ""]` | 禁用 thinking 块——product 场景不需要 CoT，避免泄露推理过程给用户。 |
| `enable_thinking` | `False` | 关闭思考模式，降低延迟与格式噪声。 |
| `max_new_tokens` | **1024**（默认 `SOULHARBOR_LLM_MAX_NEW_TOKENS`） | 单轮回复上限；中文共情回复通常 200-600 字。 |
| `attn_implementation` | `sdpa`（不兼容时 fallback 去掉） | 不强制要求 flash-attn；PyTorch SDPA 在大多数 GPU 上已够用。 |
| `seed` | 42 | 引擎初始化时设置，便于复现。 |

### 13.2 规划 / 可选重排 / summary 参数

| 场景 | temperature | max_new_tokens | adapter / scale | 理由 |
|------|-------------|----------------|-----------------|------|
| 摘要 | **0.3** | 512 | 裸基座 | 客观压缩，避免 DPO 腔 |
| Rerank（历史 id 数组）| **0.1** | **128** | chat @ 0.3 | 现行记忆不使用（特征重排替代） |
| 对话（咨询/闲聊）| **0.6** | 1024 | chat @ 0.7 / 0.3 | 见 13.1 |

### 13.3 解码策略选型决策树

```
你想要的输出是什么？
├── 严格的结构化 JSON（tool-call、id 列表）
│   └── temperature=0.1 + max_new_tokens 小
│        └── 可选 json_repair 兜底（`_repair_json`：去前缀、去尾、补引号、去尾逗号、补闭括号）
├── 客观压缩（会话摘要）
│   └── temperature=0.3 + disable_adapter（裸基座）
├── 自然语言对话（用户回复）
│   └── temperature=0.6 + repetition_penalty=1.08 + enable_thinking=false
│        └── 路由强度由 LoRA scale 控制（咨询 0.7 / 闲聊 0.3）
└── 数学/代码/CoT（不在本项目）
    └── temperature=0.6 + enable_thinking=True（未用）
```

**面试金句**：「参数选择不是审美问题，是分布匹配问题——对话配 DPO 偏好温度，摘要关 LoRA 走基座做客观压缩。」

### 13.4 进阶：什么时候用 beam search、min_p、 mirostat

> **本项目都没用**，但解释为什么、什么时候该用。

- **Beam search（num_beams>1）**：适合有明确正确答案的任务（翻译、ASR）。**不适合开放式对话**——会输出最"安全"的回复，反而显得敷衍。本项目不用。  
- **min_p**（min probability sampling）：本项目用 top_p=0.95 替代。  
- **mirostat**（自适应困惑度控制）：用于长文本生成时维持稳定的"惊讶度"。对话场景不需要；长篇摘要可考虑。  
- **DRY / repetition_penalty（按 n-gram）**：1.08 的全局惩罚对中文短句有时过激，未来可换 DRY sampler（避免常见 n-gram 重复）。

## 14. 记忆评测与可观测性

> 面试最容易被问"你怎么证明你的记忆是好的"。现行记忆（aer）的正式评测是**长程 QA 对比**（同协议对照 Mem0），见 `06_记忆系统_对比实验设计.md` 与 `evaluate/memory/episodic_eval/`。

### 14.1 记忆评测（现行）：长程 QA（AER vs Mem0）

- **数据**：`evaluate/memory/data/all_30.jsonl`（30 条真实长程咨询弧，6 类 × 5）。
- **协议**：每个方法按同一对话流逐轮 ingest；延迟测试点用**固定 reader**（MiniMax-M3）只接收"该方法的记忆检索块 + 测试题"作答（`run_qa_episodic.py`）；Mem0 同协议跑（`run_qa_mem0.py`）。
- **指标**：QA 准确率（MCQ 精确 + judge）、Staleness 率、内容 F1（对 gold 应记/应忘）。
- **结果（真实跑次）**：

| 方法 | QA 准确率 | Staleness 率 | 内容 F1 |
|---|---|---|---|
| **AER（aer）** | **91%–93%** | **7%–14%** | **0.79–0.89** |
| Mem0 | 64% | 43% | 0.48 |

逐类：context_recall 0.93 vs 0.47、cross_session_integration 0.93 vs 0.60、current_state 1.0 vs 0.60、detail_recall 0.93 vs 0.87、preference_recall 0.93 vs 0.73、temporal_sequence 0.73 vs 0.60。消融（固定 top-k）：QA 84.4% vs 覆盖度选择 91–93%。
