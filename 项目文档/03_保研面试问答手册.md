# 第一部分：项目答辩问答（保研高频）

> **写作约定**：每个 Q 给出"老师可能怎么问 → 你怎么答"。回答从 PPT/口述视角出发，强调"为什么这样做 + 怎么证明这样做是好的"，不罗列工程细节（代码细节老师看不到，强行背只会翻车）。

## 一、开场与项目定位

### Q1. 用一分钟介绍 SoulHarbor。

**答（推荐结构：场景 → 系统 → 边界）：**

> "我做的是 SoulHarbor，**校园心理健康辅助对话系统**。它跑在一个 14B 的开源大模型上，外挂了几个小模型/机制：
>
> - 一个 **MacBERT-base** 二分类做意图分流（只控语气强度）；
> - 一个 **BGE-M3 + 字级词法检索**做长期记忆的混合召回；
> - 一份 **chat LoRA（DPO）** 承担对话生成（咨询/闲聊不同 scale）；会话摘要走裸基座。
>
>
> 产品边界是**辅助倾听与情绪支持**，不替代诊断、不报警、不开药；用户可关记忆/一键遗忘；管理端做匿名分诊。"


### Q2. 这个项目的核心问题定义是什么？为什么不是直接接一个大模型 API？

**答：** 直接用通用大模型做心理支持，三个坑：

1. **路由不稳**：用户可能问候天气也可能倾诉自杀倾向，模型语气与干预强度失控；
2. **跨会话失忆**：保研焦虑、异地恋这种话题，用户往往讲很多轮、跨很多天，模型每轮从零开始；
3. **记忆乱写乱提**：该记的不记、不该记的乱记，或寒暄时硬塞隐私。

SoulHarbor 的解法是**职责解耦 + 场景化工程整合**：

- 用独立小分类器管"语气强度"（不依赖大模型自我克制）；
- 用长期记忆"原文库 + 查询时重建"管"个性化"（可控注入、只存原文）；
- 最后用 Web/管理端做成可演示的闭环。

**面试加分点**：强调这是**系统整合**而非"基础算法创新"——保研更看重"问题定义 + 解决思路"。

### Q3. 这个项目的创新点怎么表述？

**答（保研稳妥版）：**

1. **分类只控"语气强度"，不控"该不该查记忆"**（安全/路由与生成解耦）；
2. **单卡单 chat LoRA × 多 scale**：咨询 0.7 / 闲聊 0.3；摘要走裸基座；
3. **记忆写路径零 LLM（原文库）+ 读路径查询时重建**：不抽取、不归纳；规划器 → hybrid → AER 扩窗 → 证据链 → 覆盖度选择 → 全量 Profile；
4. **consent 确认制画像**：稳定画像必须经"助理提议 → 用户确认"，政策层拦截诊断词/人格标签/瞬时情绪；
5. **离线指标有量级提升**：记忆长程 QA（同协议对照 Mem0）QA 准确率 **93% vs 64%**、内容 F1 **0.89 vs 0.48**。

### Q4. 三分钟答辩怎么安排？

**答（按这个节奏讲）：**

1. **定位（30s）**：校园心理、非临床、辅助倾听；
2. **系统结构（60s）**：画一张三层图（前端 → 推理引擎 → 记忆子系统）+ 一句话讲流水线；
4. **训练与评测（30s）**：PT→SFT→DPO→LoRA；BLEU/ROUGE/F1/over_memory；
5. **产品与边界（30s）**：隐私开关、管理端分诊、已知局限。

### Q5. 项目最难的部分在哪？

**答（最经典的保研反问）：** 难的是**职责边界与"线上/线下"一致**，三个层面：

1. **分类只影响"强度"，不偷改"该不该查"**：`is_consult` 只调 LoRA scale（咨询 0.7 / 闲聊 0.3）和写 `turn_metrics.route`，**不门控记忆**。这要求记忆读写路径在闲聊上也能稳定工作。

2. **职责分离靠「单 chat LoRA × 多 scale + 记忆零写时 LLM」**：
   - 对话用一份 DPO LoRA，靠 scale 区分咨询/闲聊；摘要关 LoRA；
   - 记忆写路径**不调用任何生成**（分块+向量由代码完成）；读路径主体代码编排，仅查询规划/可选重排用 LLM；
   - Qwen chat template 对多条 `role=system` 不稳定，记忆块以 system 注入时排在摘要之后、未摘要原文之前，并带"无关可忽略"前缀。
3. **DPO 负样本质量与评测口径**：rejected 用 MiniMax-M2.7 合成，要防「合成质量反超 chosen」、防模型风格泄漏。DPO 后 BLEU 略降（sft 29.56 → dpo 27.91），但 ROUGE-1/2 略升——这说明 **DPO 优化的是偏好，不是 n-gram 复现**。要看 ROUGE、人工、安全三类指标综合判，不能只看 BLEU。

### Q6. `is_consult` 这个分类器现在到底在控制什么？

**答（精准答，避免被追问细节）：**

| 影响 | 不影响 |
|------|--------|
| chat LoRA scale（咨询 0.7 / 闲聊 0.3） | 是否检索长期记忆 |
| `turn_metrics.route` 写入（`consult`/`chat`） | 是否运行记忆写路径（ingest_message） |
| 管理端分诊筛选用 | 用户是否开记忆 |

记忆路径只看 `memory_enabled`，与 `is_consult` 完全解耦——这是"安全/路由与生成解耦"设计的具体落地。

## 二、架构与系统设计

### Q7. 系统整体架构是怎样的？画一张图。

**答（老师要图，用 ASCII 也能讲清）：**

```
用户消息
   │
   ▼
┌──────────────────────────────────────────────┐
│  FastAPI Web 层                              │
│  - 鉴权 / Cookie                              │
│  - 异步提交到线程池                            │
└──────────────────────────────────────────────┘
   │
   ▼
┌──────────────────────────────────────────────┐
│  意图分流：MacBERT-base（毫秒级）              │
│  is_consult ∈ {0, 1}                         │
└──────────────────────────────────────────────┘
   │
   ▼
┌──────────────────────────────────────────────┐
│  记忆子系统（仅当用户开启记忆时）              │
│  原文库 + 查询时 AER：                        │
│  hybrid 召回（BGE-M3 + 字级 BM25, RRF）       │
│  → 扩窗成"一段经历" → 跨会话时序链            │
│  → 覆盖度贪心选择 ≤6 → <memory>    │
│  → system 前缀注入（只含 user 原文）           │
└──────────────────────────────────────────────┘
   │
   ▼
┌──────────────────────────────────────────────┐
│  生成引擎：Qwen + chat LoRA（多 scale）         │
│  - 同一份 Qwen3-14B 4-bit 基座                 │
│  - chat LoRA: 咨询 scale=0.7 / 闲聊 0.3       │
│  - 流式返回                                    │
└──────────────────────────────────────────────┘
   │
   ▼
后端线程池（post-turn，非阻塞）：
  ├─ ingest_message（分块 + BGE-M3 向量，无 LLM）
  ├─ Profile（提议→确认→落库）
  └─ 摘要生成（裸基座）条件触发
```

**关键设计**：
- **应用并行、GPU 串行**：HTTP 异步处理用户请求；引擎内 RLock 串行所有 GPU 调用；post-turn 在线程池后台跑，不阻塞首 token。
- **记忆读/写路径无逐轮 LLM**：记忆与生成解耦——检索出问题，对话仍可继续（注入空块兜底）。

### Q8. 单轮对话在运行时是怎么走的？

**答（按代码顺序，但只说 5 步）：**

1. 鉴权 + 拿到 `sid` + 把用户消息写库；
2. **MacBERT 分类**得 `is_consult`；
3. 构造模型消息：摘要 system +（若开记忆）`<memory>` system 前缀块（只含 user 原文、带日期与来源）+ 自上次摘要以来的全部原文；
4. 流式生成（chat LoRA，scale 按 is_consult 选）；
5. 写库 + 写 turn_metrics + 提交 post-turn。

**保研加分点**：强调这是 **"单次上下文组装，不重复检索"**。

### Q9. 单卡怎么同时做咨询语气、闲聊语气和会话摘要？

**答：**

- **执行上**：引擎内 `threading.RLock` 串行所有 GPU 调用；
- **强度上**：只加载一份 `chat` LoRA，`set_scale` 切换——咨询 ≈0.7、闲聊 ≈0.3；摘要关 LoRA 走基座；
- **应用层**：post-turn 线程池异步跑 ingest / 摘要，不阻塞首 token。

长期记忆已是 AER 原文库，写路径不需要第二份任务 LoRA。

### Q10. 流式传输时客户端断了，回复还能写库吗？

**答：** 能，而且**故意这样设计**：

- 流式接口 `/api/chat_stream` 用 `TextIteratorStreamer` 把 chunk 灌进独立 worker 线程，**非 daemon**，客户端 Abort 只停读 `StreamingResponse`；
- 后台线程跑完整个 `generate_stream`，最后用 `_finalize_chat_turn` 把全文写 assistant 消息表；
- 客户端断开 → 切会话 → 后台继续写 → 前端轮询 `/api/history` 补全。

**取舍**：算力换体验与正确性——单卡单进程下能接受。

## 三、长期记忆子系统

> 这是保研最常被深挖的部分：研究问题定义、设计思路、为什么这样做、怎么证明。

### Q11. 为什么需要长期记忆？直接塞上下文不行吗？

**答：** 不行，原因四层：

1. **跨会话**：用户反复讲保研焦虑、异地恋，模型每轮从零开始；
2. **经历证据**：AER 存的是原文块，查询时扩窗重建经历，而不是把人生压成几条标签；
3. **可控注入**：覆盖度选择 + token 预算，避免把几十段旧经历全塞进 prompt；
4. **隐私可开关**：用户能关记忆 / 一键遗忘。

> **面试金句**：「长上下文解决"一轮能塞多少"，不解决"跨会话记住用户且不乱贴标签"。记忆系统的价值是**跨会话 + 原文证据 + 可控 + 隐私**。」

### Q12. 记忆存什么？和"长上下文"有什么区别？

**答（讲清楚"原文库"哲学）：**

现行记忆（aer）**只存原文**：每条消息按确定性规则分块、BGE-M3 向量化后原样入库（`memory_episode_chunks`），不做抽取、不归纳、不概括。另有一条 **Profile 旁路**：用户确认过的稳定画像（origin = explicit / confirmed）单独存表。

**为什么只存原文**：心理场景里，任何"写时理解"都是风险——把"一次考砸"改写成"他是个失败者"就是写时污染。原文库把"理解"完全后置到读路径：系统只保证存得全、查得准，不保证"先归纳好"。

**与长上下文（128K）的区别**：长上下文解决"一轮能塞多少"，不解决"跨会话记住用户"。记忆系统的价值是**跨会话 + 可控注入 + 隐私开关**（用户可关记忆/一键遗忘）。

### Q13. 记忆的读路径（检索 + 重建）怎么设计的？

**答（按"查询时自适应经历重建 AER"讲，体现"不是简单 top-k"）：**

```
QueryRouter：比较句拆子查询（direct/split），纯情绪短句强制 direct
   ↓
hybrid 召回：BGE-M3 cosine（assistant 降权 ×0.55）+ 字级 unigram/bigram BM25
   ↓ RRF 融合 → seed top-8
AER 扩窗：沿会话向两边做连续性游走
   ↓ 连续性 = 0.40×核心相似 + 0.22×已选区相似 + 0.18×实体Jaccard
   ↓          + 0.10×位置邻接 + 0.10×查询词覆盖；≥0.28 纳入，连续失败2次停
   ↓ 产出"一段完整经历"（跨度≤12、bundle≤10）
重叠合并 → 特征重排 → 跨会话时序证据链
   ↓ 链打分 = 0.30×实体 + 0.30×语义 + 0.20×时间序 + 0.15×查询覆盖 + 同会话
覆盖度贪心选择（top-6）
   ↓ 得分 = 相关(≤2.2) + 1.6×新增覆盖 + 1.0×查询词增益 + 时间桶首现 − 1.8×重叠
<memory> system 前缀注入（只含 user 原文 + 日期/来源）
```

**设计取舍**：
- **写时不理解、读时才理解**：写路径零 LLM、零抽取，读路径每轮按需重建上下文——与 Mem0（写时抽取 fact）的路线正相反；
- **混合召回**：字级 BM25 对中文人名/专名/数字敏感，与 dense 互补，不再需要专门精排模型；
- **AER 而非固定窗口**：固定 ±N 窗口要么切碎上下文、要么塞无关寒暄；连续性游走按"是不是同一件事"决定扩多少；
- **覆盖度选择而非纯 top-k**：`selector` 保证候选间不重复（去冗余）+ 时间桶多样性（新旧兼顾）；
- **跨会话链**：把分散在多周的经历串成一条链，回答"整合多个会话"的问题（cross_session_integration 93% vs Mem0 60%）。

### Q14. 记忆的写路径怎么设计？

**答：写路径不做 LLM 决策，全部是确定性的：**

1. **分块**：`chunker.py` 按句界切分、按 150–350 字合并，≤500 字整段；
2. **向量化**：每块 BGE-M3 编码，失败进 `memory_embed_retry` 重试队列（attempts<5）自动补跑；
3. **幂等入库**：按 `(message_id, chunk_index)` upsert，重发/回填不产生重复；
4. **Profile 旁路**（唯一"写理解"的地方，但需用户确认）：
   - 用户说"记住/别忘了…" → 直接存（explicit）；
   - 助理说"要不要我记住…" → 存 pending；用户回"可以/对" → 落库（confirmed）；
   - 说"忘掉/删掉…" → 按关键词软删；
   - **政策硬拦截**：诊断词（抑郁症/双相/人格障碍…）、人格标签、瞬时情绪（"今天有点难过"）→ 一律拒绝。

**为什么不写 LLM 抽取**：抽取即改写——写错的标签会长期污染对话。零抽取从根上消除"该记不该记"的写时判断；成本转到读路径（hybrid + 扩窗 + 覆盖选择；可选规划/重排）。

### Q15. 怎么"证明"记忆系统有用？

**答（保研老师爱听"如何评测"）：**

**长程 QA 对比（现行正式评测，`evaluate/memory/`）**：

| 方法 | QA 准确率 | Staleness 率 | 内容 F1 |
|------|-----------|--------------|---------|
| **AER（aer）** | **91%–93%** | **7%–14%** | **0.79–0.89** |
| Mem0（同协议） | 64% | 43% | 0.48 |

- **协议**：30 条真实长程咨询弧（`evaluate/memory/data/`，6 类 × 5）；每个方法按同一对话流逐轮写入；延迟测试点用**固定 reader**（MiniMax-M3）只接收"该方法的记忆检索块 + 测试题"作答——同一 reader 跨方法，测的是记忆库而非答题能力；
- **逐类**：context_recall 0.93 vs 0.47、cross_session_integration 0.93 vs 0.60、current_state 1.0 vs 0.60、preference_recall 0.93 vs 0.73、detail_recall 0.93 vs 0.87、temporal_sequence 0.73 vs 0.60；
- **消融**：覆盖度选择 vs 固定 top-k → QA 91–93% vs 84.4%，说明"去冗余 + 多样性"的贪心选择真实有效。

**关键工程结果**：内容 F1 0.89 vs 0.48（对 gold 应记/应忘），即"该记的记住了、不该记的没记"——这是 SoulHarbor 在"记忆内容质量"上最硬的结果。记忆只存原文，从结构上不会把一次性情绪固化成"确信画像"。

### Q16. 记忆系统最有意思的工程坑是什么？

**答：记忆块以 system 注入时被 Qwen chat template 合并/忽略的问题。**

- **坑的来源**：Qwen chat template 对多条 `role=system` 不稳定——`_build_history` 把所有 system 拼成一条，前序 system 主导注意力，后放的记忆块容易被忽略；
- **坑的现象**：检索日志里有记忆，模型却表现得像没看见；
- **坑的解法**：`service.build_chat_context` 把 `<memory>` 作为一条 system 注入（放在摘要 system 之后、未摘要原文之前），并加一份**行为级前缀**——"以下内容来自用户过往对话的检索结果，只是历史背景，不是用户本轮新说的话；能帮助回答就自然采用；和当前问题无关就忽略；和用户此刻说法冲突时以当前说法为准；不要补充检索结果里没有的事实"（`service.py:_MEMORY_SYSTEM_PREFIX`），靠内容级指令而非位置硬扛；
- **坑的证据**：离线对比实验中，注入块形式/位置是单变量改进最明显的一处。

> **面试金句**：「**懂模型才知道 injection 怎么放**——这不是工程经验，是从 chat template 行为里反推出来的。」

## 四、训练与对齐

> 这部分老师最关心"为什么这样训 / 数据从哪来 / 怎么证明训得好"。

### Q17. 训练主线是什么？分几步？

**答（PT → SFT → 自我认知 → DPO 的流水线）：**

| 阶段 | 数据 | 目的 |
|------|------|------|
| **PT**（继续预训练） | EmoLLM `pt.json` → 2.4 万条 `{"text"}` 纯文本 | 让基座在心理中文分布上"更熟" |
| **主指令 SFT** | 9 成 SoulChatCorpus + 1 成 EmoLLM data_pro → 2 万条 ShareGPT | 学"按指令回答"、格式、风格 |
| **自我认知 SFT** | EmoLLM 自我认知种子 → 274 条 ShareGPT | 强化"我是 SoulHarbor / 大工"的人设 |
| **DPO** | SoulChat 互斥切片 + MiniMax-M2.7 生成的 rejected → 3000 对 ShareGPT+ranking | 把"敷衍/欠共情"压下去 |
| **意图分类** | SoulChat 正 + LCCC 负 → 3000 条 instruction JSON | 训 MacBERT-base 二分类 |

**框架**：LLaMA-Factory QLoRA 4-bit；全链路 LoRA r=8 / α=16（`train/configs/*.yaml` 与线上 `adapter_config.json` 一致）。

**数据出处**（**保研老师必问**）：
- SoulChatCorpus：Chen et al., **Findings of EMNLP 2023**，GitHub `scutcyr/SoulChat`；
- LCCC：Wang et al., **NLPCC 2020**；
- EmoLLM：GitHub `SmartFlowAI/EmoLLM`（开源项目，不是顶会论文）。

### Q18. 为什么要先 PT 再 SFT？

**答：** 通用基座 Qwen3-14B 在百科/代码/新闻上分布偏多，对"心理咨询口语化情绪表达"陌生。PT 不是"加知识"——参数没真的"记事实"——而是**重塑 token 分布**，让模型在心理语料上的 perplexity 下降。做完 PT 后再做 SFT，更容易收敛到正确格式与风格，避免基座"陌生感"。

### Q19. DPO 是怎么做的？数据怎么来？

**答：**

1. **Prompt 池**：从 SoulChat 等多轮语料切"上文 + 当前用户句"，并与已进主 SFT 的样本**互斥**（防止数据泄漏导致虚高）；
2. **Chosen**：保留语料中较好的助手回复（或裁判优选）；
3. **Rejected**：用 **MiniMax-M2.7** 按"仍相关但更敷衍/欠共情"指令合成——偏空泛、欠共情、敷衍、说教等；
4. **质检**：`check_rejected_quality.py` 过滤不可用负样本（避免"合成质量反超 chosen"）；
5. **写出 3000 对 ShareGPT+ranking**，topic 较均衡；
6. **训练**：从自我认知 SFT adapter 继续，4-bit LoRA（r=8 / α=16），`pref_beta=0.1`，lr 5e-6，1 epoch。

**DPO 的核心思路**（**老师很爱追问**）：把 RLHF 的最优策略写成闭式，发现 reward 可以直接用策略与 reference 的 log 比表达——**不必显式训 reward model，也不跑 PPO 采样环**，直接对偏好数据做监督训练。

### Q20. DPO 后 BLEU 反而降了，怎么解释？

**答：**

- 实测：base BLEU-1 ≈ 13.23 → sft ≈ 29.56 → dpo ≈ **27.91**（**略降**），但 ROUGE-1/2 略升（dpo ROUGE-1 ≈ 31.49 > sft 30.65）；
- **结论**：DPO 优化的是**偏好**（更共情、少敷衍），不是 n-gram 复现。表达更自然/多样时 BLEU 可能降，但 ROUGE（覆盖）可能升；
- **怎么判断 DPO 是否成功**：分模型分维度评——chat 看人工/LLM-as-judge 偏好胜率；task 看字段级 P/R/F1；**不能用 chat 的 BLEU 代替 task 的结构化指标**。

### Q21. LoRA / QLoRA 怎么选？参数为什么这么设？

**答（保研稳妥）：**

- **选 QLoRA + 单 chat LoRA**：单卡塞 14B；用 scale 区分场景，而不是多 adapter；
- **全链路统一 r=8 / α=16**（PT / 主 SFT / 自我认知 / DPO 一致，`train/configs/*.yaml` 与线上 `adapter_config.json` 对齐），`lora_target=all`（q/k/v/o/gate/up/down 全部覆盖）；
- **超参阶梯**：lr PT 5e-5 → 主 SFT 2e-5 → 自我认知 3e-5（小数据快速学人设、5 epoch + best checkpoint）→ DPO **5e-6**（只做偏好微调）；
- 自我认知与 DPO 都是**低 lr 或保守配置**，防止把主 SFT 已经学好的话术冲掉。

### Q22. 为什么最终放弃写时抽取？

早期写时抽取即便把工具调用指标做上去，仍无法从结构上消灭误记——心理场景里误记的代价高于漏召回。终态 AER：**写路径零 LLM 存原文，读路径再重建经历证据**；consent Profile 才允许极少量结构化偏好。详见 `00` §5 与 `05`。

### Q23. 怎么证明训练是有效的？

**答（保研口径）：**

- **主对话**：SoulChat seen/unseen 各 1000 条 → base 13.23 → sft 29.56 → dpo 27.91（BLEU-1）；相对 base 涨了 +14 ~ +16，ROUGE-L 涨 +9 ~ +10；
- **消融**：seen / unseen 分开报告，说明不是死记训练集；

## A0. 零基础前置：符号约定

> 这一节把所有公式都用到的符号统一约定。**答辩被追问公式时，能不能在 30 秒内把字母含义说出来**——这决定老师给不给你过。

### A0.1 线性层是什么
一个线性层就是 $y = Wx + b$，$W \in \mathbb{R}^{k\times d}$ 是要学的权重。

### A0.2 微调 vs 全量
**微调** = 在预训练权重基础上继续训；**全量微调** = 14B 参数全更新——显存吃不消；**PEFT** = 只训一小部分参数。

### A0.3 低秩是什么
矩阵的**秩** = 线性无关的行/列最大数目；**低秩** = 秩远小于矩阵维度。

### A0.4 $BA$ 的形状接得上 $W_0$
$W_0 \in \mathbb{R}^{k\times d}$，LoRA 取 $A \in \mathbb{R}^{r\times d}$，$B \in \mathbb{R}^{k\times r}$（$r \ll \min(d,k)$），$B(k\times r) \cdot A(r\times d) = (k\times d)$，可与 $W_0$ 相加。

### A0.5 自回归 / CLM 损失
$$\mathcal{L}_{\mathrm{CLM}} = -\frac{1}{T}\sum_t \log p_\theta(w_t \mid w_{<t})$$

### A0.6 KL 散度
$$\mathrm{KL}(P\|Q) = \sum_x P(x)\log\frac{P(x)}{Q(x)}$$
不对称，衡量"两个分布差多远"。

### A0.7 五个易混的"α / β / r / scale / lr"

| 名字 | 出处 | 含义 |
|------|------|------|
| **LoRA α** | LoRA 论文 | 训练时 $\Delta W = \frac{\alpha}{r}BA$ 的缩放系数 |
| **DPO β** | RLHF / DPO | KL 约束强度，**和 LoRA α 无关** |
| **LoRA r** | LoRA 论文 | 低秩瓶颈维度 |
| **推理 scale** | 运行时 `set_scale` | 推理时**额外**乘的 LoRA 强度 |
| **lr** | 优化器 | 参数更新步长 |

> **面试金句**：「**LoRA α/r 决定训练时 $\Delta W$ 多大；DPO β 决定离 reference 多近；推理 scale 决定运行时 LoRA 影响多强**——三个独立旋钮。」

### A0.8 本项目的"魔法数字"

| 数字 | 含义 |
|------|------|
| 14.8 × 10⁹ | Qwen3-14B 参数量 |
| 1024 | BGE-M3 dense embedding 维数；FastAPI `max_new_tokens` |
| 1600 / 6 / 10 | 记忆注入 token 预算 / 注入 bundle 上限 / bundle 内消息上限 |

| 0.55 | assistant 角色块的召回降权系数 |
| 0.7 / 0.3 / 1.0 / 0.05 / 0.1 / 0.6 / 0.3 | 各 scale / DPO β / chat temp / summary temp |

## A. LoRA（Low-Rank Adaptation）

### A1. 一句话定义
LoRA（Hu et al., 2021）= **冻结**预训练权重 $W_0$，**只训练**一对低秩矩阵 $A$、$B$：
$$W = W_0 + \frac{\alpha}{r}BA$$

| 字母 | 含义 | 形状 | 可训练？ |
|------|------|------|---------|
| $W_0$ | 基座权重 | $\mathbb{R}^{k\times d}$ | 否 |
| $A$ | 下投影 | $\mathbb{R}^{r\times d}$ | 是 |
| $B$ | 上投影 | $\mathbb{R}^{k\times r}$ | 是 |
| $r$ | 秩（瓶颈维度） | 整数 | 调参 |
| $\alpha$ | 缩放系数 | 整数 | 调参 |

### A2. 为什么 $r=8$ 就能搞定？内在维度
Aghajanyan 等人（2020，*Intrinsic Dimensionality of Fine-Tuning*）发现：大模型在很多任务上只要 $d' =$ 几百~几千的随机子空间就能达到全量微调性能。任务的**内在维度**远小于参数空间维度。LoRA 由此假设"$\Delta W$ 落在低维子空间"，用 $BA$ 近似即可。$r=8$ 是从经验下限推导的"够用"选择。

### A3. 参数量节省到底多少
单层 $d=k=3584$ 时：

- 全量 $W_0$ 参数：$3584^2 \approx 1.28 \times 10^7$；
- LoRA $r=8$：$A$ 参数量 $r\cdot d = 28672$，$B$ 参数量 $k\cdot r = 28672$，合计 $57344$；
- 比例：$57344 / 1.28 \times 10^7 \approx 0.44\%$。

14B 模型 ≈ 280 个线性层 $\times$ 5.7万 ≈ 16M，**省 99.9%**。

### A4. 初始化与"不破坏基座"
PEFT/LLaMA-Factory 默认 $A$ 高斯随机、$B$ **置零**。代入：

$$\Delta W = \frac{\alpha}{r} \cdot B \cdot A = \frac{\alpha}{r} \cdot \mathbf{0} \cdot A = \mathbf{0}$$

所以训练第一步 $W = W_0$，模型行为**完全等于基座**——平滑过渡到 SFT 模型。

### A5. 训练时梯度推导（链式法则）
$\Delta W = \frac{\alpha}{r}BA$，对 $B$：

$$\frac{\partial \mathcal{L}}{\partial B} = \frac{\alpha}{r} \cdot \frac{\partial \mathcal{L}}{\partial(\Delta W)} \cdot A^\top$$

对 $A$：

$$\frac{\partial \mathcal{L}}{\partial A} = \frac{\alpha}{r} \cdot B^\top \cdot \frac{\partial \mathcal{L}}{\partial(\Delta W)}$$

$\frac{\partial \mathcal{L}}{\partial(\Delta W)}$ 形状 $(k\times d)$ 是全量微调时的同一个梯度，LoRA 把它"切成两半"按 $A,B$ 位置传。**梯度计算量从 $O(kd)$ 降到 $O(r(k+d))$**。

### A6. $\alpha$ 与 $r$ 的真正含义
$\alpha/r$ = 训练时 $\Delta W$ 的有效初始强度。工程经验：**让 $\alpha/r$ 在不同 $r$ 之间保持稳定**（本项目都让 $\alpha = 2r$），换 rank 时梯度量级不变，便于复用学习率。

| Adapter | r | α | α/r | dropout |
|---------|---|-------|-------|---------|
| chat（DPO） | 8 | 16 | 2 | 0 |


### A7. Rank $r$ 的工程选择
- $r$ 太小（4）：欠拟合，简单偏好微调勉强能用；
- $r=8 \sim 16$：典型 PEFT 区间；
- $r=32 \sim 64$：复杂任务，主 SFT 大数据；
- $r\geq 128$：接近全量，丧失 PEFT 优势。

### A8. 本项目怎么用 PEFT 调语气强度
PEFT 的 `LoraLayer` 挂在目标线性层外。本项目只挂一份 `chat` adapter，用 `set_scale` 调推理强度：

```
model (Qwen3-14B base, frozen)
└── LoraLayer
    └── adapter "chat": (A, B)
        scale ∈ {0.7 咨询, 0.3 闲聊}；摘要 disable_adapter
```

`set_adapter("chat")` 激活；`set_scale("chat", s)` 改乘数。

## B. QLoRA 与 4-bit 量化

### B1. 一句话定义
QLoRA（Dettmers et al., 2023）= **4-bit 量化的基座 + LoRA**。三件套：
1. **NF4 数据类型**——专门为"权重近似正态"设计的 4-bit 格式；
2. **Double Quantization**——把 scale 也再量化；
3. **Paged Optimizer**——optimizer 状态 page 到 CPU。

### B2. 量化基础
线性量化：把 $[x_\text{min}, x_\text{max}]$ 切成 $2^n$ 个 bin，scale $s = (x_\text{max}-x_\text{min})/(2^n-1)$。

### B3. NF4：等概率分位
预训练权重近似正态分布 $\mathcal{N}(0, \sigma^2)$。INT4 等距切分在 $[-0.125, 0.125]$ 上浪费分辨率（密度最高）。NF4 把标准正态在 $[-1,1]$ 上切成 8 等概率正负分位 + 0，**每个 bin 概率质量近似相等**，量化误差更小。

### B4. 14B 显存账

| 方案 | 权重 | 梯度 | Adam 状态 | 激活 | 总 |
|------|------|------|-----------|------|-----|
| 全量（fp16） | 28 GB | 28 GB | 112 GB | 几 GB | **168+ GB** |
| QLoRA | 7 GB（NF4） | 0 | 仅 LoRA 部分 | 几 GB | **< 36 GB** |


### B5. 数据流（再强调一遍）
**4-bit 只用于存储冻结基座**；计算（矩阵乘、前向/反向）始终在 fp16；优化器更新只发生在 LoRA 参数。

## C. SFT（Supervised Fine-Tuning）

### C1. 一句话定义
在「输入 → 标准输出」对上做**下一 token 预测**，损失：

$$\mathcal{L}_{\mathrm{SFT}}(\theta) = -\frac{1}{T}\sum_{t=1}^{T}\log p_\theta(y_t \mid x, y_{<t})$$

### C2. Teacher Forcing 与 Exposure Bias
训练时**强制喂真实前缀**（teacher forcing），每个位置独立算 loss、并行；推理时每步用自己采样结果，**训练/推理分布不一致** = exposure bias。

### C3. Label Masking
非 assistant 段 label 设为 `-100`（`CrossEntropyLoss.ignore_index`），让模型只学"怎么答"。LLaMA-Factory `train_on_prompt=false`。

### C4. Label Shift
$$\text{logits}[:,:-1,:] \quad \text{对} \quad \text{labels}[:,1,:]$$
框架自动 shift。

### C5. SFT vs PT vs DPO
| 阶段 | 数据 | 目标 |
|------|------|------|
| PT | 连续文本 | 适配领域 token 分布 |
| SFT | instruction / 对话 | 学"怎么答" |
| DPO | chosen vs rejected | 学"哪种更好" |

---

## D. DPO（Direct Preference Optimization）

### D1. 一句话定义
DPO（Rafailov et al., 2023）= 把 RLHF 最优策略写成闭式后，**reward 可以直接用策略 $\pi_\theta$ 与 reference $\pi_\text{ref}$ 的 log 比表达**——不必显式训 RM，不跑 PPO：

$$\mathcal{L}_{\mathrm{DPO}}(\theta) = -\log\sigma\!\Big(\beta\big[\log\frac{\pi_\theta(y_w|x)}{\pi_\text{ref}(y_w|x)} - \log\frac{\pi_\theta(y_l|x)}{\pi_\text{ref}(y_l|x)}\big]\Big)$$

### D2. 推导全景

```
RLHF 目标（含 KL 正则）
        │
        ▼（拉格朗日求最优策略）
闭式最优策略 π*(y|x) ∝ π_ref · exp(r/β)
        │
        ▼（取对数反解 reward）
r(x,y) = β·log[π*/π_ref] + β·log Z(x)    ← log Z(x) 对所有 y 一样
        │
        ▼（代入 Bradley-Terry 偏好模型，log Z(x) 在差分时抵消）
DPO 闭式 loss（只依赖两个 log 比）
```

### D3. Bradley-Terry 直觉
世界杯 4 支球队，胜率 = $\sigma(r_i - r_j)$；已知胜负反推实力 $r_i$。DPO 跳过反推 $r$ 的步骤，直接比较差值。

### D4. $\beta$ 的作用（很多人答错）
$\beta$ 在 KL 正则项里：$\beta$ 大 → 强约束 → **保守**；$\beta$ 小 → 约束弱 → 偏好学得狠但可能漂移。**反直觉**：教材常说"β 大偏好强"，**错的**。

实现中 $\beta$ 还缩放 margin 影响 sigmoid 饱和区。

### D5. 梯度方向
DPO 优化的是 `margin = log(π_θ(y_w)/π_ref(y_w)) − log(π_θ(y_l)/π_ref(y_l))`，目标是最大化 margin。chosen/rejected 绝对概率可以同时下降，只要 margin 上升就有效——**绝对概率不重要，相对 ref 的 margin 才重要**。

### D6. Reward Hacking
策略找到奖励漏洞但未满足真实意图：超长骗 ROUGE、套话骗流畅性、一味认同骗偏好。心理场景要警惕"一味认同用户"——强化错误认知。

缓解：对抗性偏好数据、RM 集成、KL 约束、长度/重复惩罚、人机混合评测。

## E. 继续预训练 PT

### E1. 一句话定义
PT = 在通用基座上**继续做 CLM 训练**，但用领域文本（这里是心理/校园中文），让 token 分布贴近该领域。

### E2. CLM 损失
与 SFT 同一公式，但 PT 是**全 token 算 loss**（无角色），目的是塑分布而非学任务。

### E3. 学习率序列
| 阶段 | lr | 理由 |
|------|----|----|
| PT | 5e-5 | 显著搬动领域分布 |
| 主 SFT | 2e-5 | 学指令格式 |
| 自我认知 | 3e-5 | 274 条小数据，accum=1 + 5 epoch + best checkpoint |
| DPO | 5e-6 | 偏好微调，更保守 |

**规律**：模型越大 lr 越保守；LoRA 可用比全参更大的 lr。对话主线的核心是"PT 拉分布 → SFT 学格式 → DPO 做偏好微调"，越往后 lr 越低，防止把前序阶段学好的能力冲掉。

## F. MacBERT 微调

### F1. 一句话定义
MacBERT（Cui et al., Findings of EMNLP 2020）= 面向中文的 BERT 变体。本项目在 `chinese-macbert-base` 上加分类头做咨询/闲聊二分类（base 而非 large：分流任务简单，base 验证准确率已达 99.7%，省下的显存留给 14B 主模型与 BGE-M3）。

### F2. MLM 同义词替换（解决预训练-微调 mismatch）
- 80%：用同义词替换选中 token；
- 10%：替换成随机词；
- 10%：保持原词。

让模型被迫学"判断是否被替换"+"识别同义关系"，且微调时正常词分布贴近预训练。

### F3. 其它改进
WWM（全词 mask）、NSP → SOP（句子顺序预测）、哈工大讯飞中文大规模预训练。

### F4. 为何不用大模型自己分类
小编码器**快、稳、可离线评测**；与生成解耦避免"既当裁判又当运动员"。**选 base 的理由**：分类任务是二分类、判别式，不需要 large 的容量；线上 `IntentClassifier._pick_checkpoint_dir` 优先取 `trainer_state.json` 的 `best_global_step`（当前 `checkpoint-188`）。

### F5. 二分类 head 微调
$$\mathcal{L} = -\frac{1}{N}\sum_i \big[y_i\log\hat{p}_i + (1-y_i)\log(1-\hat{p}_i)\big]$$
$\hat{p}_i = \sigma(W_\text{head} \cdot h_\text{[CLS]} + b)$。

## G. 记忆检索：AER 自适应经历重建（现行）

### G1. Hybrid 召回（BGE-M3 cosine + 字级 BM25 → RRF）
语义：$\text{sem} = \cos(q, c)$，assistant 角色块 ×0.55。词法：中文按单字 + 相邻二元组做 BM25。
$$S_{\text{rrf}}(d) = \sum_{r \in \text{rank}_s(d), \text{rank}_l(d)} \frac{1}{60 + r}$$
pivot top-8 进入扩窗。

### G2. AER 连续性游走（核心）
对 seed 沿会话向两边逐条判断是否纳入"同一段经历"：
$$\text{cont} = 0.40\,c(q_{\text{sim}})\ +\ 0.22\,c(\text{span})\ +\ 0.18\,J(\text{ent})\ +\ 0.10\,\text{pos}\ +\ 0.10\,J(q\text{-tokens})$$
其中 $c$ 为余弦、$J$ 为实体/词 Jaccard；`cont ≥ 0.28` 纳入，连续失败 2 次停止；跨度 ≤12、bundle ≤10。
### G3. 跨会话时序证据链

两段经历的链得分：
$$S_{\text{link}} = 0.30\,J(\text{ent})\ +\ 0.30\,\cos\ +\ 0.20\,\text{time}\ +\ 0.15\,\text{query gain}$$
时间分 `time` 不是硬编码奖励，而是按间隔衰减：后者晚于前者时 `time = max(0.05, 0.35·exp(−days/90))`（≈0.35@当天 → ≈0.12@90 天 → ≈0.05 下限），顺序倒置但 3 天内给 0.15，更早的倒序给 0。贪心以"最相关"为种子向前生长，链条按最早时间排序、跨会话才打 `E1/E2…` 标签。

### G4. 覆盖度贪心选择（去冗余 + 时间多样性）
$$\text{score} = \min(\text{rel}, 2.2) + 1.6\,\tfrac{|C_{\text{new}}|}{|C|} + 1.0\,\tfrac{|(C_{\text{new}}\cap Q)|}{|Q|} + \text{temporal} - 1.8\,J(C_{\text{new}}, C_{\text{covered}})$$
时间桶=7 天，桶内首个候选 +0.9、重复 −0.15。top-6 注入。

### G5. 为什么写路径"零抽取"
- 抽取即改写——把具体事件改写成语义标签是"过度固化"的来源（Mem0 路线）；原文库从根上消除写时污染；
- 读路径按需重建 = 把"该记什么"的判断后置到每一次查询，交给上下文选择而非一次性归纳；
- 唯一写理解 = Profile，但需要用户确认（explicit / confirmed），政策层再拦诊断词/人格标签/瞬时情绪。

# 第三部分：心理 AI 伦理与安全（领域题，老师很关心）

> 这是 SoulHarbor 的领域属性决定的——任何心理 AI 都会被问"你怎么对待脆弱人群"。
> 小节编号用 `Q.E*` 前缀，与第二部分的 A–H 章节互不冲突。

### Q.E1. AI 做心理咨询合法吗？怎么划清边界？

**答：** 不同司法辖区的处理：

- **中国**：卫健委 2023 年《互联网诊疗管理办法》要求 AI 不能独立提供诊疗——SoulHarbor 明确"辅助倾听与情绪支持"，**不替代诊断**；
- **美国 FDA**：SaMD（Software as Medical Device）分级，多数心理 AI 属 Class I/II；
- **欧盟 EU AI Act 2024**：心理健康 AI 被列为**高风险 AI 系统**，需透明、可审计。

**SoulHarbor 的合规设计**：
- 首页 disclaimer：不替代专业咨询；
- 危机场景建议拨打 24h 心理援助热线；
- 不存储用户原始对话超过必要时间；
- 管理员分诊机制（高风险会话人工介入）；
- `forget-all` 一键遗忘符合 GDPR。

### Q.E2. 用户隐私怎么保护？哪些数据不能存？

**答：**

| 类别 | 例子 | SoulHarbor 处理 |
|------|------|----------------|
| 身份信息 | 身份证、手机号 | 不采集 |
| 财务信息 | 银行卡、密码 | prompt 过滤 + 不写库 |
| 健康信息 | 病史、用药 | 默认采集但前端不展示 |
| 位置信息 | IP、GPS | 不采集 |
| 生物特征 | 声纹、人脸 | 不采集 |

**合规依据**：
- 中国《个人信息保护法》（PIPL）：敏感个人信息需单独同意；
- GDPR：right to be forgotten（删除权）；
- HIPAA（美国医疗）：心理健康对话受保护。

### Q.E3. 危机干预怎么办？模型说错话可能出大事

**答：** 这是**最高优先级**的安全问题。

**当前 SoulHarbor 的处理**：
- MacBERT 分类器检测"咨询"信号 → 路由到 scale 0.7 chat LoRA → 语气更稳重；
- 系统 prompt："温和"、"不替代专业"、"建议咨询专业人士"；
- 危机场景不报警（不自动联系监护人）。

**生产级应做**（明确说是 gap）：
- 危机关键词检测（"自杀"、"想死"、"轻生"）→ 立即提示拨打 24h 热线；
- 高风险会话自动加入管理端 triage；
- 人工值班转介协议；
- 模型生成内容审查（不能输出"如何自杀"等有害内容）。

### Q.E4. 用户和 AI 形成情感依赖怎么办？

**答：** AI 心理对话的经典伦理问题。SoulHarbor 通过：

1. **明确身份**：system prompt 显式说明"我是 AI，不是真人咨询师"；
2. **鼓励专业转介**：长期用户推荐真人心理咨询；
3. **不主动情感表达**："我爱你" / "我完全理解你的感受"等暧昧话术 hard rule 避免；
4. **使用时长监控**：单次对话 > 60 分钟 → 提示休息（生产级方案）。

### Q.E5. AI 的回复被用户作为心理治疗证据怎么办？

**答：** 当前 SoulHarbor 已在 disclaimer 中明确：
- 不替代专业诊断；
- 不出具诊断报告；
- 不提供处方。

但**没有技术上的强约束**——理论上用户可以截图作为证据。生产级应加：
- 每条回复末尾加 watermark："本回复由 AI 生成，不能作为诊断依据"；
- 服务条款中明确法律责任；
- 不定期人工抽查高风险回复。

### Q.E6. 模型偏见怎么处理？某些群体被歧视？

**答：** 心理对话 AI 容易被忽略的偏见：
- 性别偏见：对女性 / 男性情绪化反应不对称；
- 文化偏见：东方 vs 西方情绪表达差异；
- 年龄偏见：对青少年 / 老年人用语差异。

**SoulHarbor 当前**（明确说是 gap）：
- DPO 训练时没有显式做偏见评估；
- 系统 prompt 没有群体敏感性提示；
- 数据集 SoulChatCorpus 主要来自大众心理场景，对校园少数群体（留学生、残障学生等）覆盖不足。

**应做**：
- DPO 数据按性别 / 年龄 / 文化均衡采样；
- 离线偏见评测集（counterfactual fairness）；
- prompt 加 bias-avoidance 声明。

### Q.E7. 用户数据二次利用（训练新模型）合规吗？

**答：** 取决于：
- 用户是否明确同意（opt-in vs opt-out）；
- 隐私脱敏是否充分；
- 是否符合当地法规。

**SoulHarbor 当前**：用户对话可能被用于改进 DPO 等离线数据（需合规同意）。生产级应该：
- 显著告知用户（隐私政策）；
- 提供 opt-out（"我的对话不参与训练改进"）；
- 训练时再次脱敏（去除 PII）。

### Q.E8. 项目里怎么保证 AI 输出可控？

**答：** SoulHarbor 用五层控制：

1. **System prompt 顶层约束**：人设、温度风格；
2. **LoRA scale 调节**：咨询 vs 闲聊的语气强度；
3. **生成参数约束**：max_new_tokens=1024 防止过长；
4. **bad_words_ids**：禁用 thinking 块（`["", ""]`）；
5. **输出后处理**：`_strip_think` 正则剥除残留。

### Q.E9. AI 心理对话效果真的比真人好吗？

**答：** **没有证据**。当前研究表明：
- AI 在"倾听"、"共情语言"上可能超过部分新手咨询师；
- 但在"危机识别"、"复杂创伤处理"、"建立长期信任关系"上**显著劣于专业咨询师**；
- AI 的优势是"24/7 可用"、"无评判"、"低成本"——这是**补充**而非替代。

**SoulHarbor 的定位**：校园场景下的**早期筛查 + 情绪宣泄**工具，不是治疗工具。

### Q.E10. 怎么评估心理 AI 的"共情质量"？

**答：** 这是开放问题。当前方法：

1. **人工评估**：5 分量表，3–5 名心理学研究生盲评；
2. **LLM-as-judge**：GPT-4 给回复打分（"共情程度"、"倾听程度"）；
3. **行为指标**：用户回复轮次、停留时间、👍/👎 比例；
4. **对照实验**：与真人咨询师对比（伦理审批困难）。

**SoulHarbor 当前**：用 BLEU/ROUGE（**不直接测共情**）——这是真实 gap。

# 第五部分：评测方法论与对比实验（保研最爱追问）

> 这一部分专门应对"你凭什么说你的方法好"——保研老师最讨厌"我做了但不知道怎么证明"。

### M1. 评测三件套

| 评测类型 | 工具 | 何时用 |
|----------|------|--------|
| **自动指标** | BLEU / ROUGE / 操作 F1 | 大批量离线评；只作**相对比较** |
| **人工评估** | 5 分量表 / A/B 偏好 / 自由点评 | 数量小但更接近真实质量 |
| **LLM-as-judge** | GPT-4 当裁判打分 | 折中方案，但有偏差 |

**心理对话的难题**：参考答案并非唯一标准答案，自动指标只能作相对比较（base → sft → dpo），不能证明"更共情"——这必须靠人工偏好或 LLM-as-judge。

### M2. 主对话评测（SoulChat 自动指标）

- **数据**：SoulChatCorpus seen / unseen 各 1000 条（是否进过训练分布）；
- **模型**：base（裸 Qwen3-14B）/ sft（自我认知 SFT）/ dpo（线上 chat LoRA）；
- **汇总**：**每个模型单独算**（对 seen/unseen 加权平均，3 组结果）；
- **结果**：
  - base：BLEU-1=13.23 / ROUGE-L=15.04；
  - sft：BLEU-1=**29.56** / ROUGE-L=**24.64**；
  - dpo：BLEU-1=27.91 / ROUGE-L=24.44。

**怎么解读**：SFT/DPO 相对 base 大幅提升（+14~+16 BLEU-1，+9~+10 ROUGE-L）；SFT 与 DPO 同量级，DPO 略低 BLEU 但 ROUGE-1/2 略高——DPO 优化偏好不保证单调抬高 n-gram。

### M3. 记忆评测（现行）

固定 reader（MiniMax-M3）只换记忆库：AER QA ≈91% vs Mem0 ≈64%；内容 F1 ≈0.89 vs 0.48。协议见 `06`。

### M4. 跟公开工作对比

| 项目 | 对话基座 | 个性化 | 自动指标 vs SoulHarbor |
|------|---------|--------|---------------------|
| SoulChat（Chen et al., 2023） | LLaMA-7B | 无记忆 | 论文未给 BLEU/ROUGE，本项目无法直接对比 |
| MeChat（中文情绪对话） | 中文 PLM | 无记忆 | 无公开指标 |
| ESConv（情绪支持对话） | BlenderBot | 无记忆 | 任务定位不同 |
| SoulHarbor（Ours） | Qwen3-14B | **原文库 + 查询时 AER 重建** | seen/unseen 各 1000 条；sft BLEU-1 29.56 / ROUGE-L 24.64；记忆长程 QA（同协议 vs Mem0）91% vs 64% |

**怎么讲**：自动指标不是同一测试集，不能直接比数字；但**方法论**上（原文库防写时固化 + 查询时 AER 重建 + consent 画像）是 SoulHarbor 的差异化贡献。

### M5. 评测的已知 gap（主动说）

- **没有检索金标集**：Recall@K 无法自动化评测；
- **没有 LLM-as-judge 对话评测**：当前只有 BLEU/ROUGE，无法直接测共情；
- **没有偏见评测**：性别 / 年龄 / 文化偏见未做；
- **没有 A/B 框架**：线上所有用户共享同一份配置；
- **没有用户感知评测**：离线指标 vs 用户主观感受可能不一致。

**主动说 gap 是加分项**——老师喜欢听到"我知道还差什么"。

# 第七部分：保研老师爱问的"发散性"问题（第二部分延伸高频追问）

> 这一部分汇总保研老师大概率会追问的二级问题，按追问链组织。

### L1. LoRA 两个矩阵怎么初始化？为什么一个置零？

**答：** 标准实现 $A$ 高斯随机、$B$ **置零**，保证训练第一步 $\Delta W = 0$，模型行为等于基座。"反过来"理论上也成（梯度照样流），关键是初始 $\Delta W = 0$——不能两个都随机，也不能两个都为零。

### L2. $\alpha$ / $r$ / scale / lr / DPO β 五个易混缩放，怎么区分？

**答：** 见 A0.7。**面试金句**：「α 决定训练时 $\Delta W$ 多大；β 决定离 reference 多近；scale 决定运行时 LoRA 影响多强。」

### L3. DPO 优化的是偏好，BLEU 降了正常吗？

**答：** 正常。DPO 优化偏好不保证单调抬高 n-gram。表达更自然/多样时 BLEU 可能降，但 ROUGE（覆盖）可能升。**怎么判成功**：分模型分维度评，chat 看人工/LLM-as-judge 偏好胜率、共情、安全；task 看字段级 P/R/F1。

### L4. 量化为什么不会让模型变傻？

**答：** 模型"变傻"的真正原因是**信息丢失**：
- 8-bit 几乎不掉点（精度损失 < 0.5%）；
- 4-bit NF4 大约掉 1-2 个百分点（perplexity）；
- 知识/推理大部分保留在**主成分方向**（少数高幅值权重）；
- 训练时仍以 fp16 计算，量化只影响**存储**。

### L5. 训练时显存真的省那么多吗？数据流是什么？

**答：** 数据流：

```
[磁盘] NF4 权重（4-bit，7 GB）加载到 GPU
       │
   forward() ──> 按 block 反量化到 fp16 ──> 矩阵乘
       │
   backward() ──> 梯度只传给 LoRA 的 A、B
       │
   AdamW ──> 只更新 LoRA 参数
```

**关键**：4-bit 只用于存储冻结基座；计算始终 fp16；优化器只对 LoRA。

### L6. 为什么记忆读路径默认不用 LLM 重排？

**答：** LLM 重排贵、且会把"理解"再次引入读路径。现行默认：hybrid 召回 + 特征重排 + AER 扩窗 + 覆盖度选择；`MEMORY_LLM_RERANK_ENABLED` 默认关。查询规划器用 LLM 是可选的（无 LLM 则 direct）。

### L7. 为什么不靠 prompt 让模型"自己决定记什么"？

写时让模型判断"该不该记"就是抽取路线——心理场景误记代价高。AER 选择结构上消除该判断：原文全存，查询时再选证据；只有 consent Profile 允许极少结构化偏好。

### L8. 为什么用 BGE-M3 不用 OpenAI Embedding？

**答：**

| 维度 | BGE-M3（本地） | OpenAI Embedding |
|------|---------------|-------------------|
| 中文检索 | 强 | 一般 |
| 隐私 | 完全本地 | 数据出境 |
| 成本 | 一次性 1.2 GB 权重 | 按 token 计费 |
| 维护 | 离线推理 | 依赖外网 |

**关键决策**：本地 + 开源 + 中文强 + 隐私 = BGE-M3。

现行写路径零 LLM；consent 拦截由 `profile/policy.py` 承担。

### L11. PT 真的有用吗？有没有 ablation？

**答：** **坦白：当前没有 PT 的 ablation 数据**（gap）。但理论上 PT 改变了 token 分布：
- 训练完后用一个小批量心理语料算 perplexity，PT 后应明显低于 PT 前；
- 同样的对照实验在通用语料上 perplexity 不应该明显上升（否则就是 catastrophic forgetting）。

**答辩口径**：可以说"PT 的作用是公认的（Qwen / Llama 等都用），本项目复用这一工程惯例；如果做 ablation 应该在心理 unseen 数据上对比『base → PT base』的 perplexity 改善"。

### L12. 数据泄漏怎么防？seen / unseen 切得合理吗？

**答：** 当前 seen / unseen 按"是否进过训练分布"切。**已知问题**：按 id 随机切可能存在"同一对话上下文出现在训练和测试中"——理想的切分：
- 按对话主题切（不是按 id 随机切）；
- 按时间切（训练用前 80%，评测用后 20%）；
- 按用户切（不同用户不出现在训练和测试中）。

**答辩要主动承认**：本项目评测没有用到最严格的防泄漏切法，可能存在少量泄漏。

### L13. SFT、DPO、RLHF、ORPO、KTO、IPO 怎么选？

**答：**

| 方法 | 数据需求 | 模型驻留 | 稳定性 | 适用 |
|------|---------|---------|--------|------|
| SFT | (instruction, response) | 单模型 | 高 | 入门；学格式、风格 |
| RLHF+PPO | 偏好对 + RM | actor+ref+RM+critic | 低 | 大算力；需在线采样 |
| DPO | 偏好对 | policy+ref | 中 | 离线偏好对充足；稳 |
| ORPO | 偏好对 | policy | 中 | 想 SFT+DPO 合一 |
| KTO | (好/坏标签) | policy+ref | 中 | 上线后只有 👍/👎 |

**本项目**：选 **DPO**——离线偏好对充足、不需训 RM、与 4-bit + LoRA 友好。

### L15. embedding 为什么是 1024 维？为什么不更高？

**答：** BGE-M3 官方设计就是 1024 维 dense 向量。**取舍**：
- 维度高 → 表达力强但存储/检索成本高（$O(d)$）；
- 维度低 → 成本低但表达力弱；
- 1024 在 MTEB 等榜单上是 sweet spot（与 768/1536 表现相近但更省）。

本项目每用户最多 30 条记忆，每条 1024 维 float32 = 12 KB；30 条 = 360 KB——远小于一次 LLM forward 的 KV cache。

### J1. 模型训练通常关注哪些性能指标？优先级是什么？

**答：** （来自 `liguodongiot/llm-action/llm-train.md`）

| 指标 | 单位 | 含义 |
|------|------|------|
| **吞吐率** | samples/s、tokens/s | 单位时间内处理的 token/样本数 |
| 单步时间 | s | 一个 step 的耗时 |
| **线性度 / 加速比** | values | 单卡扩展到多卡的效率 |
| 内存占用 | % | 显存使用百分比 |
| 带宽占比 | % | 显存带宽利用率 |
| 训练效率 | tokens/day | 每天训多少 token |
| 浮点运算 | TFLOPS | 每秒浮点运算次数（理论值） |
| **MFU（Model FLOPs Utilization）** | % | 模型一次前反向消耗的算力 / 机器算力 |
| **HFU（Hardware FLOPs Utilization）** | % | 考虑 checkpoint 重计算后的利用率 |

**优先级排序**：吞吐率 > 单步时间 > 线性度 > 内存 > 带宽 > 训练效率 > TFLOPS > 算力利用率。

**SoulHarbor 应用**：本项目是**单卡 QLoRA 4-bit** 训练，**没有**多卡线性度问题，主要看：
- 单步时间（与 batch / grad_acc / cutoff 相关）；
- 显存峰值（14B 4-bit + LoRA 约 36 GB，**单卡够用**）；
- 训练效率（`tokens/day`）。

> **面试金句**：「算力利用率是描述**机器有多忙**；吞吐率是描述**单位时间干多少活**。MFU 上 50% 是优秀，30% 是合格。」

### J2. 混合精度训练（fp16 / fp32）的优缺点？

**答：** 来自 `liguodongiot/llm-action/llm-train.md`。

| 精度 | 范围 | 精度 | 用途 |
|------|------|------|------|
| **fp32** | ±3.4e38 | 23 bit | 权重 / 优化器状态；默认精度 |
| **fp16** | ±65504 | 10 bit | 前向/反向；下溢问题严重（梯度易变 0） |

**fp16 三大问题**：
1. **下溢**（underflow）：训练后期梯度小，fp16 直接归 0；
2. **舍入误差**（rounding error）：累加易丢精度；
3. **溢出**（overflow）：loss / activation 偶尔 > 65504。

**fp16 标准配套**：
- **FP32 master copy**：权重保留 fp32，梯度更新时用 fp32 算；
- **Loss scale**：loss 乘以 scale（避免小梯度下溢），反向时梯度也等比放大，optimizer 更新前再除回；
- **LayerNorm / Softmax 在 fp32**：加法除法累加易出精度问题。

**SoulHarbor 应用**：
- 训练：所有 `train/configs/*.yaml` 均配置 `fp16: true`，通过 AMP 训练；
- 推理：`bnb_4bit_compute_dtype=float16`，矩阵乘在 fp16；adapter / 优化器状态在 fp32。
- 显存账见 §A0 / §B4。

### J3. 半精度 / 量化为什么不会让模型变傻？

**答：** 量化掉的是**细枝末节**，不是**主成分**。

- 神经网络权重近似**正态分布**，少数高幅值权重贡献大部分信号；
- 把这些高幅值映射到更粗的网格上，相对误差小；
- **4-bit NF4 实测 perplexity 上涨 1–2 个点**（Dettmers 论文），推理影响小；
- 训练时仍以 fp16 计算，量化只影响**存储**。

**SoulHarbor 应用**：4-bit NF4 + fp16 计算是项目能单卡跑 14B 的关键；如果量化让模型变傻，项目早就崩了——实测对话质量符合预期。

### J4. 常见大模型量化方法有哪些？GPTQ / AWQ / SmoothQuant 区别？

**答：** 来自 `liguodongiot/llm-action/量化` 章节。

| 方法 | 定位 | 数据依赖 | 本项目用？ |
|------|------|---------|----------|
| **BNB 4-bit / NF4** | 训练时量化 + 推理 | 无 | ✅（训练 + 推理） |
| **GPTQ** | 训练后量化（PTQ），基于 Hessian 二阶信息逐层量化 | 需校准集 | ❌ |
| **AWQ** | PTQ；激活感知——找出"显著权重"加以保护 | 需校准集 | ❌ |
| **SmoothQuant** | PTQ；把激活里的 outlier 平滑到权重上 | 需校准集 | ❌ |
| **LLM.int8()** | 推理；Vector-wise quantization | 无 | ❌ |
| **LLM-QAT** | 量化感知训练 | 无（但需额外训练） | ❌ |
| **KV Cache 量化（KIVI / IntactKV / KVQuant）** | 推理；压缩动态生成的 KV | 无 | ❌ |

**QLoRA 与 GPTQ 的关键区别**：
- **QLoRA**：边训边量化基座 + 挂 LoRA；偏**训练**；
- **GPTQ**：训完再量化（PTQ）；偏**部署**。

**SoulHarbor 为什么不用 GPTQ / AWQ**：项目是教学/科研 + 单卡推理，训练和推理用同一套 BNB，工程简单。如果上线高并发生产环境，可以导出 GPTQ/AWQ 量化引擎。

### J5. 介绍 LoRA、AdaLoRA、QLoRA 这几种高效微调方法及其特点。

**答：** 来自 `liguodongiot/llm-action/llm-ft.md` 与多篇综述。

| 方法 | 核心思想 | 关键参数 | 适用 |
|------|---------|---------|------|
| **LoRA** | 冻结 $W_0$，只训低秩 $BA$ | $r, \alpha$ | 标准 PEFT |
| **AdaLoRA** | 动态分配 rank，重要层大 r、不重要层小 r | rank budget | 大模型多任务 |
| **QLoRA** | LoRA + 4-bit 量化基座 | r, α, bnb_4bit | 单卡训大模型 |

**其他主流 PEFT**（**校招社招最常见必问**）：
- **Prompt Tuning**：在 embedding 层加可学习的 virtual token；
- **P-Tuning**：LSTM + MLP 编码 virtual token，再输入到模型；
- **Prefix Tuning**：每层 attention 的 K/V 前加可学习的 prefix；
- **P-Tuning v2**：把 prefix 加到每一层（深而多）；
- **Adapter**：插入小 MLP 瓶颈层；
- **BitFit**：只训 bias。

| 方法 | 加在哪儿 | 可训练参数量 | 性能 |
|------|----------|-------------|------|
| Prompt Tuning | Embedding 层 | 极少 | 较弱 |
| P-Tuning | Embedding 层 | 极少 | 较弱 |
| Prefix Tuning | 每层 K/V | 较多 | 强 |
| P-Tuning v2 | 每层（深） | 多 | 强 |
| Adapter | 插入新层 | 中 | 中（改结构） |
| LoRA | 权重低秩 | 中（不改结构） | 强 |
| BitFit | bias | 极少 | 弱 |

**SoulHarbor 应用**：选 **LoRA + QLoRA**——不改结构（PEFT 的核心优势），按需切换 adapter，单卡可跑。

### J6. LoRA 中 A 和 B 矩阵的初始化方法，能不能反过来？

**答：** 来自 `liguodongiot/llm-action/llm-ft.md`，引自 LoRA 官方 issue（microsoft/LoRA#98）。

> 标准：$A$ 高斯初始化，$B$ 零初始化。
> **反过来**：$A$ 零初始化，$B$ 高斯初始化也行。
> 关键：**只要两者中一个为零、另一个非零即可**（保证训练初始 $\Delta W = 0$，不破坏基座）。
> 两个都零 → 学不到东西；两个都非零 → 训练起点不是基座。

> **金句**：「**保研老师可能追问 → LoRA 论文 vs 工程实践：Hu 原文选 A 高斯 B 零，是因为 A 输入是 token embedding 分布（高斯初始化更稳）；但反过来实验上没显著差异（PEFT / ms-swift 都支持）。」

### J7. Prefix Tuning、Prompt Tuning、P-Tuning、P-Tuning v2 四种方法的核心区别？

**答：** 来自 `liguodongiot/llm-action/llm-ft.md`。

| 维度 | Prompt Tuning | P-Tuning | Prefix Tuning | P-Tuning v2 |
|------|---------------|----------|---------------|--------------|
| 加在哪儿 | Embedding 层 | Embedding 层（加 LSTM+MLP 编码） | 每层 K/V 前 | 每层（深而多） |
| 训什么 | 虚拟 token | 虚拟 token + LSTM/MLP | Prefix + 前面 MLP | Prefix 参数 |
| 推理时 prefix 处理 | 直接拼 | 替换 encoder | 训完只保留 Prefix | 训完保留 |
| 性能 | 较弱 | 较弱（受 LSTM 编码影响） | 较强 | 较强 |
| 参数量 | 极少 | 少 | 较多 | 多 |

**关键差别**：
- **Prompt Tuning vs Prefix Tuning**：前者只在 embedding 加（浅），后者在每层加（深）；
- **P-Tuning 用 LSTM+MLP 编码虚拟 token**：让收敛更快，但 LSTM 让 token 之间有顺序依赖（不一定优）；
- **P-Tuning v2 = Prefix Tuning + 去掉 MLP**：深而多，效果稳定。

**SoulHarbor 没选这些方法的理由**：需要学**任务级技能**（DPO 对齐 / tool-call JSON），仅训 prefix / virtual token 不够；LoRA 直接训权重增量更直接。

### J8. RLHF / PPO 为什么难？为什么现在很多人改用 DPO？

**答：** 来自 `liguodongiot/llm-action/RLHF` 章节与多篇综述。

**PPO 在 RLHF 里难在五处**：

1. **需要训练 reward model**：单独训练 + 单独评估；
2. **需要 actor + critic + reference + value 共 4 个模型驻留**：14B actor + 14B ref + 14B critic + RM = 显存爆炸；
3. **在线采样**：每次训练都要跑 policy 采样生成回复，慢且不稳定；
4. **reward hacking**：critic 学到了 reward 函数漏洞，policy 利用漏洞刷分；
5. **KL 约束敏感**：$\beta$ 太小漂移，太大不学偏好。

**DPO 为什么能规避**：
- 把 RLHF 的最优策略写成闭式，发现 reward = $\beta\cdot\log(\pi/\pi_\text{ref}) + \text{const}$；
- 不需要 RM，只需要 reference（与 policy 同基座）；
- 离线训练：直接用偏好对 (chosen, rejected) 做监督；
- 稳定性更好（标准监督学习）。

**SoulHarbor 为什么选 DPO**：离线偏好对充足（3000 对）、单卡算力紧张（4 个模型驻留不了）、DPO 与 4-bit + LoRA 友好。

> **金句**：「**RLHF 像开赛车——快但难；DPO 像自动驾驶——稳但慢**。本项目选稳。」

### J9. DPO 是不是就完全替代 RLHF 了？

**答：** **不完全**。区别：

| 维度 | RLHF+PPO | DPO |
|------|----------|-----|
| 数据形式 | 在线采样 + reward 打分 | 离线偏好对 |
| 模型驻留 | actor+ref+critic+RM (4) | policy+ref (2) |
| 多样化奖励 | 可任意（RM 给任意标量） | 仅偏好对 |
| 性能上限 | 高（可扩展多目标） | 受偏好对分布限制 |
| 工程成本 | 高 | 低 |

**DPO 的限制**：
- 偏好对 = 1 vs 1，无法表达「这条比那条好但又差一点点」（Bradley-Terry 假设把偏好强度塌缩成 0/1）；
- 无法融合多维 reward（safety + helpfulness + conciseness）；
- 离线训练 → 不可能学到"用户当前轮"的反馈。

**变体**：
- **IPO**：用 $\sigma^{-1}$ 替代 sigmoid，适合噪声大的偏好对；
- **KTO**：用好坏标签（不需配对），适合 👍/👎；
- **ORPO**：SFT + 偏好项合一，可省 ref；
- **SimPO**：长度归一化的对数概率作 reward，可省 ref。

**SoulHarbor 的妥协**：偏好对齐阶段选了 DPO；评估上承认只覆盖了"共情偏好"，没覆盖"安全"、"简洁"等多维 reward。

### J10. 训练指标的"Macro F1 vs Micro F1"怎么选？


| 类别 | Macro F1 | Micro F1 |
|------|----------|----------|
| **定义** | 每类 F1 算术平均 | 全局 TP/FP/FN 算 F1 |
| **对不均衡敏感** | **敏感**（小类占比权重相同） | 不敏感（大类主导） |
| **何时用** | **类别不均衡**，要"每类都做好" | 大类主导，"整体好就行" |
| **避坑** | "no_changes 占 50% → 啥都不做 macro_f1 也高"（不行） | "macro_f1 高但小类全崩"（不行） |


### J11. LLM 推理服务的关键性能指标？

**答：** 来自 `liguodongiot/llm-action/llm-inference.md`，是工业界部署的标准。

| 指标 | 含义 | 关键 |
|------|------|------|
| **TTFT**（Time to First Token） | 输入到首 token | 实时对话重要 |
| **TPOT**（Time Per Output Token） | 每 token 时延 | 用户感知"速度" |
| **端到端时延** | 总时延 ≈ TTFT + TPOT × 输出 token 数 | - |
| **请求吞吐** | 每分钟请求数 | 并发能力 |
| **生成吞吐** | tokens/s | 批量效率 |
| **单请求成本** | 每次推理的钱 | 商业化 |
| **百万 token 成本** | 单位成本 | - |

**SoulHarbor 的实际情况**：
- TTFT：包含同步 rerank ≈ 800ms（实测）；
- TPOT：4-bit QLoRA 单并发 ≈ 50-100ms/token；
- 端到端：100 token 回复 ≈ 800ms + 100 × 100ms = 10.8 秒；
- 单并发：RLock 串行 GPU，batch=1。

**生产化路径**（明确说 gap）：vLLM PagedAttention + continuous batching + 多卡张量并行 → TTFT P99 < 500ms、TPOT < 50ms。

### J12. 端到端推理时延和模型大小的关系是线性的吗？

**答：** **不是线性，是次线性**。来自 `liguodongiot/llm-action/llm-inference.md`。

- 同样硬件下，模型越大推理越慢；
- 但**推理速度比 ≠ 模型参数量比**：
  - MPT-30B 延迟 ≈ MPT-7B 的 2.5 倍（参数量比 ≈ 4.3）；
  - Llama2-70B 延迟 ≈ Llama2-13B 的 2 倍（参数量比 ≈ 5.4）；
- **原因**：大模型并行度更好、矩阵乘法 GPU 利用率更高。

**SoulHarbor 应用**：14B 在单卡上比 7B 慢约 1.5–2 倍，但**比 70B 慢 5 倍**；选 14B 是显存与精度的折中。

### J13. 输入 token 长度对 TTFT 的影响？

**答：** 来自 `liguodongiot/llm-action/llm-inference.md`。

- **输入长度对端到端时延影响小**：512 个输入 token 增加的延迟 < 生成 8 个额外输出 token 的延迟；
- **但对硬件要求高**：长输入直接撑爆 KV cache；
- **TTFT 与输入长度相关性弱**：有研究指出 250–800 输入 token 之间 TTFT 几乎没差异。

**SoulHarbor 应用**：
- 记忆注入块最多 3600 字 ≈ 1500 token，对 TTFT 影响小；
- 主要瓶颈是**同步 rerank**（LLM 生成）+ **GPU 串行**，不是输入长度；
- 改进路径：rerank 异步化 → TTFT 砍掉 rerank 的 800ms。

### J14. LLM 推理的瓶颈是什么？KV Cache 是什么？

**答：** 来自 `liguodongiot/llm-action/llm-inference.md`。

**推理分两阶段**：

| 阶段 | 算力瓶颈 | 显存瓶颈 | 优化目标 |
|------|----------|---------|---------|
| **Prefill**（处理输入） | 算力密集（GEMM） | 不敏感 | 缩短 TTFT |
| **Decode**（逐 token 生成） | 访存密集（每步读权重 + KV） | **KV cache** | 提升 TPOT |

**KV Cache**：decode 阶段把历史 token 的 K/V 缓存到显存，避免每步重算。显存占用：

$$\text{KV Cache} = 2 \times \text{layers} \times \text{batch} \times \text{seq\_len} \times H_{kv} \times d_k \times \text{sizeof(精度)}$$

举例：14B 模型 40 层、seq_len=4K、$H_{kv}=28$、$d_k=128$、fp16：

$$\text{KV Cache} = 2 \times 40 \times 4\text{K} \times 28 \times 128 \times 2 = 2.3\ \text{GB/请求}$$

**SoulHarbor 应用**：单并发 + 短输入 + KV cache 占用 < 5 GB，**不是瓶颈**；瓶颈是 LLM rerank 同步串行 + 单并发。

### J15. 大模型推理优化技术有哪些？

**答：** 来自 `liguodongiot/llm-action/llm-inference.md` 的「推理优化技术」目录。

| 技术 | 优化什么 |
|------|---------|
| **KV Cache** | decode 阶段访存 |
| **KV Cache 量化（KIVI / IntactKV / KVQuant）** | KV Cache 显存 |
| **Continuous batching**（vLLM） | 多请求共享 prefill/forward |
| **PagedAttention**（vLLM） | KV Cache 显存碎片 |
| **FlashAttention** | attention 计算访存 |
| **Flash Decoding** | 长序列 decode 加速 |
| **Speculative Decoding** | 用小模型 draft、大模型 verify |
| **Chunked Prefill** | 长输入拆批 |
| **张量并行 / 流水并行** | 多卡扩展 |
| **结构化文本生成**（constrained decoding） | 限制输出 schema |

**SoulHarbor 没做的事**（明确说 gap）：
- 没上 vLLM（单并发 batch=1，vLLM 收益小）；
- 没上 PagedAttention；
- 没 KV Cache 量化；
- 没 Speculative Decoding。

**生产化路径**：上 vLLM + 多卡张量并行 → continuous batching 把并发吞吐拉起来。

### J16. 大模型为什么会"幻觉"？怎么缓解？

**答：** 来自 `wdndev/llm_interview_note` + 多篇综述。

**幻觉的来源**：
1. **训练数据噪声**：SFT/DPO 数据中有错误事实，模型学会；
2. **解码时的随机性**：top-p / temperature 让模型"瞎猜"；
3. **长尾知识遗忘**：参数没真正"记"事实，是学"分布"；
4. **指令冲突**：用户指令与 system / 检索内容冲突时，模型偏向满足指令；
5. **OOD 输入**：训练分布外的输入，模型泛化到不存在的概念。

**缓解方法**：
| 方法 | 缓解什么 |
|------|---------|
| RAG（检索增强） | 事实性幻觉 |
| 限制 temperature（≤0.3） | 随机幻觉 |
| constrained decoding（JSON Schema） | 格式幻觉 |
| 数据去重 + 高质量过滤 | 数据噪声 |
| 自我一致性（self-consistency，多次采样投票）| 不确定性幻觉 |
| 训练时"诚实回答不知道" | 强行输出幻觉 |

**SoulHarbor 怎么做**：
- 系统 prompt 明确"不替代专业诊断"；
- RAG 注入用户记忆，减少对"常识"的依赖；
- 但**幻觉不可能根除**——这是 LLM 的固有局限，必须诚实承认。

### J17. 怎么评估开放性生成任务？

**答：** 来自 `liguodongiot/llm-action/llm-eval.md`。

**传统指标的问题**：
- BLEU / ROUGE 与人类基准不对齐（偏离实际需求）；
- 心理对话无唯一标准答案——两个回复都"合理"但表达不同；
- 自动指标无法捕捉**风格 / 共情 / 安全性**。

**更好的评估方式**：

1. **Elo 评分**（最贴合实际）：让用户盲评 A vs B 的对话质量；
2. **业务指标**：用户对话轮次、停留时间、👍/👎、复访率；
3. **LLM-as-judge**：GPT-4 当裁判打分（5 分量表或 pairwise），有偏差但成本低；
4. **人工评估**：心理学研究生盲评 5 分量表，最可信但成本高。

**SoulHarbor 的妥协**：用 BLEU/ROUGE 做**相对比较**（base → sft → dpo），承认不能直接证明"更共情"；gap：没有 LLM-as-judge 对话评测、没有用户行为 A/B。

### J18. RAG 系统的核心组件是什么？

**答：** 来自多篇 RAG 综述。

```
User Query
   ↓
[Query 理解]（改写 / HyDE / step-back）
   ↓
[Retriever]（bi-encoder 向量召回）
   ↓
[Re-Ranker]（cross-encoder / LLM rerank）
   ↓
[Filter]（相关性阈值 / 去重 / 安全过滤）
   ↓
[Generator]（LLM 接收 query + 召回 chunk 生成回复）
```

**关键设计选择**：
- **chunk 大小**：太小召回不准，太大噪音多；常见 256–512 token；
- **召回数量 K**：5–10；过多会撑爆 prompt，过少召回不全；
- **embedding 模型**：中英通用 → BGE-M3；中文 → text2vec / m3e；
- **rerank 模型**：bi-encoder 召回 + cross-encoder / LLM 重排是当前主流。

**SoulHarbor 是结构化记忆库，不是经典 RAG**：检索的"chunk"是结构化条目（有 type/title/summary/how_to_apply），不是文档切片；写侧是 Agent 而非离线索引。

### J19. Lost in the Middle 是什么？怎么解决？

**答：** Liu et al., 2023 的发现。

**问题**：长 prompt 里中间位置的信息利用差，开头和结尾的信息利用好——**U 形 attention 利用曲线**。

**原因**：
- Position embedding 的近因效应；
- Prefill 阶段的 attention 计算中段较分散；
- 模型没经过"长 prompt 信息查找"的训练。

**解决**：
- 把最关键信息放**开头或结尾**；
- Re-rank 把最相关放第一位；
- 减少 prompt 长度（RAG 比塞全文好）；
- 用长上下文训练（如 YaRN / NTK-aware 插值）。

**SoulHarbor 的做法**：
- 记忆块以 **system 前缀**注入（放在摘要之后、未摘要原文之前），并带"与当前问题无关时可忽略"指令；
- 覆盖度选择保证候选去冗余、时间桶多样性（新旧兼顾）；
- token 预算 1600 防过长稀释；
- 详见 §Q16。

### J20. 多 Agent 系统 vs 单 Agent 的区别？

**答：** 来自 `liguodongiot/llm-action/Agent` + 多篇综述。

| 维度 | 单 Agent | Multi-Agent |
|------|----------|-------------|
| **角色** | 一个大脑 + 多个工具 | 多个专家 + 协调器 |
| **任务分解** | Agent 自己拆 | Supervisor 拆 |
| **通信** | 自己内部状态 | Agent 间 message passing |
| **适用场景** | 简单任务 | 复杂多步任务 |
| **实现复杂度** | 低 | 高（LangGraph / AutoGen） |
| **调试难度** | 中 | 高 |

**SoulHarbor 是"轻多 Agent"**：5 个 tool 是"伪 Agent"，本质是一个 LLM 调用 5 个工具；**不算真多 Agent**。

**如果升级到真多 Agent**：引入 Supervisor 拆分任务 → Researcher 并行检索 → Writer 综合 → Verifier 核查引用（参考 OpenAI Deep Research）。

### J21. Agent 系统怎么做超时和资源释放？

**答：** 三层超时：

1. **外部超时**（HTTP 客户端）：`aiohttp.ClientTimeout(total=30)` 或 `requests.get(timeout=30)`；
2. **内部任务超时**：`asyncio.wait_for(task, timeout=10)`；
3. **底层操作超时**（DB / 网络）：连接级别 `connect_timeout`、`read_timeout`。

**资源释放**：
- GPU 显存：任务结束及时 free；
- KV cache：每请求结束清；
- 数据库连接：用连接池，避免泄漏。

**SoulHarbor 怎么做**：
- 同步路径：`max_new_tokens=1024` 隐含生成上限；
- 流式路径：`CancelCriteria` + `threading.Event`（`_iter_stream` finally 中 `cancel_event.set()` + `worker.join(timeout=5.0)`）；
- 后台路径：`run_post_turn` 在 ThreadPoolExecutor 排队但**无硬超时**——长任务可能堆积（gap）。

### J22. 你的项目里 Agent 的状态怎么管理？

**答：** SoulHarbor 的 Agent 状态非常轻量：

- **会话级状态**：DB 持久化（messages / conversations / memories）；
- **内存级状态**：`_summary_in_progress` set 防止并发跑摘要；
- **没有跨会话工作流状态**——每个工具调用是独立事务。

**对比工业级 Agent（LangGraph 风格）**：
- 节点（node）+ 边（edge）+ 状态图（StateGraph）；
- 自定义 reducer（`operator.add` / `pending_review_reducer` / `merge_dicts`）；
- DAG 多跳（`Send` 动态并行 + `depends_on` 依赖注入）。

**如果 SoulHarbor 要升级到工业级**：
- 把当前的"线性 5 个 tool_call 循环"换成 StateGraph；
- 加 checkpoint 机制（崩溃恢复）。

### J23. 你怎么测试 Agent？

**答：** 三层测试金字塔：

| 层级 | 测试对象 | 工具 | SoulHarbor 现状 |
|------|---------|------|----------------|
| **单元** | 单模块（`chunker` / `selector` / `profile.detector` 等）| pytest | ✅ 部分覆盖（`product_app/tests/memory/test_aer.py`） |
| **集成** | `RetrievalPipeline.run` / `build_chat_context` 整体 | pytest + mock LLM | ⚠️ 弱 |
| **端到端** | `/_startup` + `/api/chat_stream` + DB | 真实对话压测 | ❌ 缺失 |

**端到端 Agent 测试的难点**：
- LLM 输出有随机性 → 用 LLM-as-judge 或确定性 seed；
- 真实对话很长 → 用 fixture 固化"金标对话"；
- 评估慢 → 离线跑 + 离线评分。

**SoulHarbor 已有**：
- `evaluate/memory/`（30 条长程 QA，AER vs Mem0 同协议）：QA 93% vs 64%、内容 F1 0.89 vs 0.48；
- `evaluate/dialogue/`（2000 条 SoulChat BLEU/ROUGE）：base 13 → dpo 28。

**缺**：外部基准（LongMemEval 子集）对照与更大规模记忆评测。

### J24. Agent 失败时怎么降级？

**答：** 五层降级：

3. **替代路径**：记忆检索失败 → 用关键词匹配顶替；
4. **限流保护**：API rate limit 超限 → 返回降级回复；
5. **熔断**：连续失败 → 直接拒绝请求，触发人工介入。

**SoulHarbor 的兜底**：

- 记忆写（分块/向量化）失败 → 进 `memory_embed_retry` 重试队列，对话不受影响；
- 摘要失败 → logger.warning 但不影响对话；
- 记忆检索失败 → `build_context` 抛错被捕获，注入空块（`engine.py` fallback），对话继续；
- LLM generate 失败（流式且 `chunks` 为空） → 客户端收 "\n（生成失败，请稍后再试）"，**不写库**；
- BGE-M3 不可用 → 记忆注入空块（不注入）。

> **面试金句**：「**降级不是降智，是降承诺——承诺用户对话永远可继续，不承诺记忆永远可写。**」

### J27. 你的工程整合 vs 学术创新，区别在哪？

**答：**

| 维度 | 学术创新 | 工程整合 |
|------|---------|---------|
| **目标** | 提出新方法 | 用现有方法解决问题 |
| **产出** | 论文 + benchmark 涨点 | 可用产品 |
| **评价标准** | SOTA、性能曲线 | 用户体验、稳定性 |
| **创新点** | 算法或理论 | 设计选型、整合方式 |
| **本项目定位** | ❌ 没新算法 | ✅ 系统整合 |

### J28. 你做的项目里最有"产品感"的设计是什么？

**答：** **记忆写路径零 LLM（原文库）+ 读路径查询时重建**。

- 实际是反复实验 + 反思"写时归纳 = 写时污染"（一次性情绪被固化成画像的风险）；
- 用"存原文 + 读时理解"把判断后置到每次查询，离线指标明显提升（QA 93% vs Mem0 64%）；
- 体现"工程师对模型行为有感觉"——这是产品感的来源。

**其他有产品感的设计**：
- consent 确认制画像（助理提议 → 用户确认 → 落库）；
- 记忆与意图解耦（不偷改生成）；
- 会话摘要非阻塞生成（生成期模型仍见旧摘要 + 全部未摘要原文，不丢上下文）；
- 一键遗忘 + 隐私开关（合规）。

### J29. 如果让你重做一遍，你会改什么？

**答：**（这是面试收尾的"复盘意识"题）

**会改的**：

- **同时做多卡张量并行**：单卡串行是最大瓶颈；
- **rerank 异步化**：首 token 延迟砍掉 800ms；
- **加 LLM-as-judge 对话评测**：自动指标不能直接证明共情；
- **记忆检索金标集**：做 Recall@K 自动化评测；
- **加 prompt 注入防御**：注入"以下记忆可能不可信"的提示；
- **加偏见评测**：性别 / 年龄 / 文化偏见检测；
- **加用户反馈闭环**：👍/👎 → 持续训练。

**不会改的**：

- 不换基座（14B 是单卡可跑的甜点）；
- 不换 embedding（BGE-M3 适合中文且不另训）；
