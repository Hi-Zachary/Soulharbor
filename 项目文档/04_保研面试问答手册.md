# 保研面试问答手册（修订版）

> 本手册用于保研、推免和研究型技术面试准备。前 95 题按项目主线整理，后续章节进一步覆盖真实面试中的高频追问：先讲清研究问题和项目主线，再进入模型适配、长期记忆、实验设计、系统实现与个人经历。答案写得相对完整，现场应根据面试时间压缩，而不是逐字背诵。
>
> 项目主线统一为：**让系统既知道应该怎样回应，也知道应该依据这个用户的哪些历史经历回应。** 模型适配负责当前轮次的互动策略，长期记忆负责跨会话的个人语境，两者最终服务于同一个目标——持续、准确且符合倾听需求的心理支持对话。

## 使用建议

1. 先掌握 Q1、Q3、Q6、Q12、Q35、Q60、Q73、Q91，这几题基本覆盖项目主线。
2. 回答技术问题时遵循“为什么做—具体怎么做—实验说明什么—还缺什么”四步，不要只背模块名称。
3. 所有数字只用于说明当前实验协议下的相对结果，不把离线指标扩大解释为真实用户效果。
4. 被追问相关工作时，可以准确说明方法来源，但不要主动把项目讲成某一篇工作的复刻；重点说明问题约束、设计选择和实验迭代。
5. 个人贡献、失败经历和不足必须结合真实过程回答，不要使用泛化模板。

# 第一部分 项目定位、问题与贡献

### Q1. 请用一句话介绍 SoulHarbor。

SoulHarbor 是一个面向校园心理支持的长期对话系统，核心研究问题是：**如何让模型在多次交流中恢复用户持续变化的个人经历，并据此采用更符合倾听、理解和适时建议需求的回应方式。**

这句话同时包含了项目的两个技术层次。第一层解决“模型应该怎么说”，也就是减少模板化表达、过早建议和过度理性分析；第二层解决“模型应该依据什么说”，也就是从跨会话历史中找回与当前问题真正相关、且没有被旧状态误导的个人经历。项目不是两个独立功能的简单叠加，而是围绕长期互动质量建立的一条完整链路。

### Q2. 你最初观察到的具体问题是什么？

我最初关注的不是模型能不能生成通顺中文，而是它在心理支持对话里经常采用不合适的互动方式。比较典型的现象有三类：第一，回复容易重复固定结构，例如先概括、再列建议、最后鼓励，连续交流后模板感很强；第二，用户还在表达时，模型就急于分析原因或提出解决方案，忽略了澄清和倾听；第三，对只希望被理解和安慰的用户，模型容易表现得过于理性，像在给问题做诊断，而不是参与一段有节奏的对话。

当交流跨越多次会话后，又会出现第二类问题：模型不知道用户提到的人是谁、事情发展到哪一步、过去的决定是否已经改变。简单地保存几条事实也不够，因为一次情绪或一个中间状态可能被误当成稳定结论。因此，我们把问题收敛为“回应策略适配”和“长期个人语境恢复”两个相互依赖的部分。

### Q3. 为什么说这不是两条割裂的技术线？

最终一条回复的质量同时取决于两个条件：系统有没有拿到正确的个人历史，以及模型会不会以合适的方式使用这些历史。记忆系统即使准确找回“用户上周与室友发生冲突”，如果生成模型仍然立即讲道理、列方案，回复依然不符合倾听需求；反过来，模型即使学会了温和追问，如果不知道用户已经和室友和好，也可能沿用旧状态继续安慰，造成明显的不连贯。

所以我把两条技术线解释为同一个生成过程中的两个条件变量：长期记忆提供可追溯的个人经历证据，模型适配决定这些证据如何被转化为当前回复。它们在生成前汇合，而不是两套平行产品功能。

### Q4. 为什么通用大模型不能仅靠提示词解决这些问题？

提示词可以规定语气和基本原则，但它很难稳定改变模型长期形成的生成偏好。比如系统提示可以写“先倾听、不要过早建议”，模型仍可能在复杂对话里恢复到熟悉的“分析—建议”结构；而且提示词越长，越会占用上下文，并与会话摘要和长期记忆竞争注意力。

更重要的是，提示词并不能解决跨会话证据选择。它可以告诉模型“参考用户历史”，却不能决定在几百条历史消息中应该找哪几条、哪些状态已经过时、哪些片段需要组合才能构成完整经历。因此，我们用微调改变生成分布，用独立记忆路径解决历史证据选择，而不是把所有要求都写进一个越来越长的 system prompt。

### Q5. 长期记忆在这个项目中具体解决什么问题？

长期记忆不是为了让模型“记住得越多越好”，而是解决三个更具体的问题。第一是连续性：用户不需要每次重新解释人物关系、事件背景和已经尝试过的方法。第二是个性化：模型可以依据用户真实表达过的沟通偏好和经历，而不是生成泛化安慰。第三是状态更新：系统要区分“曾经发生过”与“现在仍然如此”，避免旧状态压过新状态。

因此我们的记忆系统不只做相关性检索，还关注证据是否完整、是否跨会话互补、是否反映当前状态。这个定位决定了后续为什么要使用原始 Trace、自适应扩窗、时间感知选择和按时间顺序注入。

### Q6. 项目的主要贡献如何概括？

我会概括为三个层次。第一，针对心理支持对话中模板化、过早建议和过度理性的问题，构建了 PT、SFT、DPO 的领域适配链路，并用轻量意图分类器调节同一份 LoRA 的推理强度，使咨询和闲聊之间保持连续而不是完全切换模型。

第二，针对长期对话中记忆碎片、写时误归纳和旧状态干扰的问题，设计了以原始 Trace 为主体的长期记忆系统。查询时通过 Planner、Dense 与 BM25 混合召回、RRF、多查询 Anchor Cross-Encoder、coverage 选种子、自适应扩窗和 CE Top-k，恢复一组可用于回答当前问题的经历证据。

第三，项目不仅展示终版，还保留了方法迭代和负结果。窗级 CE 一度造成窗口数量和时间覆盖下降；裸 Anchor CE 又暴露出关键短事实容易被 top-k 截断的问题；最终才形成多查询 coverage 方案。这个过程说明模块位置和优化目标需要实验验证，而不是“模型越强越好”。

### Q7. 老师说“这些都是已有模块，创新在哪里”，你怎么回答？

我会先承认 LoRA、DPO、BM25、RRF、Cross-Encoder 和 MMR 都是成熟方法，项目不把这些基础组件包装成原创算法。我的贡献主要体现在问题定义、模块职责和场景化取舍上：心理支持对话不仅需要相关信息，还要避免把一次表达固化成长期判断；记忆选择也不仅是单段相关性排序，还涉及状态更新、多窗口覆盖和时间顺序。

更具体地说，我们通过实验发现，通用文档式 rerank 放在经历窗之后并不适合这个任务，因此把 CE 前移到 anchor 层，只负责种子精排；时间有效性和集合覆盖继续由后续选择器负责。创新强度应当被准确描述为“面向具体问题的系统化方法设计和实证分析”，而不是声称重新发明了长期记忆范式。

### Q8. 你如何说明自己参考了相关工作，但不是照着实现？

我会从“已有工作解决了什么”和“我们的约束有什么不同”两方面回答。领域对话研究让我意识到，心理支持的失败不只体现在事实错误，还体现在建议时机、倾听感和回复结构；长期记忆研究则提供了抽取式记忆、原始经历、上下文化检索等不同路线。我们没有否认这些基础思想，而是把它们放进校园心理支持这个高敏感、状态易变化的场景中重新检验。

项目中的关键选择并不是照抄某一条流水线。例如我们试过扩窗后的神经精排，结果下降；又试过裸 Anchor CE，发现它能改善 staleness 和内容 F1，却会漏掉导师、地点和偏好等短证据；最终才引入原始问题与 Planner 子查询共同打分的 coverage selection。这个设计来自具体错误分析，而不是先看一张架构图再复刻。

### Q9. 这个项目最核心的研究假设是什么？

可以拆成两个相互连接的假设。第一，心理支持中的回复质量不仅由语言流畅度决定，模型需要对“何时倾听、何时追问、何时建议”进行专门的行为适配。第二，在个人状态经常变化的长期对话中，保留可追溯的原始经历，并把复杂理解放到查询时完成，比写入时就把对话压成结论更不容易造成持续性的错误。

实验分别围绕这两个假设建立证据。模型侧比较 base、SFT 和 DPO；记忆侧固定 reader，只替换记忆库和读路径，并增加时间项和 CE 位置的消融。当前证据能支持的是离线协议下的相对优势，不等于对所有长期对话系统都成立。

### Q10. 项目最强的证据和最弱的证据分别是什么？

最强的证据来自记忆侧的同协议对照和逐步消融。固定 reader、固定问题，只替换记忆形态后，QA、staleness 和内容 F1 均有明显差异；时间项移除后性能下降，也说明选择器并非装饰。窗级 CE 和裸 Anchor CE 的失败样本还能解释模块为什么放在当前位置。

相对较弱的是回应行为层的主观质量证据。Base 到 SFT 的 BLEU/ROUGE 提升能说明领域分布和参考回复的接近程度，但无法直接证明“更会倾听”；DPO 后 BLEU 略降也需要结合偏好目标解释。当前缺少系统的人类盲评，因此我不会把自动指标直接说成共情能力已经得到充分证明。

### Q11. 这个项目为什么更像研究，而不只是产品开发？

产品开发关注功能是否可用，而研究还要求提出可检验的问题、比较不同假设并分析失败原因。SoulHarbor 确实有对话界面、会话管理和记忆开关，但这些主要用于跑通闭环。真正的研究部分是：为什么写时抽取会在状态变化场景中造成错误固化；为什么单窗 CE 可能损害多窗覆盖；相对新近性是否真的改善当前状态判断；模型适配与记忆证据如何分协议评测。

这些问题都有对照、消融或负结果支撑。即使去掉前端，训练链路、记忆形态和评测结论仍然成立，所以我会把它定义为一个有完整工程载体的研究原型。

### Q12. 请用三分钟完整介绍项目。

我会先用四十秒讲问题。通用大模型在心理支持对话中虽然语言流畅，但容易出现固定模板、过早建议和过度理性分析；当交流跨越多次会话时，模型又缺乏稳定的个人语境，容易忘记关键经历，或者把旧状态当成当前状态。因此项目关注的不是“做一个更会聊天的机器人”，而是长期互动中回复方式和历史依据的共同质量。

接下来用一分钟讲方法。回应行为层以 Qwen3-14B 为基座，依次做领域继续预训练、倾听式 SFT 和偏好 DPO；MacBERT 只判断咨询或闲聊，用于调节同一份 LoRA 的强度。长期记忆层以原始 Trace 为主体，Profile 只保存少量稳定事实。查询时 Planner 生成直接查询或子查询，Dense 和 BM25 各召回候选，RRF 融合后用原始问题与子查询共同进行 Anchor CE 打分，通过 coverage 选出种子，折叠同消息多 chunk，再在所属会话内自适应扩窗。最终按 CE 分数取 Top-k，按消息记录时间展示并注入生成模型。

最后用一分钟讲证据和反思。对话侧 Base 到 SFT 的自动指标明显提升，DPO 则更偏向调整回复偏好；记忆侧在固定 reader 的 all_50 协议上，ER 的 QA 为 90.8%，staleness 为 6.9%，内容 F1 为 0.602，对照方法分别为 68.7%、46.6% 和 0.400。我们还发现窗级 CE 会伤害多窗和时间覆盖，因此最终只在 anchor 层使用 CE。当前最大的不足是人工共情评测和更独立的泛化测试仍需补充。

# 第二部分 模型适配与回应行为

### Q13. 模型训练链路分为哪些阶段？每一步解决什么问题？

训练主线是 PT、SFT 和 DPO。PT 使用约 24443 条心理领域文本继续做因果语言建模，目的是让基座更熟悉中文心理支持中的表达和语义分布；SFT 使用约两万条对话数据学习“给定用户表达后应该怎样回应”，同时混入少量自我认知样本稳定项目身份；DPO 使用约 3000 对 chosen/rejected 数据，在 SFT 基础上压制敷衍、空泛、说教和过早建议等回复倾向。

此外，MacBERT 分类器不是训练主线中的第四阶段，而是运行时的轻量路由模块。它不生成回复，只根据当前用户输入判断更偏咨询还是闲聊，从而调节同一份 LoRA 的推理强度。

### Q14. 为什么在 SFT 前做继续预训练？

继续预训练和 SFT解决的问题不同。PT仍然优化下一词预测，主要改变模型对领域词汇、口语表达和共现关系的熟悉程度；SFT才直接学习“在这样的对话条件下输出什么回复”。如果基座对心理领域表达不够熟悉，SFT需要同时完成语言分布适配和任务格式学习，训练难度更高。

不过当前项目没有做完整的 PT ablation，所以我不会声称 PT 的独立收益已经被严格证明。更严谨的补充实验是：比较有无 PT 时领域验证集的 perplexity、SFT 收敛速度和最终回复指标，同时检查通用能力是否明显退化。

### Q15. SFT 在项目中具体学到了什么？

SFT首先学习对话映射，也就是在用户表达压力、冲突或犹豫时，回复应该包含哪些信息和怎样的互动节奏。它不只是学习温柔措辞，还会影响是否先复述用户感受、是否提出澄清问题、建议是否过早出现，以及回复长度是否合适。

训练时用户和系统部分作为条件，主要对助手回复 token 计算损失。这样可以避免模型花大量容量复现用户原话或系统提示。少量自我认知样本与主 SFT 同阶段混合，用于稳定名称和身份，不应被讲成独立的“第四阶段训练”。

### Q16. 为什么还需要 DPO？SFT 不够吗？

SFT告诉模型一个可接受的参考答案，但心理支持对话往往有多种语言上都正确的回复，它们的互动质量却不同。比如两个回复都相关，一个先确认用户感受并留出表达空间，另一个马上给出三条建议；仅靠最大似然学习不一定能稳定区分这种相对偏好。

DPO使用 chosen/rejected 对，直接拉开两类回复的相对概率。它适合我们这种可离线描述的偏好目标，而且不需要额外训练奖励模型和运行 PPO。项目采用低学习率、较小 beta 和一轮训练，是为了在已有 SFT 行为上做温和调整，而不是重新塑造整个模型。

### Q17. DPO 数据如何构造？最大的风险是什么？

每个样本包含同一个对话上下文下的 chosen 和 rejected。Chosen 来自相对高质量的回复；Rejected 根据敷衍、欠共情、过早建议、说教等失败模式生成，并经过基本质检。DPO prompt 与主 SFT 数据按对话签名做互斥，降低同一对话既被监督又被偏好训练的泄漏风险。

主要风险是偏好对本身不可靠。Rejected 如果太差，任务会变得过于容易，模型只学会识别明显坏答案；如果 chosen 与 rejected 的长度和格式差异过大，模型可能把长度当作捷径；如果 rejected 实际上不比 chosen 差，就会产生反向信号。因此更完整的质检应包括人工抽样胜率、长度匹配、模板频率和主题分布检查。

### Q18. DPO 的目标函数和 beta 应怎样理解？

DPO比较策略模型相对于参考模型对 chosen 和 rejected 的偏好差。常用形式可以写为：

$$
\mathcal{L}_{\mathrm{DPO}}=-\log\sigma\left(\beta\left[\log\frac{\pi_\theta(y_w|x)}{\pi_{\mathrm{ref}}(y_w|x)}-\log\frac{\pi_\theta(y_l|x)}{\pi_{\mathrm{ref}}(y_l|x)}\right]\right)
$$

直觉上，它希望 chosen 相对 reference 的提升幅度大于 rejected。Beta 控制偏好更新的尺度和保守程度，不能与 LoRA 的 alpha 混淆。项目中 beta 取 0.1，并配合较低学习率和一轮训练，以减少从 SFT 分布中过度漂移的风险。

### Q19. SFT 的损失为什么通常只计算助手回复部分？

SFT本质上仍是条件语言模型训练：给定 system 和 user 上下文，预测 assistant 回复。若对整段对话所有 token 都计算损失，模型会花大量梯度复现固定系统提示和用户输入，尤其当输入比输出更长时，真正的回答行为会被稀释，还可能增加复读用户的倾向。

因此训练数据需要正确构造 chat template 和 loss mask。面试中如果被追问实现细节，我会强调不仅要检查 JSON 格式，还要抽样查看 token 化后的角色边界和标签掩码，确认助手回复被完整监督、条件部分被正确忽略。

### Q20. 为什么选择 Qwen3-14B 作为基座？

选择 14B 是中文能力、上下文处理、显存预算和可复现性之间的折中。更小的模型训练和部署更便宜，但在长记忆注入、复杂多轮表达和细腻措辞上可能余量不足；更大的模型可能有更高上限，但会显著增加训练、推理和实验复现成本。

项目的目标不是证明 14B 是最优规模，而是在单卡 QLoRA 条件下验证方法设计。换成更大基座后，所有训练和记忆实验都需要重新跑，不能把现有数字直接外推。

### Q21. LoRA 的原理是什么？项目中怎样使用？

LoRA冻结原始权重 $W_0$，只学习一个低秩增量：

$$
W=W_0+\frac{\alpha}{r}BA
$$

其中 $r$ 远小于原矩阵维度。直觉是预训练模型已经具备大部分通用能力，下游任务只需要在较低维子空间中调整行为。项目使用 r=8、alpha=16，并覆盖注意力和前馈相关投影，以较小训练参数完成领域适配。

推理时的 LoRA scale 是另一层运行时乘数。咨询输入使用较高强度，闲聊使用较低强度；改变 scale 不需要重新训练，而改变 r 或 alpha 需要重训。回答时必须把这几个概念区分开。

### Q22. QLoRA 和 4-bit 量化解决了什么？会不会损失效果？

QLoRA把冻结的基座权重以 4-bit 形式存储，只训练 LoRA 参数，从而显著降低显存占用。NF4等量化形式针对预训练权重分布设计，在存储成本和误差之间取得折中；计算时通常仍会反量化到更高精度完成矩阵运算。

量化误差客观存在，项目没有做 bf16 全精度对照，所以不能声称完全无损。当前结论只是：4-bit QLoRA 使 14B 在单卡上可训练，并在现有指标上达到可接受效果。若资源允许，应比较 4-bit、8-bit 和 bf16 LoRA 的稳定性与生成质量。

### Q23. 这些训练超参数是怎样确定的？

学习率从 PT 的约 $5\times10^{-5}$、SFT 的约 $2\times10^{-5}$ 到 DPO 的约 $5\times10^{-6}$ 逐步降低，因为越靠后的阶段越接近目标行为，更新应更保守。LoRA r=8、alpha=16 是在任务数据规模、单卡显存和表达能力之间的工程折中；DPO只训练一轮，也是在降低过拟合和偏好漂移风险。

这些参数有方法动机和开发集经验，但没有完成全面网格搜索，因此不能称为理论最优。更严谨的实验应报告 rank、学习率和 beta 的敏感性，并比较 unseen 数据和人工偏好，而不是只选择最高自动指标。

### Q24. 为什么使用 MacBERT 做咨询/闲聊分类，而不是让大模型自己判断？

这是一个相对明确的中文二分类任务，用 Encoder 模型比调用 14B 生成模型更快、更稳定，也更容易做阈值和错误分析。MacBERT双向编码整句，分类头直接输出 logits，适合短文本意图判断；使用大模型零样本分类会增加延迟，而且让同一个生成模型同时充当裁判和执行者，难以独立评测。

更重要的是，分类器职责被刻意限制得很窄：它只影响 LoRA scale，不决定是否检索记忆、是否写入历史，也不切换成完全不同的模型。因此即使出现误判，影响主要是语气强弱，而不是整个系统路径被错误关闭。

### Q25. 为什么不用两个独立 LoRA，而是调节同一份 LoRA 的 scale？

两个 LoRA 可以分别优化咨询和闲聊，但会带来数据切分、边界样本、适配器切换和版本管理问题。我们的目标不是把两类对话做成完全不同的任务，而是在保留共同中文对话能力的基础上调节倾听风格强度，因此使用一份 LoRA 加连续 scale 更简单。

咨询和闲聊之间本来就存在模糊边界，例如用户先闲聊后表达压力。连续强度比硬切两个模型更平滑。这个选择仍需要与双 LoRA 方案做对照才能证明更优，目前主要是工程和鲁棒性上的取舍。

### Q26. 为什么会话摘要要关闭对话 LoRA？

摘要的目标是压缩事实和时间线，而对话 LoRA 强化的是倾听、回应和安慰风格。如果摘要时仍启用较强 LoRA，模型可能把反映式倾听、安慰语或建议写入摘要，导致后续上下文把助手措辞误当成事件内容。

因此摘要使用裸基座和更低温度，强调保真与稳定；对话生成才启用 LoRA。这个设计体现了同一个基座在不同任务下可以选择性启用适配器，而不是所有模块都共享同一种风格。

### Q27. 训练数据如何清洗和避免泄漏？

SFT数据需要做重复样本清理、异常长度过滤、角色模板统一和低质量回复筛选。DPO prompt 与 SFT 按对话 signature 互斥，减少同一段对话既作为监督答案又作为偏好输入；评测中的 seen/unseen 也采用一致的签名规则，而不是简单按随机行切分。

这只能降低显式泄漏，不能完全消除主题相似和模板相似。意图分类数据还需要检查来源差异和长度捷径，避免模型只根据句子长短或特定词汇判断。回答时应明确“做了哪些防泄漏措施”和“仍然可能有哪些残余偏差”。

### Q28. BLEU 和 ROUGE 在这个任务中能说明什么，不能说明什么？

BLEU主要关注生成 n-gram 与参考答案的精确重合，ROUGE关注参考内容被覆盖的程度，ROUGE-L还考虑最长公共子序列。它们适合比较同一协议下模型输出与参考回复的接近程度，因此可以说明 Base 到 SFT 的领域对齐趋势。

但心理支持回复没有唯一正确说法。一个更自然、更简洁或更有倾听感的回复可能与参考文本字面差异很大，所以 BLEU/ROUGE不能直接等价为共情质量。它们是低成本、可复现的相对指标，而不是项目最终目标的完整测量。

### Q29. 为什么 DPO 后 BLEU-1 从 29.56 降到 27.91？这是否说明 DPO 失败？

不能仅凭 BLEU下降判断 DPO失败。SFT直接拟合参考回复，通常更容易达到较高字面重合；DPO优化的是 chosen 相对 rejected 的偏好，可能让回复更简洁、更多样或改变建议节奏，从而降低与单一参考的 n-gram 重合。项目中 DPO 的 ROUGE-1/2 并未同步明显下降，也说明不是简单的整体退化。

不过反过来也不能仅靠这个解释宣称 DPO成功。若要证明它减少说教和过早建议，需要人工盲评或经过校准的多维 judge。当前合理结论是：DPO改变了生成偏好，自动重合指标不足以完整评价它。

### Q30. 如果补一套更合理的回应质量评测，你会怎样设计？

我会先定义可观察维度，而不是笼统评价“是否共情”。例如：是否准确理解用户情境、是否承认情绪、是否过早提出建议、是否给用户继续表达的空间、是否出现模板化开场、在用户明确求助时是否提供了有针对性的回应。不同场景需要分层，包括单纯倾诉、明确求建议、信息不足需要追问、关系冲突和轻度闲聊。

评测可以采用随机打乱的成对盲评，比较 Base、SFT 和 DPO；至少两名标注者独立判断，并报告一致性和置信区间。LLM-as-judge可用于大规模初筛，但应通过少量人工标注校准，避免长度和位置偏差。

# 第三部分 长期记忆系统与检索路径

### Q31. 为什么需要独立的长期记忆系统？直接扩大上下文不行吗？

长上下文解决的是容量问题，但不自动解决选择问题。用户历史变长后，把全部对话放进 prompt 会增加成本，也会让无关经历和旧状态干扰当前回复；模型对长上下文中间部分的利用也可能下降。真正困难的是决定“当前问题需要哪几段历史”，而不是单纯把窗口做得更大。

长期记忆系统将全部历史保存在外部存储中，每次只选择少量与当前问题有关、时间上有效、彼此互补的证据注入。因此它更像上下文选择器和经历重建器，而不是无限扩展的聊天记录。

### Q32. Trace 和 Profile 分别存什么？为什么要分开？

Trace 是记忆主体，保存用户和助手的原始消息及其时间、会话位置和向量索引。它不在写入时改写用户内容，保证后续能够回到原始证据。Profile 是少量稳定事实的旁路，只允许身份、教育、地点和偏好等白名单字段，便于在不同问题下直接使用。

二者分开是因为信息稳定性不同。一次事件、一次情绪或一段关系状态应保留为可追溯经历，不应直接变成用户画像；而姓名、学校或明确表达的沟通偏好可以作为较稳定信息。这样的分层降低了短期状态被长期固化的风险。

### Q33. 为什么坚持保存原始 Trace，而不是写入时直接抽取事实？

写时抽取的优点是库结构简洁，但它会把模型理解提前固化。心理支持对话中的很多表达具有暂时性和语境依赖性，例如“我这次考砸了，感觉自己什么都做不好”。如果写入模型把它概括为“用户长期缺乏自信”，这个错误可能在之后多轮对话中持续出现。

原始 Trace 把可逆性保留下来：错误检索最多影响一次回答，原文仍可重新解释；写时错误摘要则会污染后续所有查询。我们的设计不是拒绝所有结构化信息，而是把复杂经历保留为原文，只对少量稳定事实开放 Profile。

### Q34. Profile 为什么使用严格白名单？如何避免模型乱写？

Profile的目标不是概括用户人格，而是保存少量跨会话稳定、容易核验的信息。允许的类别包括姓名、年龄等身份信息，学校、年级、专业等教育信息，家乡或常住地，以及用户明确表达的沟通偏好和稳定爱好。诊断标签、人格判断、瞬时情绪和单次事件不进入 Profile。

即使 LLM 抽取出了不合规字段，写入前仍会经过 schema 校验，不在允许类别中的内容无法落库。抽不到信息时允许返回空列表，不为了“让画像看起来丰富”强行生成。这个设计的核心是宁可少记，也不把不稳定推断变成长期事实。

### Q35. 请完整讲一遍当前长期记忆召回流程。

当前用户问题先进入 Memory Planner。简单问题走 direct，复杂问题可以拆成最多若干子查询。每个 Planner 查询分别进行 BGE-M3 Dense top-50 和字词法 BM25 top-50 召回；两路结果取并集并用 RRF 融合，形成 top-40 anchor 候选。

随后使用 Cross-Encoder在 anchor 层精排。CE 查询集合包括原始用户问题和 Planner 查询；原始问题保留整体人物、事件和限定条件，子查询覆盖不同证据目标。Coverage selection保留原始问题的高分候选和每个子查询的高分候选，去重后补齐到 12 个 anchor。

这些 anchor 在各自所属会话内进行自适应扩窗（余弦连续性），同一会话中按位置重叠连通分量合并并硬保留锚点。最后按 CrossEncoder 分数选择最多 12 个经历窗；先按 CE 装入 token 预算（超限跳过继续），再按消息记录时间升序格式化，与 active Profile 一起注入生成模型。时间不参与召回打分。

### Q36. Memory Planner 的 direct 和 split 分别适合什么问题？

Direct适合检索目标单一的问题，例如“我之前有没有提过物理考试”或“我更喜欢怎样的安慰方式”。Planner可以把口语化问题改写成较短、实体明确的检索表达。Split适合一个问题同时要求多个对象、阶段或事实槽位，例如“我和小林的关系怎么变化，现在是什么状态”，可以拆成关系变化过程和当前状态两个查询。

Planner的价值是提高召回覆盖，不是替代后续排序。拆分数量受到限制，失败时可以回退到简单查询，避免生成过多宽泛子问题导致候选池膨胀。

### Q37. 为什么 split 初召回主要使用 Planner 子查询，而 CE 又加入原始 query？

这两个阶段承担的职责不同。初召回阶段需要把复杂问题分成更清晰的检索目标，因此使用 Planner 子查询分别做 Dense/BM25 搜索，可以提高每个证据方向的覆盖；如果仍然只用一个很长的原始问题，多个语义目标会在一个向量或一个词法查询里相互稀释。

但 Planner改写可能省略地点、否定词、时间或人物限定，所以 CE阶段重新加入原始问题。原始 query 不负责再次从全库找候选，而是在已有候选中检查其是否符合完整问题；子查询判断候选是否支持某个局部目标。这个设计既利用拆分能力，又保留原始语义约束。它并不能完全消除 Planner漏召，因此仍需通过召回消融和失败样本评估这一取舍。

### Q38. Dense 和 BM25 的差别是什么？为什么两者都需要？

Dense把查询和消息分别编码成向量，用余弦或内积衡量语义相似度，擅长处理同义改写和口语转述。例如“最近有点扛不住”和“压力很大”字面不同，但向量可能接近。BM25基于词项出现和逆文档频率，擅长人名、课程名、公司名、地点和数字等精确线索。

两者的失败模式互补。Dense可能把语义相似但人物不同的事件召回，BM25可能因为没有完全相同词汇而漏掉转述。因此项目先分别召回，再通过 RRF融合排名，而不是只依赖单一路径。

### Q39. RRF 是怎样融合 Dense 和 BM25 的？为什么不用直接加原始分数？

Dense余弦分数和 BM25分数不在同一个量纲，直接相加需要归一化和人工权重。RRF不使用原始分数，而根据候选在每条排名列表中的位置计算倒数排名贡献：

$$
S_{\mathrm{RRF}}(d)=\sum_r\frac{1}{k+\operatorname{rank}_r(d)}
$$

如果一条消息同时被 Dense 和 BM25排在前面，两路贡献会叠加；只在一路出现时，另一路贡献为零。项目对两路 top-50 的去重并集计算 RRF，再保留 top-40 给 CE。这种做法避免了分数量纲校准问题，并优先保留被多路认可的候选。

### Q40. 为什么 Dense 和 BM25 各召回 50 条，RRF 后保留 40 条？

这些参数反映了召回率、CE成本和当前用户历史规模之间的折中。两路各 top-50 的并集通常大于 50，小于等于 100，能够保留语义和词法两种不同来源的候选；RRF top-40 进行一次温和截断，让后续 Cross-Encoder仍面对较大的、相对“脏”的候选池，而不是在十几个已经很干净的候选上重复排序。

Top-40到 coverage top-12 是真正的精排阶段。参数不是理论常数，需要在候选召回率、最终 QA、时延和 GPU批处理上做敏感性分析。当前数值来自开发过程中的稳定折中，不应描述为普遍最优。

### Q41. Cross-Encoder 和 Dense 召回本质上有什么不同？

Dense是双塔结构，查询和候选分别编码，历史消息向量可以提前计算，因此适合从大库快速找到几十条候选。代价是查询和候选在编码时没有逐 token 交互，否定、条件和细节关系可能被压缩在单一向量中。

Cross-Encoder把 query 和 anchor 拼接后共同编码，可以让两边 token直接注意，通常更适合在小候选池中做细粒度匹配。但它无法预计算候选，每一个 query-anchor 对都需要前向计算，所以只能用于精排。项目的分工是 Dense/BM25广泛召回，CE从 RRF top-40 中选择更合适的种子。

### Q42. 为什么把 CE 放在扩窗之前，而不是对完整经历窗精排？

我们最初也尝试过扩窗后对 window 使用 CE，直觉上完整上下文应该更容易判断。但实验发现这种做法效果明显下降。一方面，经历窗更长，关键句可能被上下文稀释或截断；另一方面，通用 CE优化的是单个 query-passage 相关性，而最终任务需要多窗口覆盖、状态更新和时间顺序，单窗高相关并不等价于集合层面的高价值。

因此最终让 CE既负责“哪些消息值得作为扩窗种子”，也直接决定最终 Top-k；对象是较短的 raw anchor。扩窗由 Stitch 负责（比较用命中 chunk，注入用完整消息）。这样模块职责更清楚，也与负结果一致。

### Q43. 为什么 CE 要同时使用原始问题和 Planner 子查询？

单一原始问题可能包含多个检索目标，CE全局 top-k容易被其中最显眼的目标占满；只使用 Planner子查询又可能因为改写而丢掉完整事件约束。多查询 CE同时保留两种视角：原始问题检查整体相关性，子查询分别检查某个阶段、对象或事实槽位。

例如问题要求“关系经历了什么变化，现在怎样”，一个子查询寻找变化过程，另一个寻找最终状态；原始问题则保证候选仍然围绕同一个人物和事件。每条 anchor分别获得不同查询下的 CE分数，后续不是简单平均，而是按查询覆盖来选择候选。

### Q44. Coverage selection 是怎样工作的？为什么不直接取 CE 全局 top-12？

全局 top-k可能被一个容易的子查询占满。例如“最初状态”相关消息数量多、字面也更强，最终状态和中间转折可能全部被挤出。Coverage selection先保留原始问题的若干高分候选，再为每个 Planner子查询保留若干候选，去重后按最大 CE分数补齐到 12。

当前实现大致是原始问题 top-4、每个子查询 top-3，并保证每个查询至少有候选。它仍然使用纯 CE排序，没有把 CE与 RRF数值混合；coverage只是控制最终候选集合的组成。这个机制的目的不是人为保证答案，而是避免多目标问题被单一排序目标垄断。

### Q45. 多查询 Anchor CE 的计算复杂度是否过高？

CE计算量大致与“查询数乘候选数”成正比。RRF保留 40 个 anchor，Planner子查询数量有限，再加原始问题，最坏通常是一百多组 query-anchor 对；模型支持批处理，因此在 GPU上属于可控的精排规模。相比对全部历史或所有扩窗后长窗口运行 CE，这个成本低得多。

后续只对 12 个 anchor做 Stitch，也控制了数据库读取和窗口构造成本。实际部署时应记录 Planner查询数、CE pair数、批次耗时和端到端首 token延迟，并在简单 direct问题上减少不必要的子查询。

### Q46. 窗级 CE 为什么失败？你从这个负结果中学到了什么？

第一次硬替换窗级内容分时，CE分数尺度与原分数不一致，并与 MMR负分早停发生交互，平均注入窗口从约六七个降到约两个，造成明显的证据不足。修复窗口数量、恢复 recency 和 week 后，效果仍未超过旧路径，说明不仅有工程尺度问题，还存在目标不匹配。

通用 CE擅长判断一个窗口与问题是否相关，但长期记忆评测还要求最新状态、跨会话互补和时间阶段覆盖。旧状态可能与问题高度相关，却不是当前答案；中间转折单独相关性较弱，却是完整时间链不可缺少的证据。这个实验促使我们把 CE前移，并把集合效用留给时间感知选择器。

### Q47. 自适应扩窗具体怎样工作？

每个 CE选出的 anchor只在所属 conversation内向前后扫描。候选消息如果与 anchor或当前窗口保持较高语义相似度，就加入窗口；对于“后来我还是去了”“她终于同意了”这类短承接句，还允许在位置相近且共享实体启发式特征时加入。扩展受最大跨度、最大消息数和连续 miss次数约束。

可以概括为：

$$
\operatorname{keep}(c)\iff \cos(c,a)\ge\tau\;\lor\;[\operatorname{dist}(c,W)\le d\land \mathcal E(c)\cap\mathcal E(W)\neq\emptyset]
$$

它与固定左右各取若干条的区别是，不同经历得到的窗口长度可以不同；主题连续时扩得更长，出现明显转题时尽早停止。

### Q48. 为什么扩窗之后还要 Merge？

同一段经历附近可能有多个 anchor，例如用户先说“准备退赛”，几条消息后又说“老师让我再考虑”。它们分别扩窗后往往产生大量重叠。如果不合并，后续 Top-k 会面对多个几乎相同的窗口，浪费候选数量和 token预算。

Merge 在同一 conversation 内按消息位置重叠连通分量合并（纯相邻不合并），硬保留全部 CE 锚点，只裁剪邻居。它不建立跨会话的显式因果链，只减少同一事件内部的重复。跨会话连续性由全局召回多个窗口与时间有序注入共同提供。

### Q49. CE Top-k 在最终选择中做了什么？

它只按 CrossEncoder 分数（必要时用 RRF fused 分兜底）选出最多 12 个经历窗（与 CE 锚点上限对齐）。时间衰减、新近性奖励、周桶奖励和 MMR 去冗余都已从正式读路径移除。选出的窗按 CE 相关性装入 token 预算（超限跳过并继续尝试后续短窗），再按消息记录时间排序展示；时间只影响展示与日期标签，不改变“选中谁”。

### Q50. 为什么不再做记忆衰减和使用强化？

正式读路径已改为 CE Top-k：相关性由 CrossEncoder 直接决定，不再用窗强度衰减或使用强化去调节排序。旧表 `memory_window_strength` 可暂留以免迁移，但产品路径不再读写它参与选窗。日期标签使用配置时区下的消息记录时间，记忆块内另给「当前日期」作为相对时间基准，并说明记录时间不是事件发生时间。

### Q51. 系统如何降低 stale，也就是旧状态干扰？

第一层是检索目标：Planner和多查询 CE尽量找出与“当前”“后来”“最终”等问题限定相关的 anchor。第二层是窗口选择：按 CE 分数取 Top-k，让与当前问题最相关的经历进入最终集合。第三层是注入组织：选中的窗口按消息记录时间升序排列，并标注「记录于」日期与「当前日期」，使模型能看到状态变化；系统明确说明记录日期是发送时间而非事件发生时间。

归档消融中（旧 MMR 路径）移除相对新近性后，QA下降、staleness明显上升，说明查询时如何组织近期证据曾是一阶因素。需要强调的是，旧经历仍然保存在库里，用户问“当时怎么想”时仍可召回；系统降低的是旧状态被误当成当前状态的概率。

### Q52. 最终记忆以什么形式注入？还会构造显式记忆链吗？

当前版本不再构造带 chain_id 的显式跨会话记忆链。系统选择来自多个 conversation的经历窗口，按最早消息时间排序，格式化为“相关经历证据”；每条用户消息带日期和来源标识，anchor可以被标记，Profile单独放在稳定信息区域。

Formatter只注入用户原始表达，不把助手话轮作为事实证据；超出 token预算时优先保留完整相关行，必要时对超长单条消息做局部截取。跨会话关系最终由时间有序的多窗口证据和生成模型共同理解，而不是预先给出确定的因果链。

### Q53. 为什么入库包含 assistant 消息，最终注入却只保留 user 消息？

Assistant 消息仍可写入 Trace 以便会话完整性与 Profile 抽取，但 Dense/BM25/ANN 与 CE 候选只保留 user；最终注入也只渲染用户原文。经历证据以用户表述为准，避免助手长回复占用召回名额。

最终注入时只保留用户消息，是为了避免把模型过去的推测、复述或建议当成用户事实，也能在有限 token预算下优先保存最可靠证据。这是“存储完整上下文，使用高可信子集”的不对称设计。

### Q54. 为什么不用会话摘要直接代替长期 Trace？

摘要适合压缩近期上下文，但不适合成为唯一长期证据。摘要是有损且不可逆的，早期对事件的概括可能忽略后来才重要的细节；同一段原文面对不同问题，需要提取的重点也不同，写入时很难提前知道未来会问什么。

因此项目将摘要用于短期上下文管理，将原始 Trace用于长期检索。查询时根据当前问题选择和重建经历，既保留原始证据，也避免每轮把全部历史塞进 prompt。

### Q55. 为什么不使用知识图谱或 GraphRAG 表示个人经历？

图结构适合相对稳定的实体和关系，例如课程先修关系、组织结构或知识库事实。但个人心理对话中大量信息是过程性的、时间性的和语境依赖的。把“我现在不想参加比赛”抽成固定三元组，仍然面临写时判断和过期状态的问题。

图方法不是没有价值，未来可以用于稳定人物关系、事件实体和时间链接；但当前核心问题是先减少写时误归纳，并保留原文可追溯性。因此我们优先采用经历窗口，而不是增加一层更强的结构化推断。

### Q56. 当前记忆系统最容易在哪些场景失败？

第一类是需要精确时序链的题。系统能找出多个相关窗口，但不一定完整恢复每个阶段和因果关系。第二类是极短、指代强的关键事实，如果 anchor本身信息弱，可能在 CE阶段被排低；coverage降低了风险，但没有彻底消除。第三类是同名人物、同地点和相似事件反复出现时，Dense、BM25和 CE都可能混淆。

此外，Planner改写错误、长用户消息被截断、候选库规模扩大后的延迟和多语言表达也需要专项评估。回答失败边界时，我会把它们对应到具体阶段，而不是笼统归为“模型幻觉”。

# 第四部分 评测、消融与研究判断

### Q57. 记忆评测数据是怎样构造的？为什么使用合成长期对话？

记忆评测需要同时知道用户历史、问题答案、当前有效状态和哪些内容应记或应忘。真实长期心理对话很难获得完整授权和细粒度金标准，因此项目构造了多用户、多会话、跨主题和状态更新的校园长程数据，并为每个用户设置 recall、context、preference、current_state、cross_session 和 temporal 等探测题。

合成数据的优点是可以精确控制同名实体、旧状态、干扰事件和跨会话证据，也便于 ER 与对照方法在完全相同的对话流上逐轮写入。缺点是语言和事件分布可能比真实用户规则，结果只能说明受控协议下的相对性能，不能直接外推到真实长期使用。

### Q58. 什么是固定 reader 的同协议对照？为什么重要？

两种记忆方法接收完全相同的历史对话，在各自的库中写入和检索；到测试问题时，使用同一个固定 reader，只把“该方法召回的记忆块 + 同一道问题”交给 reader回答。这样 reader的知识和推理能力保持不变，最终差异更可能来自记忆形态和读路径。

如果 ER使用更强生成模型、对照方法使用更弱模型，就无法判断提升是记忆还是答题能力造成的。固定 reader是这组实验最重要的内部效度设计之一，但仍需承认 reader自身会产生判断误差。

### Q59. QA、staleness 和内容 F1 分别衡量什么？

QA是固定 reader对测试问题的正确率，反映最终记忆是否足以支持回答。Staleness专门统计当前状态类问题中，系统是否错误依赖旧状态，越低越好。内容 F1将记忆库或注入内容与应记、应忘金标准对齐，综合考虑漏记和误记，反映库是否完整且干净。

三者不能互相替代。QA高不代表没有旧状态，只可能是 reader克服了噪声；F1高也不保证多窗口组合后一定答对；staleness只关注状态更新子集。因此项目同时报告三项，而不是只挑一个最好看的数字。

### Q60. 当前最重要的记忆实验结果是什么？

在 all_50 的固定 reader协议下，ER的 QA约为 90.8%，staleness约为 6.9%，内容 F1约为 0.602；写时抽取对照分别约为 68.7%、46.6% 和 0.400。这个结果表明，在当前合成长程数据上，原始 Trace加查询时重建更容易保留完整证据，也更不容易让旧状态影响当前回答。

需要限制结论范围：这是离线受控协议，不是线上用户满意度；对照不仅包含存储形态差异，也包含各自的读路径设计，所以更准确的说法是“整体记忆方案在同协议下表现更好”，而不是把全部差距归因于某一个单独模块。

### Q61. 相对新近性消融说明了什么？

在早期无 CE路径中，移除相对新近性后，QA约为 84.4%，staleness明显升高；加入相对新近性和周桶后，QA约为 92.2%，staleness下降。这说明长期记忆不能只按语义相关性选择，时间状态本身是需要建模的变量。

这个消融支持的是“时间感知选择器有独立价值”，不是证明当前 beta和 week bonus是理论最优，也不能直接解释 ER相对所有基线的全部提升。更完善的实验还应分别拆开 decay、recency 和 week，报告多数据集敏感性。

### Q62. Anchor CE 实验的结果怎样理解？

裸 Anchor CE在 hard数据上没有超过正式旧路径的总 QA，但 staleness和内容 F1有所改善。逐题分析发现，CE有时更容易找到最终状态句，却会把导师、地点、偏好等早期短事实排出 top-10。这个结果说明 CE不是无效，而是单一 query、单一全局截断不适合多目标长期记忆。

因此后续没有简单扩大 CE权重，而是把原始问题和 Planner子查询分别打分，用 coverage控制候选组成，并将保留数从 10增加到 12。这个迭代体现了“根据错误类型改变目标”，而不是继续盲调一个 epsilon。

### Q63. 目前实验规模是否足够？如何回答“样本太小”？

当前规模足以支持受控对照、逐题错误分析和模块消融，但不足以证明真实用户和不同领域上的普遍有效性。all_50共有 50个用户案例和 250道问题，比早期 30案数据更复杂，但仍然是合成数据，且参数在开发过程中多次观察过错误样本。

因此我会强调内部效度：同 reader、同问题、只换记忆方案，效应量较大；同时承认外部效度有限。下一步应冻结参数后构造独立 held-out用户历史，增加人工审核和不同 reader复核，再报告置信区间。

### Q64. 你们有没有统计显著性分析？

当前主表更强调效应大小和协议一致性，没有完整报告多随机种子和正式显著性检验。因此不能直接说“已统计显著”。对于逐题二分类结果，可以使用配对 bootstrap或 McNemar检验比较两种方法；对用户级案例可以进行 case-level bootstrap，避免把同一用户的多道题完全当成独立样本。

若把项目推进到论文，除了 p值，还应报告置信区间、效应大小和按题型分组结果。尤其 temporal和 judge边界样本数量较少，单个题目的变化可能带来较大比例波动。

### Q65. 反复看测试集是否会造成隐性过拟合？

会。我们在 all_30 和 hard数据上多次分析错误，并据此调整 CE位置、候选数量和 coverage配额，这些数据更接近开发集，而不是完全独立测试集。即使没有直接针对答案写规则，反复观察失败类型也会影响设计。

更严格的流程是：用开发集完成参数选择和消融，冻结代码后只在一批新的 held-out用户历史上跑一次主结果。当前文档应将现有数字称为统一基准或阶段性结果，而不是最终泛化结论。

### Q66. LLM reader 或 Judge 会不会带来评测噪声？

会。Reader可能在证据充分时仍答错，也可能凭常识猜对；Judge对“答案是否足够完整”的边界也可能不稳定，尤其 temporal问题中，回答包含起点和终点但缺少中间阶段时，不同判定会有差异。

因此错误分析需要查看实际 memory block和模型答案，区分“证据没召回”“证据召回但 reader没用”“答案基本正确但 judge过严”。更稳妥的做法是对争议样本进行人工复核、使用多个 judge或让 judge输出结构化理由，并报告一致性。

### Q67. 为什么选择写时抽取方法作为主要基线？还需要哪些基线？

主要研究假设是“复杂个人经历在写入时被压缩和归纳，容易造成信息损失和错误固化”，因此写时抽取方法是最直接的竞争假设。固定 reader后比较两种记忆方案，可以观察原始 Trace和查询时重建是否更适合当前场景。

仍然需要更多基线，包括直接长上下文、固定邻域扩窗、无 Stitch的原文 top-k、会话摘要型记忆、纯 Dense、纯 BM25和不同 reranker。基线不是越多越好，应分别对应“是否需要检索”“是否需要经历重建”“是否需要自适应边界”“是否需要时间建模”等问题。

### Q68. 项目最有价值的负结果是什么？

最有价值的是窗级 CE没有提升，甚至明显下降。它迫使我们区分“单段文本与问题的相关性”和“多段长期证据对最终回答的集合效用”。更强的神经排序器并不自动适合所有阶段，尤其当任务还涉及旧状态、时间覆盖和多窗口互补时。

另一个重要负结果是裸 Anchor CE总 QA略降，但 staleness和 F1变好。它揭示了纯 top-k精排在短事实和多目标问题上的召回损失，并直接推动了 coverage selection。负结果让最终架构更有因果依据。

### Q69. 什么实验结果会让你承认当前方法不成立？

如果在冻结参数、独立 held-out数据和多个 reader条件下，ER不再优于写时抽取，或者优势只存在于某个合成模板；如果人工检查发现原始 Trace虽然召回更多，却导致明显更高的隐私暴露、噪声和错误引用；或者在相同效果下，延迟和存储成本远高于更简单方法，那么当前主张就需要收缩。

模型适配侧，如果人工盲评不能确认 SFT/DPO减少过早建议和模板化，只是提高了与训练文本的字面相似度，也不能继续声称回应策略得到改善。一个研究假设必须允许被证伪，而不是所有结果都能解释成成功。

### Q70. 如果重新做一轮实验，你最优先补什么？

第一优先是回应行为层的人工盲评，因为目前这一部分证据最弱。第二是冻结参数后的独立长期记忆测试集，避免反复看开发集带来的隐性调参。第三是 temporal专项实验，明确区分召回、时间排序和 reader推理各自的瓶颈。

若时间只有一周，我会先完成一组小规模但高质量的人工成对评测，同时对记忆主表做 case-level bootstrap和争议题人工复核。相比直接换更大模型，这些实验更能补强现有结论。

### Q71. 如何保证实验可复现？

对话侧需要固定数据签名切分、checkpoint、chat template、解码参数和随机种子；记忆侧需要固定用户历史、reader、召回 top-k、CE模型、Stitch参数、时间项和 MMR设置。每次运行保存完整配置、逐题答案、注入 memory block和错误日志，而不是只保存一个 summary。

代码中不同实验路径应通过配置开关切换，避免临时手改造成不可比。若面向公开复现，还应提供依赖版本、模型下载说明、数据库初始化脚本和一键评测命令，并说明硬件差异可能影响延迟但不应改变逻辑结果。

### Q72. 如果老师随机打开一条错误样本，你如何现场分析？

我会沿数据流逐层检查。首先看正确证据是否存在于历史库；其次看 Dense/BM25和 RRF是否召回；然后看 CE coverage是否把关键 anchor保留；再看同消息 chunk 折叠与 Stitch是否扩到包含答案的句子，CE Top-k是否漏掉高相关窗；最后确认 memory block有证据时 reader是否仍答错。

只有定位到具体层，才能提出对应改进。例如召回漏失需要改查询或候选规模，CE误杀需要改 coverage，Stitch缺上下文需要检查边界，reader错误则不应继续修改检索系统。这样的现场分析比笼统说“模型幻觉”更可信。

# 第五部分 工程实现与系统复杂度

### Q73. 请从一次用户请求开始，完整讲一遍系统如何运行。

用户消息到达后，系统读取当前会话和用户设置。MacBERT判断这一轮更偏咨询还是闲聊，只用于选择 LoRA scale。若长期记忆开启，Memory Planner生成 direct或 split查询，随后完成 Dense/BM25、RRF、多查询 Anchor CE、coverage、chunk 折叠、Stitch、Merge和 CE Top-k，形成 memory block。

生成模型接收系统提示、近期上下文、会话摘要和长期记忆，使用对应 scale流式生成回复。生成完成后，回复落库；原始用户和助手消息写入 Trace，Profile抽取和摘要等非首 token关键任务可以在后台执行。最终实际注入的窗口才进行 usage reinforcement。

### Q74. 如果某个组件失败，系统怎样降级？

Planner失败时可以退回 direct查询；Dense或 BM25其中一路失败时，仍可使用另一条召回列表；CE不可用时可以回退到 RRF前若干 anchor；记忆检索整体失败或用户关闭记忆时，生成模型仍然依据当前会话回答，只是失去跨会话背景。Profile为空也是合法状态，不影响 Trace检索。

这种降级设计体现了模块解耦。MacBERT误判只影响语气强度，不关闭记忆；记忆组件故障也不应阻塞基本对话。工程上还需要在 trace中记录是否发生 fallback，否则看到正常输出时可能误以为所有模块都在工作。

### Q75. 当前方案的主要计算开销在哪里？

主要开销有三部分：生成模型的自回归解码、Planner的 LLM调用，以及多查询 Anchor CE。Dense检索使用预计算向量，BM25和 RRF相对便宜；Stitch和 Merge主要是数据库读取与向量相似度计算。CE最坏需要对原始问题和多个子查询分别处理 40个 anchor，但可以批量推理。

降低成本的方法包括限制子查询数量、direct问题不做不必要拆分、按候选长度动态 batching、减少 CE最大长度，并缓存会话消息和向量。复杂度是否可接受最终应通过 P50/P95延迟、GPU占用和首 token时间报告，而不是只看流程图模块数量。

### Q76. 单卡如何支持 14B模型、检索和其他任务？

14B基座使用 4-bit量化，主要加载一份 chat LoRA；咨询和闲聊通过 scale调节，不同时常驻多份大适配器。生成、Planner或其他需要大模型的任务在 GPU上进行调度，BGE、MacBERT和 CE相对更小，可以根据显存情况常驻或串行。

摘要和 Profile写入不必阻塞回复首 token，可以放在回复完成后执行。单卡设计的核心不是所有任务真正同时并行，而是控制常驻模型数量、使用量化和低秩适配，并把非关键写路径从用户等待链路中移出。

### Q77. 流式生成和消息落库怎样保证一致性？

流式输出时，前端逐步接收 token，但服务端应在生成线程中保留完整文本。生成正常结束后统一写入助手消息和相关指标；客户端中途断开不应直接丢弃已经消耗算力生成的完整回复，可以在后台完成后落库，用户重新进入会话时从历史中恢复。

需要区分“用户是否看到了完整输出”和“服务端是否生成并保存完成”，并记录生成状态。如果生产化，还要处理超时、取消请求、重复提交和事务一致性，避免同一轮被写入两次。

### Q78. 为什么当前使用 SQLite 和按用户索引？

当前系统是单机研究原型，SQLite便于快速实现消息、Profile、向量元数据和实验记录的一致存储，部署和复现成本低。向量检索按用户隔离，既减少候选规模，也避免不同用户历史混入；进程内缓存可以加速常用索引，但数据库仍是事实源。

如果用户规模和并发提高，需要迁移到更适合的关系数据库、分布式对象存储和向量检索服务，并增加索引更新、备份和一致性策略。方法层的原始 Trace和查询时重建可以保留，变化主要发生在基础设施。

### Q79. 系统如何保证不同用户的数据不混淆？

所有消息、Profile和向量记录都带用户标识，检索在查询层首先按用户过滤，再进行相似度排序。缓存和索引也应以用户或租户作为命名空间，不能依赖前端传入的会话 ID直接访问数据。写入、读取和删除操作需要在服务端完成权限校验。

实验环境中还应检查数据库初始化和批量评测是否为每个案例使用独立命名空间，避免上一位用户的向量残留影响下一位。长期记忆系统的准确性首先建立在数据隔离正确之上。

### Q80. 如果用户规模增长到十万，哪些部分需要重构？

需要重构的是存储、索引和调度。SQLite和进程内全量索引不再适合，需要分片数据库、近似最近邻服务、异步嵌入任务和更完整的缓存策略；CE和生成模型需要批处理、队列和多实例部署，Planner也可能使用更轻的路由模型或缓存。

可以保留的是方法逻辑：按用户隔离、原始 Trace、候选召回、anchor精排、经历扩窗和时间感知选择。规模化不是简单把 top-k调小，还要监控召回延迟、索引新鲜度、GPU排队和删除一致性。

### Q81. 为什么不让一个大模型端到端完成分类、检索、规划和生成？

端到端大模型看起来简单，但会把不同失败模式混在一起。分类和向量检索是高频、结构明确的任务，使用小模型或算法更快，也容易离线评测；生成模型适合处理自然语言表达，但不适合每次遍历全部历史。把所有环节交给一个模型还会增加延迟和不可控性。

模块化并不意味着越多越好，而是将不同计算形态放在适合的位置：Encoder做分类与表示，Cross-Encoder做小候选精排，规则和 MMR做集合控制，Decoder负责最终语言生成。每一层都能单独降级和消融。

### Q82. 当前工程距离真正稳定部署还缺什么？

首先是性能与可观测性，需要系统记录每个阶段的延迟、候选数量、fallback、token使用和错误率；其次是数据治理，包括删除一致性、备份、访问审计和敏感信息处理；再次是并发调度，单卡串行需要队列、限流和超时策略。

研究侧还需要把实验配置和线上配置严格区分，避免为了追求离线分数引入不可接受的延迟。当前工程能够演示完整链路和复现实验，但不能把它描述成已经完成大规模生产验证。

# 第六部分 与项目直接相关的基础知识

### Q83. Transformer 中与这个项目最相关的机制是什么？

生成模型使用 decoder-only Transformer和因果掩码，每个 token只能关注之前的上下文，按 $p(x_t|x_{<t})$ 自回归生成回复。PT和 SFT都建立在这个条件语言模型上，DPO则比较不同回复在同一条件下的相对概率。

MacBERT和 BGE属于 Encoder体系，可以双向利用整句信息，分别输出分类 logits和文本向量；Cross-Encoder同样是联合编码 query和候选，输出相关性分数。理解 Encoder、双塔和 Decoder的差异，才能解释为什么系统没有用一个模型包办全部任务。

### Q84. KV Cache 是什么？它与长对话有什么关系？

自回归生成每一步都需要过去 token的 key和 value。如果每生成一个新 token都重新计算完整前缀，会产生大量重复计算。KV Cache保存历史层的 key/value，新一步只计算新增 token，从而显著加速解码。

代价是缓存显存随上下文长度和生成长度增加，因此长期记忆不能无限注入。即使模型支持长上下文，过多历史仍会增加 KV Cache和首 token成本，这也是检索后只注入少量窗口的工程原因之一。

### Q85. Encoder、双塔、Cross-Encoder 和 Decoder 分别适合什么任务？

普通 Encoder双向读取输入，适合分类、序列标注和句子表示；双塔让 query和候选分别编码，候选向量可以预计算，适合大规模召回；Cross-Encoder把两者联合输入，匹配精度更高但不能预计算，适合几十条候选精排；Decoder按左到右方式生成自然语言，适合最终回复。

在项目中，MacBERT是分类 Encoder，BGE-M3是双塔嵌入，BGE reranker是 Cross-Encoder，Qwen3是 Decoder。这个分工是由任务和成本决定的，不是模型越大越适合所有环节。

### Q86. 什么是灾难性遗忘？当前训练怎样降低风险？

灾难性遗忘是模型在新数据上更新后，原有通用能力明显退化。项目通过 LoRA限制可训练参数空间，学习率逐阶段降低，DPO只训练一轮，减少对基座权重的大幅改变。PT、SFT和 DPO分阶段进行，也比一次混合强更新更容易观察问题。

不过项目没有系统评测通用能力退化，所以只能说设计上采取了保守策略，不能说已经解决遗忘。更完整的验证应在通用中文理解、知识问答和开放域对话基准上比较训练前后差异。

### Q87. 温度和 top-p 如何影响项目评测？

温度控制概率分布的平滑程度，越高输出越随机；top-p从高概率 token中选择累计概率达到阈值的集合。心理对话需要一定多样性，但评测又要求可复现，因此解码参数必须固定，并在比较 Base、SFT和 DPO时保持一致。

摘要、Profile抽取和 Planner更强调稳定与结构正确，通常使用较低温度；用户可见回复可以使用更开放的采样。不同解码设置下的绝对 BLEU和主观听感不能直接横向比较。

### Q88. 什么是 Lost in the Middle？为什么它支持检索式记忆？

Lost in the Middle指模型对长上下文中间位置的信息利用可能弱于开头和结尾。把几十次会话原样拼接不仅成本高，还可能让真正关键的历史落在不利位置，旧状态和无关内容也会共同干扰注意力。

检索式记忆先缩小证据集合，再按时间组织和控制 token预算，使每段证据更靠近生成输入的有效区域。它不能彻底消除长上下文问题，但比无选择地全量拼接更可控。

### Q89. MMR 为什么是贪心选择？它有什么局限？

MMR每一步选择“与查询相关性高、同时与已选内容不太相似”的候选，属于贪心近似。它计算简单，能在有限窗口数下减少重复，适合在线选择；但它不保证全局最优，也不真正理解事实槽位、因果关系或时间链。

因此项目在 MMR前加入相对新近性和周桶，尽量提供任务结构；仍然较弱的 temporal结果说明，简单去冗余不能替代显式时间推理。未来可以研究 listwise选择或状态演化建模，但需要证明收益能够覆盖新增复杂度。

### Q90. BM25 为什么适合抓人名、地点和数字？

BM25根据词项在当前文档中的频率以及在整个语料中的稀有程度评分。人名、地点、课程和数字通常在个人历史中出现频率较低，逆文档频率较高，因此当查询中出现这些精确词项时，它们能提供强匹配信号。

它的局限是对同义改写和省略表达不敏感，例如“那次答辩”与具体比赛名称可能没有词面重合。因此 BM25与 Dense结合比单独使用更稳。

### Q91. 这个项目中你具体负责了什么？

我会按可验证模块回答，而不是笼统说“整个项目都是我做的”。我能够完整负责和解释的部分包括：项目问题定义与统一叙事；PT、SFT、DPO数据组织和训练评测；MacBERT路由及 LoRA scale接入；Trace/Profile数据形态；Planner、混合召回、RRF、多查询 Anchor CE、coverage、Stitch、CE Top-k和格式化；固定 reader评测、消融和逐题错误分析；以及将这些模块接入可运行的对话原型。

基座模型、嵌入模型和 Cross-Encoder来自公开模型，部分基础算法和库也采用开源实现，我不会把它们说成自己发明。若有团队协作，应准确说明谁负责数据、前端或部署接口，以及我实际修改和验证了哪些部分。

### Q92. 项目中最困难、也最能体现你能力的问题是什么？

最困难的不是某个依赖安装，而是发现“更强的 reranker”为什么反而让系统变差。最初把 CE放在扩窗后替换内容分，QA明显下降。我们先通过平均注入窗数和日志定位到分数尺度与 MMR早停问题；修复后仍下降，说明还存在任务目标不匹配。随后把 CE前移到 anchor层，裸 CE又暴露出短事实被 top-k截断的问题，最终才形成多查询 coverage方案。

这段经历体现了我处理复杂系统问题的方法：先区分实现 bug和研究假设，再通过控制变量、逐题分析和模块位置调整形成新方案，而不是看到下降就简单换模型或调权重。

### Q93. 为什么选择读研？你希望在研究生阶段继续研究什么？

这个项目让我发现，把系统跑通和把研究问题证明清楚之间差距很大。比如自动指标不能直接证明倾听质量，合成长期数据也不能替代真实泛化评估；只有通过相关工作、实验设计和统计分析，才能把工程直觉变成可靠结论。我希望读研系统学习机器学习和 NLP方法论，并参与更规范的科研流程。

兴趣方向可以围绕对话系统、检索增强、长期记忆和模型对齐，但我不会把自己限制在一个具体应用。更重要的是学习如何定义问题、构造基线、设计消融和写出可证伪的主张，并根据导师课题完成方向迁移。

### Q94. 你的优点和需要改进的地方是什么？

我的优势是愿意深入分析失败样本，并把它们转化为可检验的修改。例如 CE的几轮迭代不是为了保住原架构，而是根据窗口数量、题型差异和证据缺失重新划分模块职责；这让我在工程实现之外逐渐形成研究判断。

需要改进的是早期容易投入较多时间把系统做得完整，却没有同步建立最严格的评测。例如回应行为层缺少系统人工盲评，部分参数也在开发集上反复观察后确定。我现在会更早写出假设、基线、失败标准和 held-out协议，避免“先做完再解释”。

### Q95. 面试结束前，你适合向老师问什么？

我会问与进入课题组后的研究过程有关、且官网难以直接查到的问题。例如：新生通常先复现组内工作还是直接参与现有课题；老师最近最希望解决的技术问题是什么；组内如何确定研究题目和评价阶段性进展；对硕士生更看重方法研究、系统实现还是两者结合。

## 8.1 研究动机、学术潜力与导师匹配

### Q96. 你为什么认为这个项目值得继续做成研究，而不只是一个课程作业？

我认为判断一个项目是否值得继续研究，不在于页面是否完整，而在于它是否暴露了可以被反复验证的矛盾。SoulHarbor 里最值得研究的不是“聊天机器人能不能跑”，而是两个稳定出现的矛盾：第一，模型越擅长给出完整答案，越可能在倾听场景中过早分析和建议；第二，记忆系统越积极地抽取和概括用户信息，越可能把短期状态错误固化成长期判断。这两个矛盾都不是换一个界面或多写几条 Prompt 就能彻底消失的，它们涉及训练目标、记忆表示和评测协议。

我已经做的工作是把工程现象收成可检验问题。例如，回应行为层不是只看“回复好不好”，而是比较 base、SFT、DPO 在同一数据和解码协议下的变化；记忆层不是只展示“能记住”，而是固定 reader，只替换记忆库与读路径，再看 QA、过时率和内容 F1。下一步如果读研，我希望进一步把这些结论放到更严格的人工评测、未参与调参的测试集和真实长期交互中验证。也就是说，当前项目已经具备研究问题和初步证据，但还没有把外部效度做完，这正是继续研究的空间。

### Q97. 你是怎样从阅读论文走到自己的设计，而不是看完就照着实现？

我阅读论文时会把内容拆成四层。第一层是作者声称要解决什么问题；第二层是核心假设，例如“写入时抽取能形成有效长期记忆”或者“偏好对能改善某类回复”；第三层是证据是否真的支持这个假设；第四层是这个假设换到我的场景后会不会失效。只有第四层出现明确冲突时，才有形成自己设计的机会。

例如，长期记忆中“写入时抽取并整理”在一般助手里很自然，但心理支持对话包含大量短期情绪和未完成事件，错抽取的长期代价更大。我没有简单否定抽取，而是把它转化为场景假设：Trace 尽量保存原始证据，把更强的理解放到查询时；稳定 Profile 则缩成窄白名单。随后再用固定 reader 对照和新近性消融去验证。这个过程不是换名词，而是从“别人为什么这样做”继续追问“在我的数据和错误代价下是否仍然成立”。

### Q98. 你如何把一个模糊的项目痛点变成可检验的研究假设？

我通常先把主观描述改成可观察的失败模式。例如“模型不够共情”太宽，我会拆成重复模板、过早建议、缺少追问、理性分析压过倾听等可标注行为；“记忆不好”也太宽，会拆成关键事实漏召、旧状态覆盖当前状态、跨会话证据不完整、相似事件混淆等问题。只有失败模式能被定位到具体样本，才能进一步提出模块和指标。

之后再写出一个可以被否定的假设。比如：“相对新近性能够降低旧状态干扰，但可能牺牲久远关键事实”；“Anchor CE 能清除混合召回噪声，但纯全局 top-k 可能损害多目标覆盖”。然后设计至少一个正向对照和一个失败检查，而不是只跑最终最好数字。对我来说，科研化的关键不是公式多，而是每个模块都对应一个明确的失败模式，并且有办法证明它没有解决、解决了一部分，或者带来了新问题。

### Q99. 你最强的证据是什么？最弱的证据是什么？

最强的证据是记忆侧的同协议对照和消融。固定 reader 后，只改变记忆库与读路径，可以比较 ER 与写时抽取基线的 QA、过时率和内容 F1；去掉相对新近性后，准确率和 stale 表现明显恶化，也能说明时间选择不是装饰。这类证据的因果归属相对清楚，因为答题模型没有一起变化。

最弱的证据是回应行为层对“共情更好”的证明。base 到 SFT 的 BLEU/ROUGE 跃升能够说明领域回复分布更接近训练语料，但 DPO 的目标是听感、建议时机和说教程度，单一参考的自动重合指标不能直接证明这些主观维度。当前更准确的说法是：训练链路完成、自动指标呈现预期趋势，但缺少系统的盲评与人类偏好胜率。老师问到时，我会主动把强证据和弱证据分开，而不是用一个数字覆盖整个项目。

### Q100. 如果实验结果与最初假设相反，你会如何处理？

我会先区分三种可能：实现有 bug、评测协议不匹配，或者假设本身错误。窗级 CE 的实验就是一个例子。最初直觉是 cross-encoder 应该比手工相关性更准确，但结果大幅下降。我们先排查分数量纲和 MMR 早停，发现平均注入窗数从约六七个塌到两三个；修复窗口数量和时间项后仍未超过旧路径，才确认不只是工程 bug，而是“单窗相关性”和“多窗时间覆盖”目标不一致。

因此负结果不会被删掉，而会改变后续设计。我们把 CE 前移到 anchor 层，再通过 Planner 多查询和 coverage selection 避免单一目标占满 top-k。这个过程说明我不会为了保住原故事而只挑最好跑次；相反，失败实验帮助缩小了模块应承担的职责。面试中把这条迭代讲清楚，通常比只展示终版更能说明科研能力。

### Q101. 你如何保证实验可复现？

可复现首先是协议固定，而不是只保存最终权重。对话侧需要固定数据切分、去重签名、模型 checkpoint、解码温度和 top-p；记忆侧需要固定 reader、数据集、召回参数、窗口上限、时间项和随机种子。每次实验都保存配置、运行目录、注入 memory block 和逐题结果，才能在指标变化时回到具体样本，而不是只看一个 summary。

其次，代码层要允许模块开关，而不是每次手改逻辑。例如窗级 CE、Anchor CE、recency、week bonus、MMR 早停等都应通过配置切换，方便形成真正可比的消融。最后还要区分“同机器可复现”和“跨环境可复现”：模型路径、依赖版本、显存约束和数据库初始化都需要说明。当前项目已经具备运行记录和配置入口，但若面向论文，还应补多随机种子、容器化环境和自动化复现实验脚本。

### Q102. 你是否可能在反复看测试集后把参数调到测试集上？

有这个风险。我们在 `all_30` 和 hard 集上多次做错误分析，再确定 CE 保留数、coverage 配额和时间参数，这些数据就不再是完全独立的最终测试集。即使没有把答案直接写进规则，反复观察错误类型也会形成隐性调参。因此当前数字更适合称为统一开发基准或阶段性主表，而不能完全等价于未见数据上的泛化结论。

更严格的做法是冻结方法和参数后，再构造一批不参与设计的 held-out 用户历史，由另一位标注者独立生成或审核，并只允许跑一次主结果。同时把参数敏感性单独放在开发集上完成。若资源有限，至少可以用 case-level bootstrap 估计区间，并把“开发集结果”和“最终保留集结果”明确分开。老师如果提出这一点，我会承认当前证据的边界，并给出清楚的改进协议。

### Q103. 你如何判断应该继续加模块，还是应该停止？

我的判断标准不是“还能不能想到模块”，而是新模块是否对应一个尚未解决、且能被独立测量的失败模式。比如 Anchor CE 对应混合召回候选中的高混淆噪声，coverage selection 对应单一 CE top-k 造成的多目标证据遗漏；这两者职责不同，所以可以同时存在。相反，如果再增加一个与 CE 同样判断 query–window 相关性的打分器，只是换模型或叠权重，就很可能是重复建模。

第二个标准是边际收益与解释成本。一个模块若只提升一两道题，却增加大量超参和线上分支，应该优先考虑删掉或只保留为实验开关。当前主链已经到“Planner—混合召回—RRF—多查询 Anchor CE—Stitch—CE Top-k”的复杂度，再往后增加图结构、状态机或第二个神经重排器，需要非常强的专项证据。我会把能解释、能消融、能稳定复现放在追求模块数量之前。

### Q104. 你的数学和计算机基础如何支撑这个项目？

数学上最直接的是线性代数、概率统计和优化。LoRA 用低秩矩阵表示参数增量，向量检索依赖内积、余弦和归一化，DPO涉及对数概率与 sigmoid 形式的偏好损失，MMR则是在相关性与相似性惩罚之间做贪心优化。概率统计还用于理解训练损失、抽样解码、置信区间和显著性，而不是只背公式。

计算机基础上，数据结构和数据库关系到消息索引、去重、时间排序和按用户隔离；操作系统与计算机体系结构帮助理解显存、量化、并发和 KV Cache；软件工程则体现在配置管理、实验日志、降级路径和模块边界。老师若从成绩单追问某门课程，我会先讲课程核心概念，再落到项目里的具体使用，不会只说“学过”。

### Q105. 如果导师的主方向与你现在的项目不完全一致，你能接受吗？

可以，但不是无条件说“什么都行”。我更看重的是问题方法是否有迁移空间，例如表示学习、检索增强、对齐、时序建模和系统评测都能迁移到不同应用。SoulHarbor 是我目前最熟悉的载体，不代表研究生阶段只能继续做心理对话。如果导师方向相近，我可以把已有经验快速转化；如果方向不同，我也愿意先复现组内工作，理解其评价标准，再寻找我能贡献的交叉点。

我会避免两种回答：一种是只说“我就想做这个”，显得适应性差；另一种是“老师安排什么都行”，显得没有研究兴趣。更成熟的表达是：我有明确的能力积累和问题偏好，但理解研究生训练首先要进入导师和团队的主线，并愿意用一段时间完成方向迁移。

## 8.2 项目真实性、个人贡献与科研过程

### Q106. 请不要讲概念，直接从一次用户请求开始，把系统完整走一遍。

用户消息进入后，系统先读取当前会话、用户设置和近期上下文。MacBERT 判断这轮更偏咨询还是闲聊，它只影响同一份 chat LoRA 的推理 scale，不决定记忆是否开启。若用户开启长期记忆，Memory Planner 根据当前问题选择 direct 或 split，并生成一个或多个检索查询；每个查询分别做 BGE-M3 dense 与 BM25 召回，RRF融合后得到 anchor 候选。

候选随后由原始问题和 Planner 查询共同进行 Anchor CE 打分，coverage selection 保证整体问题和各子目标都有一定种子。选出的同消息多 chunk 折叠后，在所属会话内做自适应扩窗（比较用命中 chunk，注入用完整消息），重叠窗口合并后按 CE 分数取 Top-k。窗口先按 CE 装入 token 预算，再按记录时间排序，与确认后的 Profile 一起形成 `<memory>` 块，拼入生成提示；Qwen3-14B 使用对应 LoRA scale 流式生成。

### Q107. 这个项目中你真正写过和调过的代码是什么？

我会按模块而不是按“整个项目都是我写的”来回答。训练侧我负责或能够讲清数据清洗、PT/SFT/DPO 数据组织、LoRA 配置、训练启动与指标评测；路由侧包括 MacBERT 数据构造、训练与在线 scale 接入；记忆侧包括 Trace/Profile 数据形态、Planner、混合召回、RRF、Anchor CE coverage、Stitch、CE Top-k、格式化和评测脚本；工程侧包括对话接口、流式落库、SQLite 数据组织和实验日志。

基座模型、BGE-M3、MacBERT、cross-encoder 和对照库都是使用公开模型或开源实现，我不会把这些权重和基础算法说成自己发明。面试前必须做到：任何写在简历上的模块都能解释输入、输出、关键参数、失败案例和代码路径；若有队友负责的部分，要准确说出协作接口和自己实际承担的工作，不能为了显得贡献大而模糊归属。

### Q108. 你使用过生成式 AI 辅助编码吗？怎样证明不是“让 AI 帮你拼出来的”？

可以诚实承认使用过代码补全、文档整理或调试建议，但辅助工具不能替代对设计和结果负责。判断我是否真正掌握项目，不是看每一行是否手敲，而是看我能否解释为什么这样设计、哪次实验失败、代码出错时如何定位、删除某模块会怎样，以及面对新约束能否修改方案。

我会举具体例子：窗级 CE 最初下降时，必须从注入窗数、分数量纲、MMR 早停和题型差异逐层排查，这不是生成一段代码就能自动得到的；后来把 CE 前移到 anchor 层、再加入多查询 coverage，也是根据逐题错误分析形成的。工具可以提高实现效率，但问题定义、实验判断和最终责任必须由我承担。若老师要求现场看代码，我应能从入口追到关键数据结构，而不是只会描述 README。

### Q109. 你遇到过最难定位的 bug 是什么？

一个典型问题是 CE 硬接管窗级相关性后，QA突然大幅下降。最初很容易归因于“模型不适合”，但日志显示平均注入窗口从约六七个降到约两个。进一步检查发现，旧内容分的量纲与 sigmoid 后的 CE 分数不同，而 MMR仍使用 `best_score < 0` 提前停止；相关性尺度变化后，候选很容易被过早截断。也就是说，表面上是模型效果问题，实际先有一个系统交互 bug。

修复早停并恢复时间项后，效果有所回升但仍低于旧路径，才说明还有任务目标不匹配。这个 bug 给我的经验是：复杂流水线中，替换一个分数不仅影响排序，还会影响阈值、停止条件和候选数量；评测下降时应先检查数据流和分布统计，再讨论模型能力。面试中讲这种“先找到工程原因，再保留方法结论”的案例，比只说解决了依赖冲突更有价值。

### Q110. 项目中哪一个重要决定是你后来推翻的？

我推翻过“写入时让模型抽取和总结全部长期信息更先进”这个想法。它的优点是库很整齐，但在心理支持场景中，一次低落或冲突可能被写成稳定性格和关系结论，错误会跨会话持续影响模型。我们后来把 Trace 改为原始对话证据，Profile只保留窄白名单，把更复杂的理解后置到查询时。

我也推翻过“cross-encoder 应该放在 stitch 后替代最终相关性”的设计。实验表明它更擅长单窗匹配，却会伤害多窗覆盖和时间状态。最终 CE只负责 anchor 选种子，经历重建和时间选择仍由后续模块承担。能够推翻自己最初偏好的方案，说明设计不是为了证明预设结论，而是由错误分析和消融推动。

### Q111. 这些 top-k、阈值和权重是怎么来的？会不会都是拍脑袋？

参数来源可以分为结构参数和任务参数。结构参数如 dense/BM25 top-50、RRF top-40、CE保留12、最终窗口6，主要由候选池规模、CE计算成本、Stitch 合并率和注入预算共同决定；它们应通过开发集上的候选覆盖、延迟和最终 QA 做敏感性比较，而不是只报一个点。Stitch 的 cosine 阈值、最大跨度和连续 miss 则关系到窗口完整性与噪声，需要在短句、长会话和主题转移样本上抽查。

时间项和 MMR 权重更偏任务参数。recency 与 week bonus 有明确消融支持，说明它们在当前协议里不是装饰；但 0.8、0.5 或 λ=0.7 仍然只是当前开发集上稳定的折中，不能说成理论最优。成熟的回答是：参数有动机、有开发集证据、有敏感性边界，但尚未完成大规模自动搜索或跨数据集验证。

### Q112. 为什么选择当前这些基线？还缺哪些基线？

当前最重要的基线是写时抽取式长期记忆，因为它与我们的核心记忆形态假设直接相反：一边在写入时理解和压缩，一边保留原始 Trace、查询时重建。固定 reader 后比较两者，能够回答“记忆库和读路径是否影响长期问答与 stale”。另外还需要内部基线，如纯 dense、纯 BM25、混合 RRF、无 Stitch、无时间项、无 CE或单 query CE，用于定位每个模块的增益。

仍然缺少的基线包括：直接长上下文、固定窗口 contextual retrieval、摘要型 episodic memory、不同 reranker 或更强 reader，以及没有记忆但提供当前会话摘要的简单方法。不是基线越多越好，而是每个基线应对应一个竞争假设。若写论文，我会优先补“固定邻域 vs 自适应扩窗”“单 query CE vs coverage CE”“长上下文 vs 检索式记忆”三类，因为它们最直接挑战当前设计。

### Q113. 你认为项目里最有价值的负结果是什么？

最有价值的负结果是窗级 CE 没有带来提升。它提醒我们，通用 cross-encoder 的 query–passage relevance 并不等价于长期记忆中的集合效用。一个旧状态窗口可以与问题高度相关，却不是当前正确证据；一段单独相关性不强的中间经历，可能是完整时间链不可缺少的一部分。若只看单窗分数，反而会破坏多窗覆盖。

第二个负结果是裸 Anchor CE 在 hard 集上提高了 staleness 和内容 F1，却略降总体 QA，错误集中在导师、地点、偏好等短事实被 top-10 截断。这促使我们从单一全局排序改为原始问题加子查询的 coverage selection。负结果的价值在于揭示“模块放哪里、优化什么目标”比“是否用了更强模型”更重要。

### Q114. 如果只能保留一个核心模块，你会保留什么？

若必须在整个项目中只保留一项研究主张，我会保留“原始经历证据 + 查询时重建”的长期记忆形态，因为它最直接对应心理场景中错误固化的风险，也有相对完整的同协议对照与消融。微调链路虽然重要，但目前对共情收益的证据更多依赖自动指标，人工评测仍不足。

如果问题限定在读路径内部，我会保留相对新近性的时间感知选择，因为消融显示它对当前状态和过时率有明确贡献。这个回答不等于其他模块没用，而是说明在证据强度和核心假设之间，我知道哪一层最能支撑项目。

### Q115. 什么实验结果会让你承认当前方法不成立？

如果在冻结参数、独立 held-out 用户历史和多 reader 条件下，原文经历重建在 QA、staleness 或人工忠实度上不再优于写时抽取，而且延迟和存储明显更差，那么“写弱读强更适合该场景”的主张就需要收缩。类似地，如果人工盲评显示 SFT/DPO 并没有减少过早建议或说教，只是更像训练语料，那么回应行为层的主张也不能成立。

一个可证伪的方法必须提前说清失败标准，而不是任何结果都能解释。当前工作真正能支持的是离线协议上的相对优势，不是“所有长期对话都应该存原文”。如果未来证据反转，我会重新考虑混合写入、可撤销摘要或针对稳定事实的结构化抽取，而不是坚持现有架构。

### Q116. 如果老师随机打开一条错误样本，你应该怎样现场分析？

先判断错误发生在哪一层：正确证据是否进入初召回；是否被 RRF 或 CE 截掉；Stitch 是否扩到关键句；时间 MMR 是否选错；memory block 是否包含事实；最后 reader 是否仍答错。不要一看到最终答案错误就笼统说“模型幻觉”，因为前四层都可能已经丢失证据。

然后对照另一路方法的 memory block，看差异是“有没有证据”“证据顺序”“旧状态干扰”还是“同名实体混淆”。最后给出只针对该失败模式的改进，例如扩大 CE coverage、保留短事实、增加时间阶段覆盖或改 judge，而不是马上增加一个大模块。现场按数据流分析，会比背结论更能体现你真正跑过实验。

## 8.3 模型微调、训练与评测深挖

### Q117. 继续预训练、领域自适应预训练和 SFT 到底有什么区别？

继续预训练或领域自适应预训练仍然使用语言模型的因果预测目标，输入通常是领域文本，不要求明确的“用户—助手”指令格式。它改变的是模型对领域词汇、表达和共现分布的熟悉程度。SFT则使用成对的指令与目标回复，并通常只在助手部分计算损失，直接学习“给定上下文应该输出什么”。

在本项目中，PT使用心理问答文本适配中文心理语料分布；SFT学习倾听式回复和项目身份；DPO再在 SFT 基础上比较 chosen/rejected，调整多种可行回复之间的相对偏好。三者不是简单重复训练，而是从语言分布、任务映射到偏好排序逐层收窄。当前没有完整 PT ablation，因此我不会把 PT 必要性说成已严格证明。

### Q118. 为什么 SFT 通常只对助手 token 计算损失？如果对全序列都计算会怎样？

训练样本中，系统提示和用户输入是条件，助手回复才是要学习的目标。若对全序列都计算损失，模型会花大量容量复现固定系统词和用户原话，尤其在多轮数据中，输入长度可能远大于回复长度，导致真正的回答目标被稀释。只对助手 token 计 loss，可以把梯度集中在生成行为上。

这也涉及模板正确性。若 chat template、角色边界或 loss mask 写错，模型可能学会复读用户、输出角色标记，或者在推理时表现异常。因此训练数据检查不能只看 JSON 能否加载，还要抽样解码 token 与 mask，确认 system/user部分被屏蔽、assistant回复被完整监督。

### Q119. DPO 的基本假设是什么？在你们数据上可能在哪里失效？

DPO假设每个 prompt 下 chosen 相对 rejected 更符合目标偏好，并通过相对对数概率让策略更偏向 chosen，同时参考模型约束更新幅度。它不需要显式奖励模型，但把奖励信息隐含在成对偏好中。因此数据对是否可靠，是整个方法的关键。

在本项目中，rejected由外部模型按“敷衍、欠共情、说教”等失败模式合成。可能失效的地方包括：rejected 太差，模型只学会识别明显坏答案；chosen 并不总是优于 rejected；长度、格式或词汇成为捷径；偏好过于单一，牺牲信息性。我们用互斥、质检、低学习率和一轮训练降低风险，但若要强结论，还需人工抽检成对胜率和长度控制实验。

### Q120. 为什么 DPO 后模型可能变长、变短或出现复读？怎样诊断？

DPO优化的是相对偏好，如果 chosen 普遍比 rejected 长，模型可能把长度当作隐含奖励；反过来也可能学成过短。复读则可能来自偏好数据中高频开场、训练步数过多、KL约束太弱，或者解码温度与重复惩罚不合适。不能只看一个平均长度，需要按 prompt 分布检查长度差、重复 n-gram、模板词频和输出熵。

诊断时先比较 chosen/rejected 的长度与格式分布，再看 SFT 和 DPO 的生成长度、Distinct-n和常见前缀；若存在明显长度偏置，可以重采样、长度匹配、过滤模板或减小更新幅度。当前项目主要关注偏好失败模式，没有系统报告这些统计，因此回答应体现我知道风险和检查方式，而不是声称已经彻底解决。

### Q121. LoRA 为什么认为参数更新可以是低秩的？rank 越大越好吗？

LoRA把权重更新表示为两个小矩阵乘积，直觉是预训练模型已经具有大部分通用能力，下游任务只需要在较低维子空间中调整行为。rank决定这个更新子空间的容量。rank太小可能欠拟合，太大则显存、训练参数和过拟合风险增加，也逐渐失去参数高效的意义。

本项目使用 r=8、α=16，是在单卡、数据规模和任务类型下的工程折中，并非经过完整网格搜索证明最优。若老师追问，我会说明合理消融应比较不同 rank 下的训练损失、seen/unseen指标、生成多样性和显存，而不是只选最高 BLEU。LoRA的优势是低成本和模块化，不意味着任何任务都能无损替代全参。

### Q122. 为什么 LoRA 要覆盖注意力和前馈层？只调 Q、V 可以吗？

只调 Q、V 是常见轻量设置，因为注意力投影直接影响上下文聚合，参数少。但心理对话适配不仅是“关注哪里”，还涉及输出风格、语气、措辞和非线性变换，前馈层承载大量特征变换，因此覆盖更多注意力与 FFN 投影可能提供更充分的行为调整空间。

代价是可训练参数和显存增加，也更需要控制学习率。我们的设置是统一覆盖相关投影并使用小 rank，而不是证明“全覆盖一定最好”。如果做严谨消融，应比较 Q/V-only、attention-all、attention+FFN，在相同参数预算或相同显存下的效果。面试时要把“当前选择有动机”和“已证明最优”区分开。

### Q123. 4-bit 量化会不会明显损害训练和推理效果？

QLoRA通常将基座权重以低比特存储，在计算时反量化到更高精度，梯度只更新 LoRA 参数。它大幅降低显存，使14B模型能在单卡上训练。量化误差确实存在，尤其对异常值、极小差异和某些层敏感，但NF4等格式是针对近似正态分布权重设计的，实践中常能在成本和效果之间取得较好折中。

我们没有做全精度对照，所以不能声称量化无损。当前结论是：4-bit QLoRA满足资源约束，并在目标指标上得到可接受效果。若资源允许，应比较 4-bit、8-bit和 bf16 LoRA，检查训练稳定性、自动指标和生成质量；若差异很小，才能更有依据地说量化成本可接受。

### Q124. 为什么用单独分类器调 LoRA scale，而不是训练两个 LoRA？

两个 LoRA可以分别优化咨询和闲聊，但会带来数据分割、适配器切换、版本管理和边界样本不连续的问题。我们希望保留一份共同的中文对话能力，只调节倾听风格的强度，因此使用一个 MacBERT 分类器输出路由，再对同一份 LoRA 设置不同 scale。这样咨询和闲聊之间是连续调节，不是两个完全独立的模型。

更重要的是，分类器职责非常窄：只控制语气强度，不门控记忆和其他关键功能，因此误判代价有限。验证准确率很高，但开放域仍可能出错；把它限制成“旋钮”而不是“总控制器”，是工程鲁棒性设计。若以后发现两类任务在知识或行为上差异更大，才有必要比较多 LoRA、adapter fusion或连续回归 scale。

### Q125. 99.7%的意图分类准确率是否可信？会不会数据太简单？

这个数字只说明在当前构造、长度对齐的咨询/闲聊对照集上分类容易且模型拟合充分，不能外推到所有开放域对话。若正负样本来源差异大、模板明显或词汇线索强，即使按字长对齐也可能存在数据捷径。高准确率反而要求更仔细地检查混淆矩阵和真实边界样本。

更好的评测应加入“看似闲聊但包含情绪”“讨论心理学知识但不是求助”“先闲聊后转咨询”“反讽和隐含表达”等 hard cases，并报告 calibration 或不同阈值下的错误。由于该分类器只影响 scale，高准确率不是项目主贡献；我会把它作为低成本路由的可用性证据，而不是宣称解决了咨询意图理解。

### Q126. BLEU、ROUGE、人工偏好和 LLM-as-judge 各有什么优缺点？

BLEU和ROUGE便宜、稳定、可重复，适合比较输出与参考的词面接近程度，但心理支持回复存在大量合理改写，它们不能直接测倾听感、建议时机或安全性。人工盲评最贴近真实体验，可以按共情、信息性、说教程度等维度判断，但成本高、一致性和标注者背景会影响结果。

LLM-as-judge成本介于两者之间，适合大规模初筛和结构化维度评分，但可能受提示、位置、长度和模型偏好影响，不能默认等同人类。合理方案是：自动重合指标用于训练趋势，LLM judge用于多维诊断，少量人工盲评校准 judge。当前项目在后两层仍不足，所以答辩时应把自动指标的结论范围说窄。

### Q127. 如果要设计一套更合理的共情评测，你会怎么做？

我会先定义维度，而不是问“哪条更好”。维度可以包括是否准确理解情境、是否承认情绪、是否过早建议、是否有追问空间、是否出现套话、是否不必要地放大风险。每个 prompt 对 base、SFT、DPO 的输出随机打乱，由至少两位标注者做成对选择或Likert评分，并记录分歧。

样本要按场景分层：只想倾诉、明确求建议、信息不足需要追问、关系冲突、考试压力、轻度闲聊等，避免平均分掩盖不同策略。统计时报告胜率、置信区间和标注一致性，同时检查输出长度是否成为偏差。若资源有限，先做100到200条高质量盲评，也比只增加更多BLEU样本更能支撑DPO主张。

### Q128. 如果更换基座模型，哪些结论可以保留，哪些必须重做？

可以保留的是问题定义和模块职责：倾听策略需要适配，长期记忆要处理原始证据、状态变化和跨会话覆盖。不能直接保留的是任何具体数字、最佳超参和训练结论。更强基座可能减少SFT收益，也可能让Planner、reader和CE表现变化；不同 tokenizer、上下文长度和指令格式还会影响数据处理。

因此迁移时要重新做至少三类实验：基座与SFT/DPO对照、同一记忆库下reader敏感性、关键参数和延迟。若只替换模型然后沿用旧数字，是不严谨的。成熟的说法是方法假设具有可迁移性，但证据必须随基座重新建立。

## 8.4 混合召回、Cross-Encoder 与长期记忆深挖

### Q129. Dense、BM25、RRF 和 CE 分别解决什么问题？为什么不能只留一个？

Dense把查询和历史消息分别编码为向量，适合召回同义改写和语义相近表达，但可能把“主题相似、实体不同”的消息排高。BM25依赖词项匹配，对人名、地点、数字和专有名词更敏感，但不擅长口语转述。RRF不直接加原始分数，而是对两路排名的倒数贡献求和，避免余弦和BM25分数量纲不可比。

CE把 query 和候选联合编码，适合在几十条候选中做细粒度交互判断，但不能对全库逐条计算。我们的分工是：Dense/BM25负责高召回，RRF融合并截断，CE只在 anchor 层精选种子，后续Stitch恢复完整经历，时间感知MMR决定最终集合。每一层解决不同错误，不是单纯叠加“更强相关性”。

### Q130. 为什么 Dense 和 BM25 各召回 50，RRF 后保留 40？

各取50是为了让两路都有足够覆盖，去重并集可能在50到100之间。RRF保留40是在召回覆盖与CE成本之间的折中：太小会在精排前丢掉单路独有的正确候选，太大则使多查询CE对数迅速增加。Planner最多几个查询时，40个 anchor 已经意味着上百个 query–candidate 对，但仍可批量处理。

这个数字不是理论常数。合理性要看RRF top-k的 gold evidence recall、CE延迟和最终结果。我们曾在较小数据上讨论全量RRF，但生产场景历史可能很大，不适合全库精确排序。当前50/40是开发集上的可用配置，最好再报告20、30、40、60等敏感性，以证明性能不是恰好卡在一个点。

### Q131. 为什么 CE 放在扩窗前，而不是对完整 window 精排？

扩窗后的window更完整，但也更长、包含助手追问和弱相关上下文，容易出现截断、长度偏置和语义稀释。更关键的是，window阶段的任务已经不只是“与query是否相关”，还包括当前状态、时间覆盖和与已选窗口的互补性。通用CE主要学query–passage相关性，不能自然替代这些集合目标。

我们实际做过窗级CE实验：即使修复分数尺度和窗数塌缩，仍明显低于旧时间感知路径。把CE放到anchor层后，它只负责从RRF候选里选出值得扩展的种子，符合短passage精排的训练形态；扩窗后的选择继续由时间与MMR负责。这个位置不是凭直觉选的，而是失败实验后形成的职责划分。

### Q132. 为什么 CE 输入用裸 anchor，不加前后文？

裸anchor让CE判断对象明确，输入长度一致，也避免相邻消息重复出现在多个micro-context中。上下文恢复由后面的Stitch负责，两个模块职责不重叠。若给每个anchor加前后消息，弱anchor可能因为邻居很相关而被抬高，轻微转题也可能污染判断。

弱点是“后来我还是去了”“她同意了”这类省略句单独信息不足。当前做法依赖Dense/BM25同时召回附近更完整的消息，或同一session中的其他种子被保留。是否加入micro-context应该作为消融：如果短指代样本的anchor recall显著提高且重复不严重，再考虑引入，而不是默认复杂化。

### Q133. 为什么 CE 同时使用原始问题和 Planner 子查询？

Planner子查询用于把复合问题拆成不同检索目标，例如“最初状态”“转折”“当前状态”，这样每个目标都有机会找到对应anchor。原始问题则保留完整人物、地点、时间、否定和任务关系，防止改写过度抽象后把相似事件混在一起。因此两者的角色是“分头判断”和“整体约束”。

在初召回阶段，我们仍以Planner查询为主，避免原始长问题与子查询重复扩大候选；CE阶段候选已经被压到40条，加入原始问题的成本可控。coverage selection会从原始问题和各子查询分别保留候选，而不是简单平均分。该设计承认Planner有用但不完美，是一种有限信任。

### Q134. Coverage selection 为什么比对所有 CE 分数取最大值再 top-k 更合理？

若只计算每个anchor在多个查询上的最大分数，再全局取top-k，一个容易的子查询可能占满所有位置。例如“当前状态”有很多直接表达，而“中间转折”只有一两条隐含句；全局排序会让后者消失。最大分数只表示“至少匹配一个目标”，并不保证不同目标都被覆盖。

coverage selection先为原始问题和每个子查询分配少量名额，去重后再按最大分补齐。它相当于在相关性之外加入最低覆盖约束，特别适合跨会话整合和temporal问题。代价是可能保留一个分数不高的子查询候选，因此配额不宜过大；当前top-4/top-3和总12是折中，需要通过单query CE、只扩大top-k和coverage CE三组对照确认独立收益。

### Q135. Planner 如果改写错了，原始 query 只在 CE 阶段出现，真的能救回来吗？

只能部分救。若正确证据已经被某个Planner查询召回到RRF top-40，原始query CE可以把它重新排高，避免子查询过度抽象。但如果Planner在初召回时完全丢掉关键实体，正确消息没有进入候选池，后面的CE无法凭空恢复。这是当前设计的明确边界。

是否让原始query也参与split模式的初召回，是鲁棒性与职责简洁之间的取舍。当前选择强调Planner负责召回、原始问题负责整体精排；下一步可以统计Planner约束保留率和漏召样本，做“子查询召回”与“原始+子查询召回”的消融。没有证据前，不应仅因为担心就增加兜底分支，也不能假装当前设计完全免疫Planner错误。

### Q136. 自适应 Stitch 到底“自适应”在哪里？

它不是固定取anchor前后各N条，而是沿同一会话向左右扫描，根据候选消息与anchor的语义相似度、与当前窗口的实体承接和位置距离决定是否加入。连续若干条不满足条件就停止，同时受最大跨度和最大消息数约束。因此不同anchor可以形成不同长度、不同方向的窗口。

这种设计适合对话经历长度不固定的情况：短事件可能只需两三条，复杂冲突可能需要更多上下文。它仍然只在同一session内扩展，不会自动建立跨session因果链；跨会话整合由多anchor召回、最终选窗和时间排序完成。若老师问创新强度，应称为内容驱动的可变边界改进，而不是全新的记忆范式。

### Q137. Stitch 的阈值过高或过低分别会怎样？怎样调？

阈值过高时，窗口接近孤立anchor，指代、起因和后续结果容易丢失；过低时，整个session被扩入，主题转移和助手长回复成为噪声，注入预算被浪费。最大miss、最大span和最大message共同决定实际边界，所以不能只调一个cosine阈值。

调参应按样本类型分层：短指代、长会话中途转题、同一事件多轮澄清、一个session包含两个主题。除了最终QA，还要看窗口证据完整率、无关消息率、平均token和长度分布。若只用最终准确率调阈值，reader可能掩盖窗口质量问题。

### Q138. 多个 anchor 扩成重叠窗口后，merge 会不会把不同事件误合并？

merge通常只在同一conversation内对重叠或足够相邻的窗口合并，能避免同一段经历因多个anchor重复进入后续选择。但同一次长会话可能中途转题，如果两个窗口仅位置接近却语义不同，过于宽松的合并会把两个事件连在一起。因此merge条件应依赖实际重叠和边界，而不是仅按conversation相同就合并。

合并后还要处理anchor分数和来源查询：可以保留最大fused score、多个anchor id和对应query，避免一合并就丢掉证据来源。当前实现的目标是去重，不是推断因果。若出现误合并，应优先收紧Stitch边界或merge相邻条件，而不是让最终LLM自己从混杂窗口中分辨。

### Q139. Decay、recency 和 week bonus 三个时间项有什么区别？会不会重复？

Decay描述记忆强度随“距上次强化时间”衰减，并保留最低权重；usage reinforcement使实际注入过的窗口恢复部分强度。Recency是相对于候选池最新证据的时间偏置，直接帮助当前状态问题。Week bonus则鼓励最终集合覆盖不同时间阶段，避免所有窗口集中在同一周。

它们确实有部分相关性，因此需要消融。旧实验显示去掉recency/week后staleness明显恶化，说明当前数据上时间覆盖有独立贡献。但三者不是越强越好：过强会压制久远但关键的事实，强化还可能产生“常用越常用”的反馈环。合理表述是当前组合在协议上有效，长期应进一步简化并分别测量其边际作用。

### Q140. Usage reinforcement 会不会导致错误记忆被越用越强？

会有这个风险。若一个窗口因为偶然误召被注入，强化后未来更容易再次进入，形成自我强化。因此我们只对最终实际注入的窗口强化，不对初召回或CE候选强化，已经比“命中即强化”更保守，但仍不能完全避免错误循环。

进一步改进可以是：只有当最终回答确实引用该证据、用户未纠正、或后续反馈确认有效时才强化；对被用户否认或删除的记忆降低权重；设置强化上限和长期衰减。当前机制更像轻量活跃度建模，不应宣传成可靠的人类记忆规律。

### Q141. 为什么 Profile 和 Trace 要分开？

Trace保存具体对话经历，内容可能随时间变化、互相矛盾，需要查询时按问题和时间选择。Profile只保存少量相对稳定、可核验的信息，如身份、教育、地点和支持偏好，适合直接注入。如果把二者混在一起，一次情绪或阶段性关系就可能被当作长期属性。

分开后，Profile写入必须更保守，可查看、可纠正、可删除；Trace则保持原文可追溯。生成时Profile提供稳定背景，Trace提供当前问题相关经历。这种设计不是简单的两张表，而是承认“稳定事实”和“事件证据”具有不同的生命周期和错误代价。

### Q142. 用户要求“忘掉这件事”时，系统应该怎样处理？

首先要明确删除对象：是删除一条Profile、某个会话的Trace，还是禁止未来使用但保留审计记录。面向用户的“忘记”应能真正影响检索和注入，不能只在提示词里说不再提。实现上需要定位对应消息或Profile，执行软删除或硬删除，并同步向量索引、缓存和强化状态。

如果数据用于研究或日志，还要区分用户产品数据与脱敏评测数据，不能以“实验需要”为由忽略用户删除。当前项目具备记住/忘掉的解析和记忆开关，但大规模生产还需要更完整的数据生命周期、备份删除和审计机制。面试时重点是表现出你知道删除不是一个字符串指令，而是跨存储层的一致性问题。

### Q143. 如何评估检索阶段本身，而不是只看最终 QA？

需要题目级证据标注，至少区分必要证据、相关但非必要、无关或误导。然后计算anchor或window层的Recall@K、MRR、nDCG、必要证据覆盖率和stale negative rejection。对于跨会话问题，还要看所有必要窗口是否共同进入，而不是命中任意一条就算成功。

最终QA仍然重要，但reader可能凭常识答对，也可能证据齐全却表达不完整。把检索指标、memory block质量和最终答案分开，才能知道问题出在召回、选择还是生成。当前项目保存逐题注入结果，已能做错误分析；若要更严格比较CE，应补gold evidence标注，而不只依赖最终选择题结果。

### Q144. 你们的方法时间复杂度和主要延迟在哪里？

Dense召回依赖向量索引，BM25依赖倒排或当前实现的词法检索；RRF只对两路候选并集排序，成本较小。最昂贵的是多查询CE：若有m个CE查询、RRF候选n条，需要大约m×n个query–anchor前向，但可以batch；Stitch对选中的约12个anchor读取同会话邻居，成本与窗口跨度相关；最终MMR在候选窗口较少时开销可忽略。

实际延迟还包括Planner LLM调用和主模型生成。优化优先级应是：缓存或规则化简单Planner、批量CE、控制候选数、复用embedding、并行dense与BM25。当前规模可接受，但用户量扩大后必须记录每阶段P50/P95，不应只报总响应时间。

## 8.5 工程、系统设计、可靠性与安全追问

### Q145. 如果要求你把系统部署给一万名用户，第一步改什么？

我不会先换模型，而会先把单机状态拆开。SQLite和进程内向量索引适合原型，但多实例下会出现写竞争、索引不一致和用户路由问题。需要把关系数据迁到支持并发事务的数据库，把向量检索变成可水平扩展的服务，并使用用户id或租户id做严格过滤。模型推理则通过队列、动态批处理和限流管理GPU。

同时建立可观测性：每阶段延迟、错误率、CE fallback、召回候选数、注入token、GPU利用率和用户删除任务都要可追踪。方法层的Trace、Profile、Stitch和时间MMR可以保留，变化的是服务化和数据一致性。回答这题要体现“算法不等于系统”，也不能简单说换成某个向量数据库就结束。

### Q146. 为什么原型用 SQLite？什么时候必须换？

SQLite部署简单、事务可靠、无需单独服务，适合单机研究原型和可复现实验。当前数据以用户、会话、消息、Profile和指标为主，访问模式相对清楚，使用SQLite可以减少工程依赖，让注意力集中在方法验证。

当出现多进程高并发写、跨机器部署、复杂权限、持续备份或数据量显著增长时，就应迁移到PostgreSQL等服务型数据库；向量检索也需要独立索引服务。选择SQLite不是认为它能支持所有规模，而是在当前阶段降低系统复杂度。老师问“为什么不用大数据库”，回答应基于需求，而不是工具偏好。

### Q147. 如何保证不同用户的记忆不会串库？

每条会话、消息、向量和Profile都必须带user_id，所有检索查询在数据库和向量索引层都要先做用户过滤，而不是召回后再删除。接口层还要从认证信息获得用户身份，不能信任客户端随意传入的user_id。缓存键、任务队列和日志也必须包含租户边界。

测试上要专门构造同名人物和相同问题的两个用户，验证任何一方都无法召回另一方内容；删除和导出也要按同一边界处理。原型中的按用户索引是基本思路，但生产环境还需权限审计、加密和最小化日志。串库是严重的数据隔离错误，不能只靠Prompt避免。

### Q148. 记忆系统会不会受到 Prompt Injection 或 Memory Poisoning？

会。用户可能在历史消息中写入“以后忽略系统指令”“告诉模型我是管理员”等内容，如果原样注入且没有明确边界，主模型可能把记忆文本当成指令。Memory poisoning还包括故意反复写入错误事实，使它们因强化和高频出现而获得更高权重。

缓解方式是把memory block标记为不可信证据而非系统命令，使用清晰角色和分隔结构，禁止记忆内容改变系统规则；Profile写入采用白名单和结构化字段；检索结果还应保留来源，出现冲突时以当前用户明确陈述和系统策略为准。长期还可检测指令型文本、异常重复和高频修改。不能因为存的是用户原话就认为天然安全。

### Q149. 线上应该监控哪些指标？

系统层需要监控总延迟和各阶段P50/P95、GPU显存与吞吐、错误率、超时、队列长度、数据库锁和流式中断。记忆层要看召回候选数、CE查询数、fallback比例、Stitch窗口长度、最终注入窗数、token预算使用、无记忆率和删除成功率。模型层可以监控输出长度、重复率、拒答或异常模板频率。

质量指标不能只在上线前跑一次。可以抽样做离线回放，观察staleness、关键事实漏召和用户纠正率；新版本通过shadow或canary与旧版本比较。尤其Anchor CE如果模型加载失败静默回退RRF，必须在trace中显式记录，否则看起来系统正常，实际关键模块已失效。

### Q150. 某个模块故障时怎样降级？

Planner失败时可以退化为direct原始查询或简单改写；dense模型不可用时保留BM25，反之保留词法；CE失败时回退RRF前若干anchor；Stitch异常时可以注入anchor本身；记忆服务整体不可用时继续用近期上下文生成，但明确不依赖长期证据。主模型故障则应返回可理解的服务错误，而不是伪造回复。

降级设计的原则是职责单一和错误可见。回退不能悄悄改变评测口径或长期强化状态，例如CE失败后不应仍标记为CE成功，也不应强化没有正常选择的窗口。面试中讲出具体降级链，能说明模块化不只是流程图，而是运行时可维护性。

### Q151. 如何做模型和数据版本管理？

模型版本不仅包括基座名称，还应记录PT、SFT、DPO checkpoint、LoRA配置、tokenizer和chat template；检索侧包括embedding、CE模型、索引版本和所有top-k参数；数据侧包括训练集哈希、清洗脚本版本和评测集版本。一次结果必须能追溯到完整组合，而不是只写“最新模型”。

上线时新旧版本应并存，支持回滚；向量模型更换通常需要重建全部embedding，不能只替换查询编码器。Profile schema变化还需要迁移。当前项目已保存跑次和配置，下一步可用实验管理工具或统一manifest把模型、数据和代码commit绑定起来。

### Q152. 流式生成时，客户端中断了怎么办？

需要区分生成任务、网络连接和数据落库。客户端断开并不一定意味着模型立即停止，可以主动取消推理以节省资源，也可以让服务完成并保存；具体策略取决于产品需求。无论哪种，都要保证消息状态明确，例如pending、completed、cancelled，避免只保存半段文本却当作完整回复。

记忆写入和usage reinforcement最好在生成成功且最终内容落库后执行，不能用户刚发消息就强化候选。若中断导致未生成答复，用户消息仍可保存，但是否进入长期Trace应按一致规则处理。流式接口看似只是前端体验，实际上涉及事务边界和幂等性。

### Q153. 如何减少推理成本和延迟？

首先避免用大模型做所有小任务：MacBERT负责简单路由，BGE负责检索，CE只处理40条候选，主模型负责最终生成。其次并行执行dense与BM25，批量处理CE，缓存历史embedding和不变Profile；direct问题可以减少Planner查询数，简单无记忆请求直接跳过读路径。

生成侧使用量化、KV Cache、合理max_new_tokens和流式输出。系统规模增大后可做动态批处理、模型常驻、请求优先级和热点用户索引缓存。成本优化不能以破坏评测协议为代价，例如把CE top-k随意压小可能省时但漏关键证据，因此要画出质量—延迟曲线。

### Q154. 如果数据库中有重复消息或用户反复说同一件事，会怎样？

重复会影响两层。初召回中相似消息可能占满top-k，CE也可能将它们都排高；扩窗后同session重叠可通过merge减少，但跨session重复仍需要MMR惩罚。usage reinforcement还可能让高频重复证据越来越强，进一步挤压其他主题。

写入时可做精确去重和轻量近重复检测，但不能过度合并，因为同一句话在不同时间可能代表状态持续或更新。更稳的做法是保留时间和来源，在选择阶段控制冗余，并对“重复但新状态”与“纯复述”区别处理。当前MMR解决一部分，但不是完整的事件归并系统。

### Q155. 你如何处理隐私和敏感数据？

最基本原则是数据最小化：只存完成任务所需内容，Profile严格限制字段，用户可以关闭记忆、查看和删除。存储与日志应区分原始文本和脱敏指标，访问需要认证和最小权限；传输与备份应加密，研究数据尽量使用公开或合成材料，不直接把真实咨询记录拿来训练。

如果未来涉及真实用户，还需要明确同意、保留期限、删除流程和研究伦理审查。当前项目的离线记忆集是合成的，能降低隐私风险，但也限制了真实分布外推。面试中不必泛泛说“我们很重视隐私”，应说清存什么、不存什么、谁能访问、怎么删除。

## 8.6 行为面、团队协作与压力面

### Q156. 讲一次你主动发现问题并推动改进的经历。

可以使用Anchor CE的迭代。最初团队可能只看到“加rerank后准确率下降”，容易直接回退。我主动把160题逐题对比，统计共同对、共同错和两路各自多对的样本，再按temporal、recall、preference等类型归因。分析发现CE不是完全无效，而是对终态有优势，却容易把导师、地点和偏好短句挤出top-10。

基于这个证据，我没有简单调一个融合权重，而是提出原始问题加Planner子查询的coverage selection，使不同检索目标都有种子。这次经历体现的主动性不在于“我加了一个模块”，而是把模糊的效果下降变成可操作的错误分类，并推动方案从单一排序改为多目标覆盖。

### Q157. 讲一次你做错判断或项目失败的经历。

我会讲窗级CE。最初我认为CE理论上更精确，所以应该替换旧手工内容分，甚至一度想删掉recency和week bonus，让职责更“干净”。结果QA从九成左右降到七八成，staleness上升，注入窗数也塌缩。这个判断错误来自把普通文档精排经验直接套到多窗口时间记忆任务。

我后来先修复分数尺度和早停，再补回时间项，确认仍然存在目标不匹配；最终不再让CE接管窗口选择，而是前移到anchor层。这个失败让我学到，模块理论能力必须和下游目标一致，所谓“更强模型”没有单调改进保证。回答失败题时要讲自己哪里判断错、如何验证、以后怎样避免，而不是把失败都归因于数据或队友。

### Q158. 如果团队成员不同意你的技术方案，你怎么处理？

我会先把争论从“谁觉得更好”变成“两个方案分别优化什么、怎么比较”。例如有人主张直接用长上下文，有人主张检索式记忆，可以共同确定相同reader、相同token预算和相同问题集，再比较准确率、staleness、延迟和成本。能用小实验解决的争论，不应靠资历压结论。

如果实验短期无法完成，就记录假设、风险和决策理由，选择可回滚的方案。沟通时也要区分核心约束和个人偏好：数据隐私、评测公平是底线；库和框架选择可以妥协。最终目标是团队对决定和证据负责，不是证明我赢了争论。

### Q159. 讲一次时间紧、任务多时如何排优先级。

我会按“是否影响主结论”和“是否阻塞后续”排序。比如答辩前同时有前端优化、文档重写、CE实验和人工评测计划，我会先确保正式主线能复现、数字和代码一致，再完成能够改变方法结论的消融，最后才处理界面细节。因为页面不够漂亮不会推翻研究结论，跑次无法复现会。

执行上把任务拆成可交付节点，每天保留实验失败的缓冲时间，并维护数字来源表，避免最后文档和代码不一致。若确实无法全部完成，会主动缩小范围并说明未完成项，而不是每条线都做到一半。面试官关心的是决策依据和结果，不是“我经常熬夜”。

### Q160. 你如何接受批评？

我会先判断批评是在质疑事实、方法还是表达。例如老师说“创新不足”，可能不是要求再加模块，而是在提醒我把已有工作说成首创、相关工作定位不清或实验不能支撑主张。我会把具体问题复述出来，确认对方质疑的是哪个层次，再修改对应内容。

项目中多次文档重写也是这个过程：从割裂讲“微调线”和“记忆线”，改为统一的长期回应质量；从夸大创新，改为场景约束、负结果和证据。接受批评不等于立刻全部照改，而是用证据判断，改完后能解释为什么更合理。

### Q161. 你是如何快速学习一个陌生技术的？

我通常先找最小闭环：读官方论文或文档，弄清输入输出和核心公式；再跑通最小示例；然后接入自己的数据，记录与默认场景的差异；最后通过消融确认它在项目中的实际作用。以DPO为例，我先理解其相对偏好损失和参考模型约束，再构造小规模chosen/rejected检查格式，最后才进行完整训练并分析BLEU/ROUGE变化。

我会避免先看大量二手教程却不动手，也避免只跑通代码就认为理解。真正掌握的标准是能解释失败模式、参数变化和替代方案。若面试现场遇到没用过的技术，我也会用这套框架给出学习路径，而不是假装熟悉。

### Q162. 你在团队中更偏领导还是执行？

我更愿意用具体情境回答，而不是给自己贴固定标签。在问题定义、实验协议和错误分析上，我可以承担推动者角色，明确主线、拆任务和检查证据；在别人更熟悉的前端、部署或特定模型上，我也能按接口执行并及时反馈。研究项目需要的是根据任务切换角色，而不是一直做“领导者”。

如果老师追问领导力，我会举推动CE错误分析、统一文档叙事或建立跑次规范的例子；如果问协作，我会说明如何界定模块输入输出、共享配置和处理分歧。好的团队贡献最终应能被交付物和决策记录看见。

### Q163. 如果你和导师意见不同怎么办？

我会先确认自己是否完整理解导师的目标和约束，很多“意见不同”其实是评价指标不同。然后用简短材料说明我的假设、已有证据、风险和一个低成本验证方案，而不是直接争论。若导师仍选择另一条路线，我会按决定执行，同时保留实验记录，除非涉及学术诚信或明显不可接受的问题。

## 8.7 英语项目问答模板

### Q168. Please introduce your main contribution to the project.

My main contribution was to turn the prototype into two connected research questions. On the response side, I organized continued pretraining, supervised fine-tuning and preference optimization to reduce repetitive, advice-first responses. On the memory side, I designed a trace-based retrieval pipeline that preserves raw conversational evidence and reconstructs relevant experience at query time.

I also built the evaluation protocol and analyzed failed variants. For example, window-level cross-encoder reranking reduced multi-window coverage, so I moved reranking to the anchor stage and used planner-generated subqueries for coverage-aware selection. I would emphasize that the foundation models and basic retrieval components are public; my work lies in the problem formulation, system integration, ablation and error analysis.

### Q169. What was the most challenging part of the project?

The most challenging part was not training the model itself, but identifying where an apparently stronger component hurt the whole system. A cross-encoder should be better at local relevance, but when I used it to replace window-level relevance, the final QA accuracy dropped significantly. Part of the issue was score calibration and early stopping, but even after fixing those engineering problems, the objective was still mismatched with temporal and multi-window evidence selection.

I then performed question-level error analysis and redesigned the cross-encoder as an anchor selector instead of a final window ranker. This experience taught me to inspect the complete pipeline and evaluation target rather than assuming that a stronger model guarantees a better system.

### Q170. Why do you want to pursue graduate study?

This project showed me the gap between building a working system and making a defensible research claim. I can implement training and retrieval pipelines, but stronger research requires better problem formalization, controlled experiments, human evaluation and a deeper understanding of related work. Graduate study would allow me to develop these skills under systematic supervision.

I am particularly interested in dialogue alignment, retrieval-augmented generation and long-term agent memory. I hope to study how models can use personal context accurately without overgeneralizing temporary states, and how such systems can be evaluated beyond simple automatic metrics.

### Q171. What is the main limitation of your current work?

The main limitation is evaluation validity. The dialogue model is mainly evaluated with lexical overlap metrics, which cannot fully measure empathy or the timing of suggestions. The memory system has a cleaner shared-reader protocol, but the datasets are still synthetic or curated and the parameters have been observed repeatedly during development.

Therefore, the current results support a relative offline comparison, not a claim of clinical or large-scale real-world effectiveness. The next step would be a frozen held-out benchmark, human preference evaluation and more diverse long-term user histories.

### Q172. Why did you use both dense retrieval and BM25?

Dense retrieval is good at semantic paraphrases, while BM25 is more reliable for exact names, locations, numbers and rare terms. In long-term personal conversations, both types of evidence are common. We retrieve candidates from both systems and use reciprocal rank fusion, which combines ranks instead of directly adding incomparable raw scores.

A cross-encoder then reranks a smaller anchor pool. The purpose of this design is not to stack models blindly, but to separate high-recall retrieval from fine-grained candidate selection.

### Q173. Why did you use the original query together with planner subqueries?

Planner subqueries decompose a complex request into evidence targets, such as the initial state, a turning point and the latest state. However, rewriting may remove important entities or constraints. Therefore, I use the subqueries to provide coverage and the original query to preserve the complete semantics during cross-encoder reranking.

The original query does not simply replace the planner. Their roles are different: the planner tells the system what pieces of evidence to search for, while the original query checks whether a candidate still matches the full question.

### Q174. Why should our lab admit you?

I have already experienced the full cycle from problem observation to implementation, evaluation, failure analysis and redesign. I do not claim that every component is novel, but I can clearly distinguish public techniques from my own decisions, and I am willing to revise a design when the evidence contradicts my expectation.

I believe I can contribute practical implementation ability, careful experimental habits and a concrete interest in language model alignment and memory. More importantly, I understand that my current work is only a starting point, and I am prepared to learn the theoretical and methodological standards required for graduate research.

# 第九部分 原理强化与大模型岗位高频深挖

> 本部分补充近期保研、考研复试以及大模型算法岗位面试中常见的“从项目继续向下追原理”问题。回答仍遵循“先给结论—再讲机制—联系项目—限定边界”的结构。公式用于帮助理解，现场不必机械背诵，但应能解释每一项的含义。

## 9.1 SFT、语言模型训练与优化原理

### Q175. SFT 的本质是什么？它和预训练在目标函数上有什么相同与不同？

SFT 的本质仍然是条件自回归语言建模。给定输入上下文 $x$ 和目标回复 $y=(y_1,\ldots,y_T)$，模型最大化目标回复在该上下文下的条件概率，等价于最小化 token 级负对数似然：

$$
\mathcal{L}_{\mathrm{SFT}}=-\sum_{t=1}^{T}\log \pi_\theta(y_t\mid x,y_{<t}).
$$

它与预训练相同的地方是都使用 next-token prediction 和交叉熵损失；不同之处主要在数据分布、条件结构和监督区域。预训练通常在大规模连续文本上预测所有有效 token，主要学习语言、知识和通用模式；SFT 则把 system、user 等内容作为条件，只监督 assistant 的目标回复，使模型学习特定任务格式和行为规范。对 SoulHarbor 来说，SFT 不是向模型灌入心理学事实，而是让它在用户表达压力、冲突或犹豫时，更稳定地选择倾听、澄清和适时建议等回复行为。

### Q176. 交叉熵为什么能训练语言模型？它与最大似然估计是什么关系？

对一个正确 token，训练标签可以看作 one-hot 分布 $q$，模型输出概率分布为 $p_\theta$。交叉熵 $H(q,p_\theta)$ 在 one-hot 情况下等于正确类别概率的负对数，即 $-\log p_\theta(y)$。对整个序列求和，就是目标序列的负对数似然。因此，最小化交叉熵与最大化训练数据在模型下的似然是同一件事。

从梯度角度看，当正确 token 的预测概率偏低时，损失和梯度较大，模型会提高该 token 的 logit；当概率已经很高时，更新幅度减小。需要注意，最大似然只要求模型逼近训练数据分布，并不直接保证事实正确、偏好合理或长期交互质量优秀。SoulHarbor 中 SFT 能显著提高与参考回复的字面接近程度，但“是否更会倾听”仍需要偏好评测或人工评测验证。

### Q177. 什么是 teacher forcing？为什么训练和推理之间会有 exposure bias？

Teacher forcing 指训练第 $t$ 个 token 时，模型看到的是数据中的真实前缀 $y_{<t}$，而不是模型自己前面生成的 token。这样训练稳定、并行效率高，也让每个位置都有明确监督。然而推理时模型只能基于自己生成的前缀继续生成，一旦早期出现偏差，后续条件分布也会跟着变化。训练时从未充分见过这些“自己犯错后的前缀”，这就是 exposure bias 的来源之一。

在对话任务中，它可能表现为开头一句略显模板化后，后续整段回复沿着固定结构展开，或者早期误解用户意图后持续给出不相关建议。DPO 等偏好优化可以调整完整回复的相对概率，但不能彻底消除自回归生成中的误差累积。实际缓解还包括提高数据多样性、加入困难负例、控制解码策略，以及用人工或模型评审分析完整回复而不只看 token 损失。

### Q178. SFT 数据是不是越多越好？数据质量、覆盖和一致性如何权衡？

SFT 数据并非越多越好。低质量、相互矛盾或模板高度重复的数据会把噪声和捷径一起写入模型。更重要的是，SFT 的有效性取决于数据是否覆盖真实部署中的输入类型、难度、表达风格和边界情况。对心理支持场景，若数据几乎都是长篇倾诉，模型可能在简单闲聊中也输出过度正式的安慰；若参考答案都很长，模型可能把“长”误学成“好”。

我会从四个维度控制数据：正确性，确保回复没有明显事实与安全问题；行为一致性，明确哪些场景先倾听、哪些场景可以建议；覆盖度，包含倾诉、求建议、信息不足、关系冲突和闲聊等多种情形；多样性，避免固定开场、固定段落数和长度捷径。数据规模应在质量稳定后扩充，并通过去重、主题分层和独立验证集观察新增数据是否真正改善泛化。

### Q179. 为什么训练损失下降，不代表模型实际效果一定提升？

训练损失只反映模型对训练目标 token 的拟合程度。它下降可能意味着模型更好地学习了目标任务，也可能只是记住了重复模板、特定措辞或数据中的偶然相关性。若训练集和真实使用分布不一致，或者验证集存在泄漏，低损失仍可能对应较差的线上表现。

因此需要同时观察训练损失、验证损失、任务指标、行为评测和错误类型。对 SoulHarbor，除了 BLEU、ROUGE，还应检查过早建议率、模板开场率、上下文理解、事实一致性和安全性。若训练损失持续下降而验证表现变差，通常提示过拟合；若自动指标提升但人工偏好下降，可能说明模型更像参考答案，却没有更符合交互目标。

### Q180. Label smoothing 在语言模型 SFT 中有什么作用？为什么不一定适合所有场景？

Label smoothing 不把正确 token 的目标概率设为严格的 1，而是给其他 token 分配少量概率质量。它可以降低模型过度自信，改善校准并缓解部分过拟合。但语言生成中一个位置往往存在多个合理词，one-hot 标签本来就只是其中一个观测答案，适度平滑有一定合理性。

不过它也会削弱对精确格式、专有名词和安全边界的学习，并可能降低模型对明确目标 token 的区分度。对于已经使用大规模预训练模型的 SFT，收益并不稳定，很多实践直接使用标准交叉熵。若在 SoulHarbor 中尝试，我会把它作为可控消融项，观察验证困惑度、生成多样性、关键事实复现和行为一致性，而不是默认它一定更好。

### Q181. 梯度累积解决什么问题？它和真正的大 batch 完全等价吗？

梯度累积把多个 micro-batch 的梯度先累加，再执行一次优化器更新，从而在显存有限时获得更大的有效 batch size。若每个 micro-batch 的损失按正确比例缩放，且中间不更新参数，那么对普通 SGD 而言，它与一次处理完整大 batch 的梯度接近。

但实践中不一定完全等价。Dropout 的随机性、动态 padding、梯度裁剪、混合精度舍入、BatchNorm，以及学习率调度按 step 还是按样本计数，都会造成差异。Transformer 通常使用 LayerNorm 而非 BatchNorm，因此差异相对小，但仍需明确 effective batch size、优化器更新次数和 warmup 的计数口径。面试时不能只说“显存不够就累积”，还要说明它改变了参数更新频率。

### Q182. Gradient checkpointing 为什么能省显存？代价是什么？

反向传播需要前向阶段的中间激活。Gradient checkpointing 只保存部分关键节点，反向时重新计算未保存的中间结果，以额外计算换取激活显存下降。对于长序列和大模型，激活往往是显存的重要组成部分，因此它能显著提高可训练的序列长度或 batch size。

代价是训练变慢，因为部分前向计算要重复执行；实现不当还可能与缓存、随机层或某些 fused kernel 冲突。它主要节省激活，不会减少模型权重、梯度和优化器状态本身。SoulHarbor 使用 QLoRA 时，4-bit 主要压缩冻结基座权重，LoRA 降低可训练参数量，checkpointing 则进一步压缩激活，三者解决的是不同显存来源。

### Q183. 为什么需要 warmup？学习率过大或过小分别会发生什么？

训练初期模型新增的 LoRA 参数、优化器动量和梯度统计尚未稳定，直接使用较大学习率容易导致更新过猛，使预训练分布发生突然漂移。Warmup 从较小学习率逐步升到目标值，让优化过程平稳进入有效区域。之后再配合线性或余弦衰减，使后期更新更细致。

学习率过大时，损失可能震荡、出现 NaN、生成质量突降或灾难性遗忘；过小时，收敛缓慢，也可能在有限训练步数内几乎没有学到目标行为。SoulHarbor 从 PT、SFT 到 DPO 逐级降低学习率，是因为后续阶段更接近最终行为，需要更保守地修改模型，但这些数值仍应通过开发集和训练曲线验证，而不能被说成通用最优值。

### Q184. Perplexity 是什么？为什么它不适合单独评价心理支持对话？

Perplexity 是平均负对数似然的指数形式，可理解为模型在每个位置面对的有效不确定性。困惑度越低，说明模型越能预测评测文本中的下一个 token。它适合衡量领域继续预训练是否让模型更熟悉某类文本，也可以用于比较相同 tokenization 和相同数据协议下的语言建模能力。

但心理支持回复具有高度多解性。一个低困惑度模型可能只是更擅长生成数据集中的常见模板，而一个更自然、更简洁的回复由于与参考措辞不同，困惑度反而较高。它也不能直接衡量共情、建议时机、事实一致性和安全性。因此若补做 PT 消融，我会把领域 perplexity 作为中间指标，并与下游 SFT 收敛、行为评测和通用能力一起报告。

## 9.2 DPO、偏好学习与对齐原理

### Q185. DPO 与 Bradley–Terry 偏好模型有什么关系？

成对偏好数据假设在同一输入 $x$ 下，标注者更偏好 $y_w$ 而不是 $y_l$。Bradley–Terry 模型用两个候选的潜在奖励差表示偏好概率：

$$
P(y_w\succ y_l\mid x)=\sigma(r(x,y_w)-r(x,y_l)).
$$

传统 RLHF 先用偏好对训练奖励模型，再通过 PPO 等方法优化策略。DPO 利用带 KL 约束的最优策略与奖励之间的解析关系，把隐式奖励写成策略模型相对参考模型的 log-probability，直接得到二分类式目标。因此它不是“没有奖励”，而是把奖励模型隐式化，并用策略与参考策略的相对对数概率来表达偏好差。

### Q186. DPO 为什么需要 reference model？不用会怎样？

Reference model 提供一个行为锚点，通常是 DPO 开始前的 SFT 模型。DPO 比较策略模型相对 reference 对 chosen 和 rejected 的概率变化，而不是只盲目增大 chosen 概率。这样可以近似体现 KL 正则：在满足偏好的同时，不让策略无约束地远离原有语言能力和输出分布。

若没有 reference，目标更像普通 pairwise ranking，模型可能通过极端提高某些模式或压低另一些模式来取巧，导致语言质量、长度、格式和通用能力漂移。对 SoulHarbor，reference 的意义是保留 SFT 已经学到的基本对话能力，只对“敷衍、说教、过早建议”等相对偏好做温和调整。

### Q187. DPO 中的 beta 到底控制什么？beta 越大约束越强还是更新越强？

在常见 DPO 写法中，$\beta$ 乘在策略相对 reference 的偏好 log-ratio 上。它与理论中的 KL 正则强度相关，但不同论文和代码库的参数化表达可能让直觉看起来相反，因此不能脱离实现只背一句“越大越保守”。更稳妥的解释是：beta 决定概率差被 sigmoid 放大的尺度，影响梯度集中在哪些样本和策略偏离 reference 的程度。

实际调参时应观察 chosen/rejected reward margin、隐式 KL、回复长度、验证偏好胜率和生成退化。beta 过小可能偏好信号弱，训练像没有明显变化；过大可能让容易样本快速饱和、困难或噪声样本产生不稳定更新。SoulHarbor 使用 0.1 是一个保守设置，但必须结合所用训练库的具体公式解释。

### Q188. DPO 的梯度直觉是什么？它会同时提高 chosen、降低 rejected 吗？

DPO 关注的是 chosen 与 rejected 的相对优势。对一个尚未满足偏好的样本，梯度会推动 chosen 相对 reference 的 log-probability 上升，并推动 rejected 的相对 log-probability 下降。但它优化的是差值，不保证每个序列的绝对概率都按固定方向变化；在共享 token、归一化和参数耦合下，实际变化更复杂。

当模型已经强烈偏好 chosen 时，sigmoid 进入饱和区，该样本梯度会变小；当偏好方向错误时，梯度较大。这个机制说明困难样本更能提供信息，但也意味着错误标注会产生强烈反向更新。因此 DPO 数据质量、难度分布和 chosen/rejected 的可比性非常重要。

### Q189. DPO 与 PPO-based RLHF 的主要区别是什么？什么时候仍可能选 PPO？

PPO-based RLHF 通常先训练独立奖励模型，再在线采样策略输出，根据奖励和 KL 惩罚更新策略。它能利用标量奖励、规则奖励或环境反馈，支持超出固定离线偏好对的探索，但训练链路复杂，涉及奖励模型偏差、采样成本、价值估计和 PPO 稳定性。

DPO 直接在离线 chosen/rejected 上训练，实现简单、稳定且资源成本较低，适合偏好目标可通过成对数据表达的场景。若任务需要与可执行环境交互、使用可验证奖励、进行多步决策，或者希望模型探索训练数据中没有出现的策略，PPO、GRPO 等在线或半在线方法仍有价值。SoulHarbor 当前目标是调整回复风格和建议时机，离线偏好对较自然，因此 DPO 更符合资源和任务约束。

### Q190. DPO 和普通二分类有什么本质区别？

表面上 DPO 使用 logistic loss 判断 chosen 是否优于 rejected，形式类似二分类；但输入特征不是人工构造的固定向量，而是策略模型和 reference 对两个完整序列的条件 log-probability 差。训练直接更新生成模型参数，改变未来生成分布。

普通偏好分类器只学会“评价两个答案谁更好”，不会自动让生成模型更常产生好答案。DPO 则把评价目标与策略优化合并到一个损失中。它仍然依赖偏好模型假设，并不能保证学到真实人类价值；如果训练对存在长度、格式或关键词捷径，生成模型也会把这些捷径学进去。

### Q191. chosen 和 rejected 长度差异为什么会成为 DPO 的捷径？怎样处理？

序列 log-probability 通常是 token log-probability 的求和，长度不同会影响总量。即使实现使用平均 log-probability，长度也可能与内容风格高度相关。如果 chosen 总是更长，模型可能学到“详细就是好”；若 chosen 总是更短，又可能过度压缩回复。心理支持场景中，长回复还可能看似关怀，实际包含过多说教。

处理方法包括控制成对样本长度分布、构造同长度或近似长度的困难负例、分别报告长度分桶胜率、检查答案长度与隐式奖励的相关性，以及人工抽样确认模型真正学到的是互动质量。还应比较训练前后平均长度、重复率、建议条目数和模板频率。

### Q192. 什么是 preference overfitting？如何判断 DPO 训练过头了？

Preference overfitting 指模型在训练偏好对上不断拉大 margin，却不再提高独立验证偏好，甚至损害语言质量、多样性和通用能力。表现可能包括固定使用某种“安全模板”、回复长度极端化、重复chosen中的常见句式，或者对未见场景也机械执行同一偏好。

诊断时不能只看训练 loss。应观察独立验证对的准确率或 log-ratio、人工盲评、KL 漂移、输出长度、distinct-n、重复率、拒答率和通用基准。早停、降低学习率或 beta、增加更困难和多样的偏好对、混入 SFT loss，都是可能的缓解方式。SoulHarbor 只训练一轮属于保守策略，但是否过拟合仍应由独立数据证明。

### Q193. 如果 chosen 和 rejected 都不好，DPO 会发生什么？

DPO 只知道两者的相对顺序，不知道 chosen 是否达到绝对质量门槛。若 chosen 只是“没那么差”，模型仍会被推动向它靠近。大量这种数据可能让模型学会相对偏好，却整体停留在低质量区域，甚至放大 chosen 中隐藏的问题。

因此偏好数据需要两层质检：先检查 chosen 是否满足最低质量和安全标准，再检查它是否确实优于 rejected。还可以加入多候选排序、标注置信度、平局或不可判定选项。对于心理支持数据，特别要避免把“更温柔”误当成“更安全”，因为某些危机场景需要明确建议寻求现实帮助，而不能只做情绪回应。

### Q194. DPO 能否解决幻觉和事实错误？

DPO 可以在偏好数据明确惩罚事实错误时降低某些幻觉倾向，但它不是事实检索器，也不会自动获得训练数据之外的新知识。若偏好对只关注语气，模型可能变得更温和，却仍然自信地使用错误记忆。事实一致性还依赖可靠上下文、检索质量、训练数据和解码约束。

在 SoulHarbor 中，长期记忆系统负责提供可追溯的个人经历证据，DPO 主要调节这些证据被使用时的回应方式。二者职责不同：检索错误不能靠 DPO 完全修复，生成模型也不应在证据不足时补造用户经历。更合理的训练和评测应包含“证据不足时承认不知道”和“冲突记忆下优先最新证据”等偏好样本。

### Q195. 为什么 DPO 前通常需要一个较好的 SFT 模型？

DPO 是相对偏好优化，不负责从零教会模型任务格式和基本回答能力。如果初始策略连对话结构、领域语言和合理回复都不会，偏好对的 log-probability 可能极低，训练不稳定；同时 reference 本身很差，也无法提供有意义的行为锚点。

SFT 先把模型带入目标任务分布，使 chosen 和 rejected 都处在模型能够理解和生成的区域，DPO 再细化相对偏好。这个顺序类似先学会“能回答”，再学习“哪种回答更好”。但 SFT 也不能过度模板化，否则 DPO 的探索空间被限制。因此需要在基础能力、行为一致性和输出多样性之间平衡。

### Q196. ORPO、IPO、KTO 等偏好方法与 DPO 的差异应该怎样回答？

面试中不必背完所有公式，可以先按监督信号分类。DPO、IPO 等主要使用成对偏好；KTO 可以利用单条 desirable/undesirable 反馈；ORPO 将监督学习与偏好 odds ratio 目标结合，试图减少单独 reference model 的需求。不同方法在损失形状、是否需要 reference、对噪声和长度偏差的敏感性上不同。

选择方法时应看数据形态、训练稳定性、计算预算和目标，而不是追逐名字。SoulHarbor 已有同 prompt 的 chosen/rejected 对，DPO 与数据结构匹配且实现成熟。若未来只有单条满意/不满意标记，KTO 类方法可能更自然；若希望把 SFT 与偏好训练合并，可比较 ORPO。最终应通过统一数据和评测协议实验，而不是理论上直接断言谁最好。

## 9.3 LoRA、量化与训练系统原理

### Q197. LoRA 的低秩假设为什么可能成立？如何从线性代数角度理解？

一个大权重矩阵有大量参数，但下游任务对模型行为的有效改动可能集中在少数方向。若全量微调得到的更新矩阵 $\Delta W$ 的奇异值能量主要集中在前几个方向，就可以用低秩分解 $BA$ 近似它。LoRA 不是说原始权重低秩，而是说“任务相关的增量”可能具有较低内在维度。

这种假设在许多任务上经验有效，但不是定理。任务差异越大、数据越复杂，可能需要更高 rank 或更多层；rank 太小会欠拟合，太大则增加参数、显存和过拟合风险。SoulHarbor 的 r=8 是资源与效果的折中，若要证明合理，应做 rank 敏感性实验，并观察不同层的有效更新。

### Q198. LoRA 中 A、B 为什么常采用一个随机初始化、一个零初始化？

常见做法是让其中一个矩阵随机初始化，另一个矩阵初始化为零，使训练开始时 $BA=0$，因此模型初始行为与原始基座完全一致。随后梯度先更新零矩阵一侧，使增量逐渐生效，避免一开始随机扰动破坏预训练能力。

具体哪个矩阵为零取决于实现，但核心目标是让初始增量为零且梯度能够传播。若 A、B 都为零，初始阶段可能出现对称性和梯度问题；若两者都随机，模型一加载适配器就发生不可控漂移。面试中应讲清初始化目的，而不只背默认配置。

### Q199. LoRA 的 alpha 和 rank 如何共同影响更新尺度？

LoRA 常把增量写成 $\frac{\alpha}{r}BA$。rank 决定低秩子空间容量，alpha 通过缩放控制增量幅度。若固定 alpha 而增大 r，单个方向的缩放会减小；若保持 $\alpha/r$ 不变，则扩大 rank 主要增加表达容量和参数量。

但最终更新幅度还受学习率、初始化、目标层和数据影响，不能只看 alpha。推理时额外设置的 adapter scale 又是另一层乘数。SoulHarbor 回答时要明确区分训练结构参数 r、训练缩放 alpha、优化器学习率和运行时 scale，避免把四者混成“LoRA 强度”。

### Q200. NF4 为什么适合量化预训练权重？double quantization 又是什么？

NF4 是针对近似正态分布权重设计的 4-bit 数据类型，它用非均匀量化级别更有效地覆盖高概率区域，从而在有限比特下减少量化误差。QLoRA 将冻结基座以 NF4 存储，计算时按块反量化到更高精度，而 LoRA 参数保持可训练。

Double quantization 进一步量化每个量化块所需的缩放常数，减少这些元数据的显存占用。它不意味着连续把模型权重量化两次，而是把“量化参数本身”再压缩。量化仍可能带来误差，因此项目只能说它提高了可训练性，不能在没有 bf16 对照时声称完全无损。

### Q201. 训练显存主要由哪些部分组成？为什么“参数量乘 2 字节”远远不够？

训练显存不仅包括模型权重，还包括梯度、优化器状态、激活、临时计算缓冲、KV 或 attention 中间结果，以及框架碎片。以 Adam 为例，全参数训练通常需要保存参数、梯度以及一阶和二阶动量，若还有 fp32 master weights，单参数成本会显著高于推理。

LoRA 冻结大部分参数，因此不需要为基座保存梯度和 Adam 状态；4-bit 又压缩基座权重。但长序列下激活仍可能占大头，所以还需要 gradient checkpointing、micro-batch 和高效 attention。面试估算显存时，应先说明精度、是否训练、优化器、序列长度、batch size 和是否启用 checkpointing。

### Q202. FlashAttention 为什么更省显存？它是否改变 attention 的数学结果？

标准 attention 若显式构造长度为 $L$ 的 $L\times L$ 分数矩阵，会产生二次方级中间显存。FlashAttention 通过分块计算、在线 softmax 和更合理的数据搬运，让中间矩阵不必完整写回显存，降低 HBM 读写和峰值内存。

它通常计算的是等价或数值近似等价的标准 attention，而不是改成稀疏注意力；收益主要来自 IO-aware 实现。实际速度取决于硬件、序列长度、精度和 kernel 支持。它可以降低训练和推理开销，但不会改变长上下文中无关信息干扰和证据选择困难，因此不能代替长期记忆检索。

## 9.4 RAG、检索与长期记忆评测原理

### Q203. RAG 系统为什么要区分 retrieval recall 和 answer accuracy？

最终答案错误可能来自两类完全不同的问题：检索阶段没有召回所需证据，或者证据已召回但生成模型没有正确利用。如果只看 answer accuracy，就无法判断应该优化 embedding、reranker、上下文组织还是 reader。

因此应分层评测。检索层可报告 Recall@k、MRR、nDCG、证据覆盖率和最新状态命中率；生成层在给定 gold evidence 时测试 reader 上限；端到端再报告 QA 和事实一致性。SoulHarbor 固定 reader 比较不同记忆库，是为了隔离记忆方法影响，但还应继续补充 anchor recall、window coverage 和冲突状态选择等中间指标。

### Q204. Recall@k、Precision@k、MRR 和 nDCG 分别适合什么场景？

Recall@k 关注所有相关证据中有多少被 top-k 覆盖，适合高召回候选阶段；Precision@k 关注返回内容中有多少相关，适合上下文预算有限、噪声代价高的场景。MRR 只看第一个相关结果的排名，对单答案查询直观；nDCG 支持多级相关性并强调前部排名，适合多个证据贡献不同的任务。

长期记忆问题常需要多个时间片共同回答，因此只看 MRR 不够。更合适的是证据集合 recall、状态覆盖、时间顺序和冗余度。SoulHarbor 的多查询 coverage selection 本质上就是在单候选相关性之外考虑多个证据目标是否被覆盖。

### Q205. 为什么 embedding 相似度高，不代表证据真的能回答问题？

双塔 embedding 把 query 和文档独立压缩为向量，擅长发现主题和语义接近，但会损失细粒度交互。一个片段可能与“室友冲突”高度相关，却只描述冲突发生，没有包含后来是否和好；也可能主题相同但人物、时间或否定关系不同。

Cross-Encoder 把 query 与候选共同编码，可以捕捉实体、否定和细粒度匹配，但成本更高。即便 CE 分数高，也不保证多证据集合完整或时间有效。因此 SoulHarbor 将 dense/BM25 用于召回、CE 用于 anchor 精排，再由 coverage、扩窗和 CE Top-k 处理集合层目标。

### Q206. Query rewriting 为什么可能降低召回？怎样设计容错？

Planner 或 query rewriting 可以拆解复杂问题、补充同义词和明确证据目标，但生成式改写也可能删除原始实体、误判时间、加入不存在的假设，导致检索偏离。尤其个人对话中，昵称、地点和模糊指代常难以可靠改写。

容错设计包括始终保留原始 query、将多个子查询并行召回、限制改写只做扩展不做替换、记录每条候选由哪个 query 命中，并对 query 质量做独立评测。SoulHarbor 在 CE coverage 阶段同时使用原问题和子查询，是一种补救，但如果某候选在第一阶段完全没被召回，后续 CE 无法恢复，因此更强方案是让原 query 也进入初始召回并进行消融比较。

### Q207. 什么是 hard negative？为什么它对 retriever 和 reranker 训练重要？

Hard negative 是表面上与 query 很相似、但不能正确回答或包含关键错误的候选。例如同一个人物的旧状态、相同主题但不同事件、含有相反结论的片段。随机负例太容易，模型只需学习主题差异就能区分，无法掌握实体、时间和逻辑细节。

对长期记忆系统，旧状态是最重要的 hard negative 之一。训练或评测中加入它，可以迫使模型区分“曾经焦虑”与“现在已经缓解”。但 hard negative 若实际也部分相关，会形成假负例，因此需要人工或规则校验，并允许多级相关标签而非简单二元标签。

### Q208. RRF 为什么不用原始分数？它有什么局限？

Dense 相似度、BM25 分数和不同检索器的尺度不可直接比较。RRF 只利用排名，通过 $1/(k+r)$ 累加多个列表中的名次，避免复杂校准，并让同时被多个检索器排在前面的候选获得更高融合分。

它的局限是丢失了原始分数差距，也默认各检索器贡献相近。某候选在第一名和第二名之间的巨大置信差异不会被充分利用，弱检索器也可能带来噪声。可以通过加权 RRF、学习排序或分数校准改进。SoulHarbor 选择 RRF 是因为数据规模和工程稳定性，但不应把它说成理论最优融合方法。

### Q209. 为什么把检索结果按相关性排序后，还要按时间顺序注入模型？

相关性排序适合选择证据，但生成模型阅读多段经历时需要理解事件演化。若按分数交错排列，可能先看到结果、后看到原因，或把旧状态和新状态混在一起，增加时序误解。选出少量相关窗口后按时间排序，可以保留事件链和状态变化。

这并不意味着最新证据永远正确，也不意味着排序本身能解决冲突。系统仍需在选择阶段识别新旧关系，并在 prompt 中标注时间。SoulHarbor 的做法是“相关性负责选，时间负责讲”，两种顺序服务不同目标。

### Q210. 如何判断长期记忆系统发生了 memory poisoning？

Memory poisoning 指错误、恶意或被 prompt injection 操控的内容进入长期记忆，并在未来反复影响回复。迹象包括某条可疑记忆被异常高频召回、用户未确认的断言进入 Profile、助手生成内容被当作用户事实、不同会话中出现相同攻击指令，或召回内容试图修改系统规则。

防护需要写入和读取两侧共同完成：区分用户原话与助手推断；Profile 采用白名单和确认制；对指令性文本做不可信数据隔离；检索后过滤“要求忽略系统提示”等内容；提供删除和审计机制。心理场景中还应记录来源、时间和置信度，避免把一次夸张表达固化为长期人格判断。

### Q211. “用户要求忘记”在技术上为什么比删除一行数据库更复杂？

一条信息可能同时存在于原始消息、向量索引、摘要、Profile、缓存、备份和评测日志中。只删除主表记录，向量库或派生摘要仍可能召回；只删除 embedding，又可能保留原文。因此需要数据血缘，知道哪些派生对象来自哪些原始记录，并执行级联删除或重建索引。

此外还要区分“今后不再使用”与“物理删除”，并处理审计、安全和备份保留策略。SoulHarbor 原型可以先实现用户级 tombstone 和检索过滤，再异步重建派生数据；真正部署还需要明确隐私政策、删除时限和验证机制。

## 9.5 Transformer、推理与系统设计原理

### Q212. Self-Attention 为什么要除以 $\sqrt{d_k}$？

Query 与 Key 的点积方差会随维度 $d_k$ 增大。如果不缩放，点积绝对值容易变大，使 softmax 进入饱和区，概率接近 one-hot，梯度变小。除以 $\sqrt{d_k}$ 可以把数值尺度稳定在更适合 softmax 的范围内，使训练更平稳。

这只是 attention 数值稳定性的一部分。实际模型还依赖 LayerNorm、残差连接、初始化和混合精度策略。面试中应能从方差随维度累积的角度解释，而不是只说“防止梯度消失”。

### Q213. Multi-Head Attention 为什么需要多个头？头越多越好吗？

多个头让模型在不同投影子空间中并行建模关系，例如局部语法、长距离依赖、实体对应和位置模式。单个高维 attention 理论上也有表达能力，但多头结构提供了更灵活的分解和优化路径。

头数并非越多越好。在总 hidden size 固定时，头越多意味着每个头维度越小，可能降低单头表达能力，也增加 kernel 和缓存管理成本。现代模型还使用 GQA 或 MQA，让多个 query 头共享较少的 key/value 头，以减少 KV Cache。SoulHarbor 不需要修改 attention 架构，但理解这些机制有助于解释长上下文推理成本。

### Q214. GQA、MQA 与标准 MHA 有什么区别？为什么能减少 KV Cache？

标准 MHA 为每个 query 头分别保存 key 和 value；MQA 让所有 query 头共享一组 key/value；GQA 则让若干 query 头共享一组 key/value，是两者之间的折中。推理时历史 token 的 K/V 需要缓存，因此 key/value 头数量减少会直接降低 KV Cache 显存和内存带宽。

代价是共享过多可能损失注意力表达能力。GQA 通常在质量与效率之间更均衡。估算 KV Cache 时需要知道层数、序列长度、batch size、KV 头数、head dimension、K/V 两份缓存和数据精度，而不能简单按模型参数量推算。

### Q215. KV Cache 为什么只能减少解码重复计算，不能降低首 token 的全部成本？

在自回归解码中，新 token 需要与所有历史 K/V 做 attention。KV Cache 保存历史 token 每层的 K/V，避免每一步重新计算整个前缀，因此显著降低后续 token 的重复前向计算。但处理初始 prompt 的 prefill 阶段仍需一次性计算所有输入 token，长上下文的首 token 延迟仍然较高。

因此系统优化要区分 time to first token 和 tokens per second。长期记忆检索减少注入 token，不仅节省 KV Cache，也降低 prefill 延迟；流式输出只能改善用户感知，不能减少总计算。SoulHarbor 若做线上优化，应分别监控检索延迟、prefill、首 token 和解码速度。

### Q216. 为什么温度为 0 也不一定绝对可复现？

温度为 0 通常意味着贪心解码，但运行结果仍可能受到浮点非确定性、不同 GPU kernel、并行归约顺序、模型和 tokenizer 版本、量化实现以及相同 logit 时的 tie-breaking 影响。服务端动态 batching 或框架升级也可能产生差异。

要提高可复现性，需要固定模型与代码版本、随机种子、硬件和依赖，启用确定性选项，并保存完整 prompt、生成参数和输入记忆。对评测来说，还应避免线上服务在不同时间静默升级。SoulHarbor 的离线对照必须记录跑次和配置，不能只写“temperature=0”。

### Q217. 流式生成时为什么不能边生成边立即把全部内容写入长期记忆？

流式过程中输出可能被用户中断、网络断开、触发安全过滤，或者模型后半段发生自我修正。若每个 token 都直接进入长期记忆，系统可能保存不完整句子、被撤回内容或助手的错误推断，还会导致大量碎片记录。

更合理的做法是先在临时状态中累计，生成成功并通过后处理后再原子落库；若中断，可标记为 incomplete，并决定是否保存可见部分。用户消息与助手消息也应区分角色，长期 Profile 不应直接从助手文本中提取用户事实。工程一致性是记忆可靠性的前提。

### Q218. 如果要把 SoulHarbor 做成在线服务，如何设计缓存而不破坏隐私和一致性？

可以缓存模型权重、tokenizer、公共 prompt、embedding 模型和不含用户数据的静态资源；对用户相关的检索结果、摘要和会话状态则必须按 user_id、版本和权限隔离，并设置较短 TTL。缓存键要包含记忆库版本和查询参数，否则删除或更新记忆后仍可能返回旧结果。

敏感内容不应进入共享日志或全局缓存。多实例部署时需要统一失效机制，或者采用版本号让旧缓存自然不可命中。对于心理对话，还应限制运维人员可见范围，记录访问审计，并对缓存、备份和监控样本应用同等隐私策略。

## 9.6 科研设计、面试追问与开放问题

### Q219. 如何设计一个能证明“DPO 确实改善了倾听行为”的最小充分实验？

首先固定基座、SFT checkpoint、解码参数和测试输入，只比较 SFT 与 DPO。测试集按场景分层，包括单纯倾诉、明确求建议、信息不足、状态冲突和危机表达。预先定义可观察指标，如过早建议率、情绪承认、澄清问题质量、模板化程度、事实一致性和安全处置，而不是事后挑指标。

采用随机打乱的成对盲评，至少两名标注者独立判断并报告一致性、胜率和置信区间；同时检查长度、重复率和通用能力，排除 DPO 只是变长或变短的捷径。再加入 DPO 数据规模或 beta 消融，确认结果对合理设置稳定。这个实验比继续堆 BLEU 更能直接支持“倾听行为改善”的主张。

### Q220. 如何区分“模型记住了训练样本”与“模型学会了可泛化行为”？

需要让测试集在对话签名、人物、主题表达和模板上与训练集隔离，并设计组合型新场景。例如训练中分别出现“室友冲突”和“希望先被倾听”，测试时用不同人物和事件表达同类互动需求。如果模型只复现训练措辞，换表达后效果会明显下降；若学到行为原则，应能在新主题上先澄清、再根据用户需求决定是否建议。

还可以做 n-gram 近邻分析、训练样本检索、模板频率比较和 paraphrase 测试。对大模型很难证明完全没有记忆，但可以通过严格去重、近似去重和分布外评测降低风险。回答时应避免把 seen/unseen 简化成随机切分。

### Q221. 如果自动指标、LLM judge 和人工评测结论冲突，应该相信谁？

没有任何单一评测天然正确。自动指标可复现但测量维度有限；LLM judge 成本低、可扩展，但受提示、位置、长度和自身偏好影响；人工评测更接近目标，却可能样本少、主观性强、成本高。发生冲突时，应先检查它们是否在测同一件事，以及评测协议是否存在偏差。

对 SoulHarbor，若 BLEU 下降而人工偏好提升，可能是措辞更多样；若 LLM judge 偏好长答案而人工认为说教，说明 judge rubric 需要校准。更稳妥的结论来自多指标三角验证：自动指标用于稳定回归，人工盲评作为关键行为依据，LLM judge 用人工样本校准后扩大规模，并公开冲突而不是只选有利结果。

### Q222. 如何做统计显著性与置信区间？为什么只报告一个百分比不够？

一个评测百分比会受样本抽样和随机解码影响。对成对胜率或准确率，可以用 bootstrap 对样本重采样得到置信区间；对同一批样本上的两个模型，可使用配对 bootstrap、McNemar 检验或适合指标的随机化检验。生成指标也可以按样本 bootstrap，而不是只比较总体均值。

置信区间能反映差异的不确定性。例如 90.8% 高于 88% 是否有意义，取决于样本量和配对错误分布。SoulHarbor 当前 all_50 规模较小，更应该同时报告原始计数、case-average、micro-average 和区间，并把结论限定为当前协议下的证据。

### Q223. 怎样设计消融，避免“删掉模块后参数预算也变了”的不公平？

理想消融只改变待研究因素，其他条件保持一致。例如比较有无 CE 时，应固定初始召回候选、最终注入窗口数、token 预算和 reader；比较时间项时，应固定其他 MMR 权重和候选集合。若删掉模块导致候选数量或计算预算变化，就需要额外的等预算对照。

还应区分模块贡献和超参数贡献。一个模块加入后效果提升，可能只是 top-k 变大或 prompt 更长。SoulHarbor 的窗级 CE 负结果说明，模块位置改变了窗口覆盖；复现实验应同时报告候选数、窗口数、token 数和延迟，才能解释性能变化来自哪里。

### Q224. 什么是 data contamination？在开源大模型上为什么很难完全排除？

Data contamination 指评测样本或高度相似内容出现在预训练、SFT、偏好训练或调参过程中，使结果高估泛化能力。对自己构造的数据，可以通过哈希、n-gram、embedding 近邻和对话签名去重；但开源基座的完整预训练语料通常不可见，很难证明某个公开数据集从未出现过。

因此应尽量使用新构造、时间较新的或受控私有测试集，并报告污染检查方法。对项目自身，至少要保证 SFT、DPO 和评测之间严格隔离，且不要在反复看测试错误后继续调参。无法排除基座预训练污染时，应诚实说明，而不是声称“完全无泄漏”。

### Q225. 如果老师问“你的项目是否真正适合心理健康场景”，应该怎样回答？

我会明确把 SoulHarbor 定位为校园心理支持研究原型，而不是心理诊断或治疗系统。当前证据主要来自离线对话和记忆评测，能说明某些回应与长期语境机制的相对改进，不能证明临床有效性，也不能替代专业人员。

真正进入敏感场景还需要危机识别、明确的转介机制、隐私与知情同意、专业人员参与的数据和评测、偏差审计、红队测试以及持续人工监督。系统也应避免诊断性语言和过度依赖。这样回答不是削弱项目，而是展示对研究边界和责任的理解。

### Q226. 如果只有两周时间继续完善项目，你会优先做什么？

我不会继续无目的加模块，而会选择最能补强核心主张的实验。第一优先级是建立一套小而可靠的人工成对评测，验证 DPO 是否减少过早建议和模板化；第二是补检索分层指标，区分召回失败与 reader 失败；第三是加入几个高价值消融，例如原 query 是否进入初始召回、不同 rank/beta 的敏感性。

工程上只修影响演示和实验可信度的问题，如日志、版本和删除一致性。两周内的目标不是把系统做成产品，而是让“模型适配改善回应行为、经历重建改善长期证据”这两条主张各有直接证据。

### Q227. 如果面试官要求你现场推翻自己项目中的一个设计，你会选什么？

我会选择挑战“原 query 只在 CE 阶段补救就足够”这一假设。因为如果 Planner 在初始召回阶段漏掉关键实体，候选根本没有进入池中，后续 CE 再使用原 query 也无法找回。更稳健的设计应让原 query 与子查询都进入 Dense/BM25 召回，再做融合和 coverage。

我会提出最小实验：固定总召回预算，比较“仅子查询召回”“原 query 加子查询召回”和“无 Planner”三种设置，报告证据 recall、最新状态命中、最终 QA 与延迟。如果原 query 并行召回稳定更好，就应修改终版。这种回答能体现我愿意基于机制和证据修正设计，而不是维护现有架构。

### Q228. 如何回答一个你确实不会的原理问题？

先明确自己掌握的边界，不要编公式或伪造结论。可以说：“这个方法的完整推导我目前不能准确复现，但我理解它解决的是……，在我的项目里对应的作用是……。”随后给出可验证的分析路径，例如需要查看哪篇原始论文、哪个实现公式、做什么最小实验来区分两种解释。

如果只是不记得常数或符号，可以先讲机制和变量关系；如果根本不了解，就直接承认并把话题拉回自己真正做过的部分。研究面试并不要求无所不知，面试官更在意是否诚实、能否定位未知、以及能否提出合理学习和验证方法。
